# 🏛️ Local Architecture Blueprint

## Layer 1: Foundations
- **Repository Purpose**: Ansina is a self-owned AI agent exposing a single internal REST API — no chat channels — built around a small always-on "Heart" model (in-process, ≤4B/8k-ctx) and a large remote "Brain" model (35B+) for actual reasoning.
- **Tech Stack**: Python ≥ 3.14 / FastAPI / SQLite. Embedded inference in-process via MLX (the only `HeartRuntime` adapter shipped so far, Apple-Silicon-only); a portable, non-Apple-Silicon fallback (originally scoped as llama-cpp-python) is deferred to a follow-up issue — see Layer 5. See `docs/architecture/blueprint.md` for the full rationale and the OpenClaw comparison this design departs from.

## Layer 2: Directory Layout
- `Makefile`: dev-workflow entry point — bootstraps `uv` (Astral installer, macOS/Linux) if missing, wraps `sync`/`lint`/`format`/`typecheck`/`test`/`check`/`clean` for the daemon, plus a parallel `tui-*` set (`tui-sync`/`tui-lint`/`tui-format`/`tui-typecheck`/`tui-test`/`tui-check`, issue #31) for the standalone `tui/` project below — `check`/`tui-check` stay independent so `check` keeps mirroring the `check` CI job exactly; `check-all` runs both.
- `src/ansina/`: Core application source code (src-layout package, `py.typed` marker for downstream type-checking).
- `src/ansina/__main__.py`: Process entry point (`python -m ansina` / the `ansina` console script). Loads config, configures logging, builds the app via `create_app()`, hands it to uvicorn.
- `src/ansina/api/`: REST API surface (issue #4). `create_app()` in `api/app.py` is the FastAPI factory. `api/middleware.py` assigns/echoes the request id and feeds `logging`'s correlation-id contextvar. `api/auth.py` (issue #5, redesigned by #24, its chain formalized by #25, extended by #26) enforces a bearer token, deny-by-default — every route needs one except `PUBLIC_PATHS` (`/healthz`, `/readyz`, and — issue #43, the first non-health-probe entries — `/auth/oidc/login`/`/auth/oidc/callback`, since a caller cannot be authenticated before completing a login). `BearerAuthMiddleware` walks an `Authenticator` chain (`auth.authenticator.build_authenticators(db, settings)` — issue #28 added `settings` so `ApiTokenAuthenticator` can read `[security] token_last_used_resolution_seconds`; a required constructor param, no in-middleware default, so a follow-up milestone's OIDC authenticator is an append, not a rewrite) rather than a comparison against one static config secret, resolving a full `auth.principal.Principal` (user + every role reachable direct-or-via-group) onto `request.state.principal` — offloaded via `anyio.to_thread.run_sync` so the blocking sqlite scan + per-row hash comparison never stalls the event loop. An inactive user's token stops authenticating (`auth.authenticator.resolve_principal`'s own check — `find_user_by_api_token` itself doesn't filter on `users.active`). `security.enabled = False` (not "no token configured" — that now means "auto-generate one") is the only way to disable enforcement, and `config.settings` refuses to boot at all if that's paired with a non-loopback bind. Once a `Principal` is resolved, an `X-Sudo-Token` header (issue #26) is additionally checked against `app.state.sudo` (`auth.sudo.SudoService`) and, on a live match, elevates it via `Principal.with_sudo()` — an absent/expired/wrong/revoked grant never turns into a 401 by itself, it just fails to elevate, leaving a sensitive route's own 403 `CODE_SUDO_REQUIRED` as the only signal. `api/authorization.py`'s `require(resource, *, sensitive=False)` (issue #25) is the FastAPI dependency every non-public route declares — the verb is read from `request.method`, not declared per-route — answering "does the caller's `Principal` hold a role with a `role_permissions` row for (this resource, this verb)" via `auth.authorization.authorize()`, offloaded the same way; denial raises `ForbiddenError`/`SudoRequiredError` (403, `CODE_FORBIDDEN`/`CODE_SUDO_REQUIRED`), distinguishable from `BearerAuthMiddleware`'s 401 (`CODE_UNAUTHORIZED`, no/invalid identity) without leaking which credential component was wrong; every decision (granted or denied) is audit-logged with actor/resource/verb. `api/route_audit.py`'s `audit_route_coverage()` (issue #25) walks `app.routes` at `create_app()` time and raises `RouteCoverageError` — same "fail loudly before uvicorn binds a port" pattern as `HeartUnavailableError` — if any non-public route lacks exactly one `require(...)` declaration; its surviving declarations are also the `resources` catalog's entire source (replacing #24's `BOOTSTRAP_RESOURCES` seed constant, since deleted). Issue #38 has it additionally union each surviving route's `route.methods` into its resource's served-verb set (filtering out anything outside `Verb`, e.g. `OPTIONS` — never grantable, since `require()` itself 403s an unmapped verb), carried on `ResourceSpec.verbs` into the catalog alongside the name/description. `api/problems.py` + `api/exception_handlers.py` map every error door (`AnsinaError`, HTTP errors, validation errors, unhandled exceptions) to RFC 9457 `application/problem+json`. `api/readiness.py` is a named-check registry backing `GET /readyz`; later milestones register their own checks there instead of editing the route. `api/routes/health.py` holds the M0 routes: `/healthz`, `/readyz`, `/version` (`GET /version` gated `require("system.version")`). `api/routes/heart.py` (issue #11) holds Ansina's first non-health, non-public routes: `GET /heart/tick` (status), `POST /heart/tick/pause`/`/resume` (the tick loop's kill switch) — all gated `require("heart.tick")`, and all return 503 `problem+json` (`CODE_HEART_DISABLED`) when `app.state.tick_loop` is `None` (only once authorization already passed — a caller without a grant gets 403 without ever learning whether the Heart is even enabled). `api/routes/openapi.py` (issue #25) serves `GET /openapi.json` behind `require("system.openapi")` as a real, gated `APIRoute` — `create_app` passes `openapi_url=None, docs_url=None, redoc_url=None` to the `FastAPI` constructor, since the framework's default `/docs`/`/redoc`/`/docs/oauth2-redirect` are plain Starlette routes that can't carry a `require(...)` declaration (and are non-functional with auth enabled anyway — no `fastapi.security` scheme is declared for Swagger UI's "Authorize" button, since auth here is middleware-level). `api/routes/sudo.py` (issue #26, generalized by #37) holds `POST /auth/sudo` (step up via `app.state.sudo.step_up()`, gated `require("auth.sudo")`), `DELETE /auth/sudo` (revoke your own grant, same resource), and the break-glass `DELETE /auth/sudo/grants` (revoke every active grant, gated `require("auth.sudo.grants", sensitive=True)` — reaching it already requires a live grant); all three are `auth.*` resources so `auth.policy.permitted_verbs` restricts them to Maintain/Admin with no policy change. Issue #37 makes the sudo gate itself fail-closed — `auth.authorization.authorize()`'s `sensitive=True` branch now requires a live grant from any role but `Admin`, not only `maintain`, so a future custom role (#40) granting an `auth.*` permission can't bypass step-up by not being named `maintain` — and generalizes `auth.step_up.StepUpRegistry.for_principal` from one fixed verifier to every verifier the caller is actually enrolled in (`StepUpVerifier.is_enrolled`, backed by `auth.repositories.CredentialRepository.has_credential`); `SudoService._resolve_factor` picks among them via an optional `payload["factor"]`, raising the new `StepUpUnavailableError` (403 `ansina.auth.step_up_unavailable`) — before any failed-attempt bookkeeping runs — when zero factors are enrolled, an unrecognized `factor` is named, or 2+ are enrolled with none named to disambiguate. `api/routes/users.py`/`groups.py`/`role_assignments.py`/`roles.py`/`permissions.py` (issue #27) round out the RBAC management surface Users/Groups/Roles the rest of M2 exists to protect. `users.py` (`GET`/`POST /auth/users`, `GET`/`PATCH`/`DELETE /auth/users/{id}`, `PUT /auth/users/{id}/password`, `POST`/`GET /auth/users/{id}/tokens`, `DELETE /auth/users/{id}/tokens/{token_id}`) and `groups.py` (`GET`/`POST /auth/groups`, `GET`/`PATCH`/`DELETE /auth/groups/{id}`, `PUT`/`DELETE /auth/groups/{id}/members/{user_id}`) each gate `GET` `sensitive=False` and every mutation `sensitive=True` on one resource (`auth.users`/`auth.groups` respectively); `DELETE /auth/users/{id}` is a one-way tombstone (`UserRepository.soft_delete`), never a row removal. Issue #28 narrows `POST .../tokens`: it mints a user's *first* `api_token` credential, never a second (`auth.management.assert_no_existing_api_token` — 409 otherwise, checked ahead of the bootstrap-identity guard below since its message actively misleads that identity); beyond the first, the user mints their own via `POST /auth/me/tokens`, and revoking their last token drops the count back to zero, making the admin route double as the lost-credential recovery path. All three token routes build on `api/tokens.py` (issue #28) — `TokenOut`/`IssueTokenRequest`/`IssuedTokenResponse` plus `issue_token()`/`list_tokens()`/`revoke_token()`, shared with `me.py` below, lifted out the same way `api/identity.py` was once a second router needed the identical shape. `issue_token()`/`revoke_token()` both call `auth.management.assert_not_bootstrap_identity()` — the bootstrap identity holds exactly one `api_token`, ever, so neither route can mint it a second one or delete the one it has (403 `ansina.auth.bootstrap_identity`); its `GET` is unaffected. Issue #39: `TokenOut` gains `expires_at: str | None` (`null` for a never-expiring token, the response shape for every existing route today); `issue_token()` gains optional keyword-only `ttl_seconds`/`clock` params — unreachable from HTTP as of this issue (`me.py`/`users.py` call it positionally with no keywords, so every route-issued token still gets `expires_at=NULL`), the seam issue #43's OIDC-minted token is the first to actually pass, minting a genuinely short-lived credential. `ttl_seconds <= 0` raises `ValueError` rather than minting a token already expired at issuance. `role_assignments.py` holds the four nested attach/detach routes (`POST`/`DELETE /auth/users/{id}/roles/{role_id}` and the `/auth/groups/...` equivalent, resource `auth.role_assignments`, always `sensitive=True`) and additionally runs every assignment through `auth.management.assert_may_assign_role` (skipped only when `security.enabled = False` leaves no resolved `Principal` to check against). `roles.py` (issue #27, custom-role write routes added by #40) and `permissions.py` (issue #27, made trustworthy by #38) are the role/permission-catalog pair. `GET /auth/roles` lists every role with its current `role_permissions` grants; builtin roles stay permanently read-only (owned by `auth.reconciler.reconcile_builtin_roles`), but issue #40 adds `POST /auth/roles` (create a non-builtin role with an initial grant set), `PATCH /auth/roles/{id}` (replace a non-builtin role's grant set wholesale via `RolePermissionRepository.replace_for_role` — one transaction, not a diff), and `DELETE /auth/roles/{id}` — all three `sensitive=True` on the same `auth.roles` resource, so #37's fail-closed sudo gate covers them the same way it covers every other `auth.*` mutation. `PATCH`/`DELETE` refuse a `builtin=1` role (`BuiltinRoleError`, 409) regardless of caller; `DELETE` additionally refuses (`RoleInUseError`, 409) a role still referenced by any `role_assignments` row — checked in the repository layer before any `DELETE` statement runs, never left to `role_assignments.role_id`'s `ON DELETE CASCADE` to decide. Every mutation runs the submitted `(resource, verb)` grant set through two guards in `auth.management`, in order: `assert_grants_grantable` (issue #40 — is each grant catalogued, `grantable` per `auth.policy.is_grantable`, and a verb the resource actually serves per #38's `Resource.verbs`? An uncatalogued or non-grantable resource can never be an escalation, so this runs first) and `assert_may_grant_permissions` (issue #40's generalization of `assert_may_assign_role`'s own subset/`auth.*`/`admin` logic over a raw grant set rather than an existing role's — the same self-escalation check now runs at grant-*edit* time, not only at role-assignment time). `GET /auth/permissions` (issue #38): each catalogued resource with the verbs it's *actually served on* — not `list(Verb)` unconditionally — plus its `auth.policy.PolicyClass` (`ordinary`/`auth`/`self`) and a `grantable` flag, `False` for every `me.*` resource since every builtin role already holds every verb there — the discovery surface `POST`/`PATCH /auth/roles` (#40) builds on. `api/routes/role_mappings.py` (issue #42) is `GET`/`POST`/`DELETE /auth/role-mappings` on a single `auth.role_mappings` resource — no policy change needed, since it falls under `auth.policy`'s existing `auth.`-prefix rule the same way `auth.roles` does. `POST` treats a submitted mapping as a *deferred* role assignment: it runs `auth.management.assert_may_assign_role` against the mapped role (not `assert_may_grant_permissions` — a mapping names one role, not a raw grant set), so a sudo'd `Maintain` can't stage a mapping onto `admin` for a future login sync to later apply; a submitted `role_id` that doesn't exist is checked and refused (404) *ahead* of the insert, so a typo is never mistaken for `idx_role_mappings_tuple`'s own 409 (both `role_mappings.role_id` and `role_assignments.role_id` are foreign keys, and either would raise the identical `sqlite3.IntegrityError`). `api/routes/oidc.py` (issue #43) is `POST /auth/oidc/login` + `GET /auth/oidc/callback` — the OIDC federated-login exchange, and the only routes in `PUBLIC_PATHS` beyond the two health probes, since a caller cannot hold a bearer token before it has logged in; neither declares a `require(...)`, so `route_audit.audit_route_coverage` skips both the same way it already skips `/healthz`/`/readyz`, and neither contributes a `resources` catalog entry. Both answer 503 (`ansina.auth.oidc_disabled`) when `app.state.oidc is None` (`[security.oidc] enabled = false`, the default), mirroring `routes/heart.py`'s `CODE_HEART_DISABLED` shape. The route layer is thin: it validates the callback's own query parameters (`error=` present, or `code`/`state` missing, both 400 `ansina.auth.oidc_callback_failed`, checked before `ansina.auth.oidc.OidcLoginService` is even consulted) and, on success, mints the resulting `api_token` itself via `api/tokens.py`'s `issue_token(..., ttl_seconds=oidc.token_ttl_seconds, clock=oidc.clock)` — deliberately not inside the service, since `ansina.auth` (the package) never imports from `ansina.api` anywhere else in this codebase, and `ansina.api`'s own package `__init__` imports `create_app`, which imports back from `ansina.auth`; the service reaching into `api.tokens` would make that a circular import. `api/identity.py` (issue #30) holds the shared request-identity helpers — `current_principal(request)` (`request.state.principal` if `BearerAuthMiddleware` resolved one, else `None`) and `no_identity_response()` (the 401 `problem+json` for when it didn't) — lifted out of `routes/sudo.py`'s and `routes/role_assignments.py`'s own private copies once a third caller needed them; both now import from here instead. `api/routes/me.py` (issue #30, extended by #28 and #37) holds `GET /auth/me`, gated `require("me.profile")`: the first route on the `me.*` self-resource policy class (`auth.policy.is_self_resource`), reachable by every builtin role including `Read` and never sudo-gated, returning the already-resolved `Principal` (user, roles, sudo status) plus, as of #37, `step_up_factors` — the verifier names `SudoService.enrolled_factors()` reports the caller could currently succeed with, the one field on this route that costs a database read (a single indexed `credentials` lookup per enrolled-verifier check) beyond what `resolve_principal` already resolved — note the resource is `me.profile` while the path stays `/auth/me`, since a resource is a stable, dotted, URL-independent name, never the path. Issue #28 adds `POST`/`GET /auth/me/tokens` and `DELETE /auth/me/tokens/{token_id}` on a second self-resource, `me.tokens` — self-service issuance/listing/revocation of the caller's own tokens, built on `api/tokens.py` (see the `users.py` entry above), refused (403 `ansina.auth.bootstrap_identity`) for the bootstrap identity on `POST`/`DELETE` but not `GET`. Issue #41 adds a third self-resource, `me.totp` (`POST`/`GET`/`DELETE /auth/me/totp`) — the one `me.*` resource with a `sensitive=True` route: `authorize()`'s sensitivity check is a per-`require()`-call flag, not a name-pattern match, so `DELETE` (disable) can still demand a live sudo grant while `POST`(enroll)/`GET` (status) stay ungated, deliberately — requiring sudo to obtain a caller's *first* step-up factor would be an unsatisfiable chicken-and-egg lockout. `POST` generates a fresh RFC 6238 secret (`ansina.auth.totp`), stores it as an AES-GCM envelope (`ansina.auth.encryption.encrypt`) via `CredentialRepository.create_totp_secret`, and returns the raw secret plus an `otpauth://` URI exactly once — never recoverable afterward, same discipline as a minted API token; refused (409 `ansina.auth.totp_already_enrolled`) if already enrolled, and (503 `ansina.auth.encryption_key_missing`) if `[security.encryption] key` isn't configured. `DELETE` is idempotent (204 whether or not a credential existed), mirroring `SudoService.revoke_for_user`. `api/routes/users.py` gets the matching Admin recovery route, `DELETE /auth/users/{id}/totp` (`auth.users`, `sensitive=True`) — clears a lost-device enrollment on the user's behalf, reachable even though it shares no dependency with the user's own sudo state, so it's never itself blocked by the very lockout it exists to fix. Issue #48 adds a fourth self-resource, `me.password` (`PUT /auth/me/password`) — self-service password set/change, deliberately never `sensitive=True` either but for a different reason than `me.totp`'s enrollment: the request body's own `current_password` check *is* the proof-of-possession, the same one `PasswordStepUpVerifier` performs at `POST /auth/sudo`, so a sudo grant on top would mean requiring the password to change the password. A caller holding no password credential yet (the default shape of a user `POST /auth/users` creates without one) may omit `current_password` to set a first one, the same chicken-and-egg carve-out `POST /auth/me/totp` makes above. Both this route and `api/routes/users.py`'s two password-setting points (`CreateUserRequest.password`, `PUT /auth/users/{id}/password`) run the submitted password through `ansina.auth.password_policy.assert_password_acceptable` before it ever reaches `CredentialRepository.set_password`, refusing (400 `ansina.auth.weak_password`, `api/problems.py`) one that's too short, too long, contains the username, or is on the bundled common-password list.
- `src/ansina/config/`: Typed `Settings` (pydantic-settings). Layering: defaults → `ansina.toml` → `ANSINA_*` env vars. Load via `load_settings()`, never `os.getenv()` directly. Secrets are env-only — a `SecretStr` field set in the TOML file is a startup error. `database.path` is normalized (`~` expanded, relative paths resolved against CWD) by a `field_validator`, so every consumer sees one already-absolute path regardless of how it was configured.
- `ansina.example.toml`: documents the config file shape; copy to `ansina.toml` (gitignored) to use.
- `src/ansina/errors.py`: `AnsinaError` base exception with a stable, machine-readable `code` (`ClassVar[str]`); every subclass must declare its own `code` or class creation raises. `ansina.config.ConfigError` and `ansina.errors.StorageError` subclass it.
- `src/ansina/storage/`: SQLite persistence foundation (issue #6). `database.py`'s `Database` hands out one connection per thread (`threading.local`) rather than a single shared connection — sub-agents (later milestone) will read this database concurrently, and WAL lets those reads proceed unblocked by the writer; writes still serialize, per SQLite. Every connection gets `PRAGMA foreign_keys=ON` (per-connection state) and `PRAGMA busy_timeout` (so a second writer retries instead of failing instantly); `PRAGMA journal_mode=WAL` is per-database and verified once at `connect()`. `migrator.py`'s `run_migrations()` is a forward-only runner backed by a `schema_version` table, rejecting out-of-order or skipped versions; migrations themselves are plain numbered `.sql` files under `storage/migrations/`: `0001_init.sql` creates `schema_version` (no domain tables in M0); `0002_rbac.sql` (issue #24) adds the RBAC identity/permission schema — `roles`, `resources`, `role_permissions`, `users`, `"groups"` (always quoted — `GROUPS` is a SQLite keyword), `user_groups`, `role_assignments`, `credentials`, `external_identities`, `role_mappings`; `0003_sudo.sql` (issue #26) adds `sudo_grants` (one active grant per user, hash/salt never the raw token) and `sudo_lockouts` (at most one row per user, driven entirely by caller-supplied timestamps from an injectable clock — never a SQL-side `now`); `0004_user_tombstone.sql` (issue #27) adds `users.deleted_at` — a one-way marker distinct from `active`'s suspend/resume flag, set once by `UserRepository.soft_delete` and never cleared by any route; `0005_resource_verbs.sql` (issue #38) adds `resources.verbs` — a comma-separated, canonically ordered `Verb` list (`auth.models.encode_verbs`/`decode_verbs`) recording which verbs a resource's route(s) are actually served on, always rewritten whole by `sync_resources` and never queried by individual element, so a plain column rather than a join table. `0006_totp_credential.sql` (issue #41) widens `credentials.type`'s `CHECK` to accept `'totp'` via the standard SQLite 12-step table-rebuild procedure (no `ALTER` path exists for a `CHECK` constraint) and adds `idx_credentials_one_totp_per_user`, a partial unique index mirroring the existing one-password-per-user index; a `totp` row repurposes `hash` for an AES-GCM envelope (`auth.encryption`) rather than a one-way hash, and `last_used_at` for the last-accepted RFC 6238 step index rather than an ISO timestamp — both deliberate, type-scoped reuses of existing columns, not new ones. `0007_role_mapping_provenance.sql` (issue #42) adds `role_assignments.source TEXT NOT NULL DEFAULT 'local'` (backfills every historical row to `'local'`, no `CHECK` — the provider set is open by construction, same as `external_identities.provider`) and `idx_role_mappings_tuple`, a unique index on `role_mappings (provider, claim, value, role_id)` — the table has had neither since `0002_rbac.sql`. `0008_oidc_login_state.sql` (issue #43) adds `oidc_login_states` (`state` primary key, `nonce`, PKCE `code_verifier`, `expires_at`) — the in-flight state one authorization-code login carries between `POST /auth/oidc/login` and `GET /auth/oidc/callback`; no foreign key, since no `users` row exists yet at `/login` time, and `OidcLoginStateRepository.take()` deletes a row in the same transaction it reads it, making every row single-use. Both `Database` and `run_migrations()` are driven from `api/app.py`'s lifespan, never called ad hoc elsewhere.
- `src/ansina/auth/` (issue #24, extended by #25, #27, #28, #30, #37, #41, #42, #43, #47): the RBAC identity & permission domain layer — data + repositories + the authorization decision itself; the HTTP routes built on top of it live in `api/routes/{sudo,users,groups,role_assignments,roles,role_mappings,permissions,me,oidc}.py` and `api/tokens.py`, described in Layer 2's `api/` entry above. Permissions are rows, not an enum: every authorization check is a `role_permissions` lookup for (a role, a resource, a verb), so a future admin-defined custom role is an `INSERT`, not a rewrite. `models.py` holds one frozen dataclass per table (each with a `from_row(sqlite3.Row)` classmethod) plus the `StrEnum`s (`Verb`, `RoleSlug`, `SubjectType`, `CredentialType`) that constrain them — `CredentialType.TOTP` (issue #41) is the first member added since #24's original two, exercising the "typed from day one" design the enum was built for: only the schema (`0006_totp_credential.sql`'s `CHECK` widening) had to change, not the enum's own shape. `User.deleted_at` (issue #27) is the one-way tombstone marker, distinct from `active`'s suspend/resume flag; `Resource.verbs: frozenset[Verb]` (issue #38) is the served-verb set, with `ordered_verbs()`/`encode_verbs()`/`decode_verbs()` as the one place that set's canonical (`Verb`-declaration-order, comma-joined) string encoding is defined. `RoleAssignment.source` (issue #42, default `"local"`) records who created the row — `"local"` for anything made through the ordinary role-assignment routes, or a provider identifier for one `auth.role_sync.sync_mapped_roles` created and owns. `RoleMapping` (issue #42) is the new `role_mappings` dataclass — `(id, provider, claim, value, role_id)`, unique on the full tuple via `idx_role_mappings_tuple`. `OidcLoginState` (issue #43) is the new `oidc_login_states` dataclass — `(state, nonce, code_verifier, created_at, expires_at)`, the one-login-at-a-time state `auth.oidc_login.OidcLoginService` reads and deletes via `OidcLoginStateRepository.take()`. `hashing.py` ships two deliberately different credential-hashing paths: passwords use argon2id (`Argon2Params`, tuned via `[security.password]`) because a stolen hash must stay expensive to brute-force; API tokens use per-row-salted SHA-256 + `hmac.compare_digest` because `api/auth.py`'s middleware verifies one on every authenticated request, and argon2's deliberate work factor has no payoff against a high-entropy machine secret. `password_policy.py` (issue #48) is the acceptability policy every password-setting path (`api/routes/users.py`'s two routes, `api/routes/me.py`'s new one below) runs *before* a password ever reaches `hashing.py`: `assert_password_acceptable` checks length bounds (`[security.password] min_length`/`max_length`, widening the same table — `min_length` floored `ge=8` per NIST SP 800-63B, the standard this module's docstring also cites for deliberately shipping no character-class/composition rules; `max_length` is an argon2 work-factor DoS ceiling, not a strength rule), username containment, and — `reject_common` — membership in the bundled `auth/data/common_passwords.txt` (a SecLists-derived, ~2,100-entry list filtered to ≥8 characters, loaded once via `importlib.resources` so it resolves from an installed wheel). `CredentialRepository.set_password` itself stays policy-free, so `auth/bootstrap.py`'s provisioning paths (which never set a password) are structurally unaffected. `encryption.py` (issue #41) ships a *third*, deliberately reversible path for the one credential type neither of the above two fits: a TOTP secret must be recoverable in plaintext to verify a code against, which a one-way hash structurally cannot support — `encrypt()`/`decrypt()` wrap `cryptography`'s `AESGCM` in a versioned `v1:<nonce_b64>:<ciphertext_b64>` envelope keyed by `[security.encryption] key` (`config.settings.EncryptionSettings`, env-only, validated at load time to decode to exactly 32 raw bytes), with `resolve_key()` doing that same decode at read time; `ensure_key_configured_if_needed()` is the boot-time guard (`EncryptionKeyMissingError`, the `HeartUnavailableError` fail-loudly pattern, run from `api/app.py`'s lifespan since it needs the database open) refusing to start if any `totp` credential row exists with no key configured to decrypt it. No re-encryption/rotation path is built — a lost or rotated key means the affected enrollments are cleared (`DELETE /auth/users/{id}/totp`) and the user re-enrolls, documented rather than silently unsupported (M3's open consideration #3). `totp.py` (issue #41) is the pure RFC 6238 implementation — hand-rolled on stdlib `hmac`/`hashlib`/`struct`, no library, verified against the RFC's own published SHA-1 test vectors: `hotp()`/`totp_code()` generate, and `find_valid_step()` verifies a candidate code within a `±1`-step drift window while enforcing anti-replay via an exclusive `not_before_step` floor — the step index a prior successful verification already consumed. `clock.py` (issue #28) holds a shared injectable `Clock` plus `utc_now()`/`iso()`/`parse_iso()` — moved out of `sudo.py` once a second caller (`authenticator.py`'s coalesced `last_used_at` bookkeeping) needed the exact same millisecond-precision-ISO-8601-sorts-as-text formatting `SudoGrantRepository.find_active`'s `expires_at > ?` comparison already relied on; `sudo.py` and `api/routes/users.py`'s own `_now_iso` copy both import from here now instead of keeping their own. `policy.py`'s `permitted_verbs()` is the *one* place the fixed builtin-role policy is expressed (any `me.*` resource=every verb, every role, checked first — issue #30's self-resource carve-out, not an escalation since the subject of a `me.*` action is always the caller themselves; Read=GET; Write=+POST/PUT/PATCH; Maintain/Admin=all verbs; any `auth.*` resource=Maintain/Admin only); its `BOOTSTRAP_RESOURCES` seed constant is gone as of #25 — `api/route_audit.py`'s real `app.routes` walk is now the `resources` catalog's only source, without changing `reconciler.py`'s `sync_resources()` contract. Issue #38 adds `PolicyClass` (`ordinary`/`auth`/`self`) and `policy_class()`/`is_grantable()` alongside `permitted_verbs`/`is_sensitive_resource`/`is_self_resource` — checked in the same self-then-auth order so the two can never disagree — backing `GET /auth/permissions`'s per-resource policy-class and grantability fields; `ResourceSpec` itself gains a required `verbs: frozenset[Verb]` field (the served-verb union `route_audit` computes), no default. `repositories.py` is the first domain repository in the codebase, built directly on `Database.connection()`/`Database.transaction()` (no ORM) — `UserRepository.create()` structurally guarantees the "every M2 user gets exactly one `provider="local"` `external_identities` row" invariant in the same transaction (skippable via `local_identity=False` for the one caller that provides its own, `auth.bootstrap`); `RoleRepository` refuses to delete or demote a `builtin=1` role. Issue #38: `ResourceRepository.upsert()` takes a required keyword-only `verbs: frozenset[Verb]`, encoded via `auth.models.encode_verbs` into the new `resources.verbs` column; `RoleRepository.list_custom_with_grant_on(resource)` is the `builtin=0` half of the reconciler's retire-warning, one join against `idx_role_permissions_resource_verb`. `CredentialRepository` (issue #28 additions): `find_api_token_credential()` is the constant-time-scan primitive now returning the whole `Credential` row (not just the user), which `find_user_by_api_token()` delegates to so the scan exists in exactly one place; `list_api_tokens()`, `delete_api_token()` (scoped by both id and `user_id` — that scoping is what stops a caller revoking someone else's token), and `touch_last_used()` back the self-service token surface. Issue #39 enforces `credentials.expires_at`: `find_api_token_credential()`/`find_user_by_api_token()` both take a required keyword-only `now` (caller-supplied, never a SQL-side `now`, the same discipline `touch_last_used()`/`SudoGrantRepository.find_active` already follow) and filter their query on `expires_at IS NULL OR expires_at > now` — the identical lexicographic-ISO-8601 string comparison `find_active`'s `expires_at > ?` relies on, no parse; `create_api_token()` gains an optional keyword-only `expires_at`, `None` by default so every existing call path (`api/routes/users.py`, `api/routes/me.py`, both of `auth/bootstrap.py`'s provisioning functions) is unaffected. Issue #37 adds `has_credential(user_id, credential_type)` — a single indexed existence check against `idx_credentials_user_type`, never a hash read — the enrollment primitive `StepUpVerifier.is_enrolled` implementations answer against; deliberately still ignores `credentials.expires_at` even with #39 landed, since nothing sets an expiry on a `password` row and `verify_password` doesn't filter on it either — filtering enrollment alone here would make the two disagree. Issue #41 adds `any_credential_of_type(credential_type)` (an unscoped existence check across every user — `has_credential`'s counterpart when the question is "does anyone hold one of these," backing `auth.encryption.ensure_key_configured_if_needed`'s boot guard), `create_totp_secret()` (inserts a `type='totp'` row, `hash` holding an AES-GCM envelope rather than a one-way hash, `salt` left `NULL` since the nonce already lives inside the envelope), and `get_totp_secret()` (the one-row-per-user read `TotpStepUpVerifier.verify` and `GET /auth/me/totp` both build on). `reconciler.py` seeds the four builtin roles and reconciles their `role_permissions` grants against the catalog at every boot, scoped to `builtin=1` roles only — a custom role's grants are never touched. Issue #47: `reconcile_builtin_roles`'s desired-grant set is `permitted_verbs(slug, resource.name) & resource.verbs` rather than `permitted_verbs` alone — a builtin role never ends up holding a grant on a verb its resource doesn't actually serve (e.g. `system.version:DELETE`, which #38's fixed policy predicted for Maintain/Admin but no route answers), so `GET /auth/roles` and #38's served-verb-aware `GET /auth/permissions` can never disagree about what's grantable for a builtin role. `permitted_verbs`'s own signature and ordinary/`auth.*`/`me.*` semantics are unchanged — only how the reconciler applies the result. The first boot after this ships is a deliberate one-time visible diff: any builtin role holding a pre-#47 over-grant loses it via the existing `current - desired` revoke loop, same as any other stale-grant prune. `sync_resources()` now also persists each `ResourceSpec`'s `verbs` on upsert, and (issue #38) logs a warning naming every custom role holding a grant on a resource before `resources.delete()`'s `ON DELETE CASCADE` strips that grant — builtin-role grants need no warning, since `reconcile_builtin_roles` rebuilds those unconditionally at every boot regardless. `bootstrap.py` holds two independent boot-time provisioning functions (issue #24, redesigned by #28). `ensure_bootstrap_admin()` provisions a single synthetic Admin identity on first boot with zero users (its own `provider="local-bootstrap"` `external_identities` row — the one deliberate exception to the "local" rule) as a permanent break-glass credential: always auto-generates a high-entropy token, prints it to stdout **exactly once** via a plain `print(..., flush=True)` that deliberately bypasses `logging` (never redacted-into-`***`, never captured by log aggregation), and stores only its hash — created once and never touched again by any code path (no override, no rotation, as of #28) except `security.bootstrap_admin_enabled`: `false` revokes the credential while keeping the user/identity for audit attribution, and `true` regenerates one *only* if the identity is currently credential-less (closing a gap #28 found — previously, disabling then re-enabling never restored a credential once the identity row existed), never touching a live one. The generated token is also registered with `logging.redaction` as defense in depth even though nothing is designed to log it. `ensure_configured_admin()` (issue #28, new) provisions a second, ordinary `provider="local"` Admin user, once, from `ANSINA_SECURITY__ADMIN_USERNAME` + `ANSINA_SECURITY__API_TOKEN` (`config.settings.SecuritySettings` guarantees they're set together or neither is) — the "configured admin," which a scripted install or CI uses to get a known, reproducible credential without touching the bootstrap identity or scraping its banner; unlike the bootstrap identity it self-mints/revokes additional tokens the ordinary way via `POST`/`DELETE /auth/me/tokens`. Its "first boot" gate is "no user *other than* the bootstrap identity exists yet," not "`users` is empty" — `ensure_bootstrap_admin()` runs first in `create_app`'s lifespan and, on a genuine first boot, has already inserted the bootstrap identity's own `users` row by the time this runs, so the naive empty-table check would never fire, on every first boot. `is_bootstrap_identity()` (issue #28) is one indexed lookup against `external_identities`, used by `auth.management.assert_not_bootstrap_identity` to keep the bootstrap identity locked to exactly one `api_token` at the route layer — the configured admin is deliberately not subject to it. `principal.py` (issue #25, extended by #26) holds `Principal` (resolved user + role ids/slugs + `auth_method` + `sudo_active`/`sudo_grant_id`) and `AuthMethod`; `with_sudo(grant_id)` returns an elevated copy, the one place `sudo_active` ever becomes `True`. `authenticator.py` (issue #25, extended by #28) formalizes #24's inline DB-backed lookup behind a real `Authenticator` `Protocol` — `ApiTokenAuthenticator` wraps `CredentialRepository.find_api_token_credential` (issue #28: returns the credential row, not just the user, so the authenticator has the id/`last_used_at` it needs), `build_authenticators(db, settings)` returns the chain `api/auth.py`'s middleware walks, and `resolve_principal()` fills a `Principal`'s roles from `RoleAssignmentRepository.roles_for_user()`, rejecting an inactive or (issue #27) tombstoned (`deleted_at is not None`) user. Issue #28's coalesced `last_used_at` bookkeeping lives in `ApiTokenAuthenticator.authenticate()`: touches the credential's `last_used_at` only when the stored value is older than `[security] token_last_used_resolution_seconds` (default 300s, `0` means every request) — a **string** comparison against `clock.iso(now - resolution)`, not a parse, reusing the same lexicographic-sort property `SudoGrantRepository.find_active` already relies on — via an injectable `clock` (`auth.clock`) so the staleness threshold is testable without real sleeping. Issue #39: `authenticate()` reads that injected clock exactly once per call and passes the single resulting instant to both `find_api_token_credential()`'s new expiry filter and this staleness check, so expiry and `last_used_at` bookkeeping can never disagree about "now" — an expired token is simply "no match," indistinguishable from an unknown one by the time it reaches `resolve_principal()`. `authorization.py` (issue #25, made fail-closed by #37) is `authorize(db, principal, resource, verb, *, sensitive=False)`, the pure decision `api/authorization.py`'s `require()` dependency wraps: `ForbiddenError` (no role grants the verb) is checked before `SudoRequiredError` (any role but `admin`, no live sudo grant on a `sensitive=True` resource — issue #37 dropped the `maintain`-role-slug condition so a future custom role granting an `auth.*` permission can't bypass step-up by not being named `maintain`) — the latter is live as of #26. `step_up.py` (issue #26, generalized by #37, a second verifier added by #41) is the pluggable `StepUpVerifier` `Protocol` (`verify(principal, payload) -> bool`, plus `is_enrolled(principal) -> bool` as of #37) behind `POST /auth/sudo` — `PasswordStepUpVerifier` (M2's only implementation) re-checks a `payload["password"]` against `CredentialRepository.verify_password` and answers its own enrollment question via `CredentialRepository.has_credential`; `StepUpRegistry.for_principal()` (issue #37) returns every verifier the principal is currently enrolled in, in registry order, rather than one fixed entry — the foundation `TotpStepUpVerifier` (issue #41) and the TUI's multi-factor `auth sudo` (#44) both build on, without `auth.sudo` ever naming a concrete verifier. `TotpStepUpVerifier` (issue #41) re-checks a `payload["code"]` against `auth.totp.find_valid_step` once the caller's stored envelope is decrypted (`auth.encryption.decrypt`, treating a `DecryptionError` as a plain non-match, same discipline `PasswordStepUpVerifier` applies to a malformed payload) and persists the matched step index onto the credential's own `last_used_at` (`CredentialRepository.touch_last_used`) as the anti-replay floor for next time; answers its own enrollment question via `CredentialRepository.has_credential(..., CredentialType.TOTP)`. `build_step_up_verifiers()` now always returns both verifiers regardless of whether `[security.encryption] key` is configured — a caller only ever resolves to `TotpStepUpVerifier` via the registry's own enrollment filter, and nobody can be enrolled without a key having existed at enrollment time, so no conditional wiring is needed. `sudo.py` (issue #26, extended by #37) is `SudoService` — issuance (`step_up()`, minting a `secrets.token_urlsafe` grant via `SudoGrantRepository`), the read side `BearerAuthMiddleware` calls (`resolve()`), revocation (`revoke_for_user()`/`revoke_all()`), and the failed-attempt lockout (`SudoLockoutRepository`-backed, `[security.sudo] max_failed_attempts` consecutive failures within `attempt_window_seconds` locks out for `lockout_seconds`, raising `SudoLockedOutError` mapped to 429 with a real `Retry-After` header) — driven by an injectable clock throughout (`auth.clock`, issue #28 — moved out of this module once `authenticator.py` needed the identical `Clock`/`iso`/`parse_iso` shape), so TTL/lockout expiry is tested without real sleeping. Issue #37 adds `_resolve_factor()` (picks among `StepUpRegistry.for_principal()`'s result via an optional `payload["factor"]`, defaulting to the sole entry when exactly one is enrolled) and `enrolled_factors()` (backs `GET /auth/me`'s `step_up_factors`); a caller with no usable factor gets the new `StepUpUnavailableError` (403 `ansina.auth.step_up_unavailable`) raised *before* `_record_failure()` ever runs, so it never consumes a lockout attempt — fixing what was previously indistinguishable from a wrong-password 401 for any password-less user (the default shape of a user created without `CreateUserRequest.password`). `management.py` (issue #27, extended by #28, #40) holds the server-side guards the management routes need beyond `authorize()` itself, pure domain logic mirroring how `authorization.py` sits under `api/authorization.py`: `assert_may_assign_role()` (a caller can never grant a `role_permissions` row it does not itself effectively hold — the `admin` role and any `auth.*`-granting role are checked directly first, since `Maintain`/`Admin` hold identical grants under M2's fixed policy and a bare subset check alone wouldn't catch a sudo'd `Maintain` minting a fresh `Admin`; the general case is a subset-of-grants check, so it keeps working unchanged once non-builtin roles exist) and `assert_admin_remains()` (refuses — `LastAdminError`, 409 — to leave zero active, non-deleted holders of the `admin` role; called from every route that deletes, deactivates, or demotes a user, directly or via a group). Issue #40 lifts `assert_may_assign_role()`'s own `auth.*`/subset logic (its steps 2 and 3) into a shared `_assert_no_excess_grants()` helper and exposes it as `assert_may_grant_permissions()` — the identical check over a raw grant set rather than an existing role's, so `POST`/`PATCH /auth/roles` can run it at grant-*edit* time, not only at role-*assignment* time (M3's open consideration #8) — plus `assert_grants_grantable()` (`InvalidGrantError` unless every submitted grant is catalogued, `grantable` per `auth.policy.is_grantable`, and a verb that resource's routes actually serve per #38's `Resource.verbs`), checked first since an uncatalogued resource can never be an escalation. M3's issue #43 (done) is the milestone's last piece — federated login via OAuth 2.0/OIDC, shaped as a **login exchange** rather than a per-request authenticator (M3's open consideration #5, resolved by not using `Authenticator` at all): `auth/oidc.py` is the pure protocol layer — an `OidcHttpClient` structural `Protocol` (`get_json`/`post_form`, same shape discipline as `HeartRuntime`/`BrainProvider`/`StepUpVerifier`) behind `discover()` (OIDC discovery, issuer-mismatch and missing-endpoint fail-closed, fetched fresh every login — no caching layer, so an IdP's key rotation takes effect on the very next login), `fetch_jwks()`, `exchange_code()` (the authorization-code + PKCE `code_verifier` redemption), and `validate_id_token()` — one `jwt.decode()` call with `algorithms` pinned to an asymmetric-only tuple (RS/PS/ES, never `none`, never `HS*` — closes the classic "algorithm confusion" forgery where a JWKS public key gets replayed back as an HMAC secret), `audience`/`issuer` checked, `options={"require": [...]}` making every claim's *presence* mandatory not just its value, and a separate `hmac.compare_digest` nonce check (no concept in `jwt.decode` itself). `HttpxOidcClient` is the one real `OidcHttpClient` — a fresh, short-lived `httpx.Client` per call (login is human-paced, not a hot path, so no persistent connection or `aclose()` lifecycle is worth keeping), with an injectable `transport` (`httpx.MockTransport`, part of `httpx` itself) letting its own unit tests exercise real success/non-2xx paths with no socket. `auth/oidc_login.py`'s `OidcLoginService` is the orchestration layer: `start_login()` discovers the authorization endpoint, mints `state`/`nonce`/PKCE `code_verifier`, persists them (sweeping previously-expired rows as a side effect), and returns the authorization URL; `complete_login(code, state)` runs, in strict order, single-use state lookup → code exchange → ID-token validation → user provisioning/linking → `sync_mapped_roles` (issue #42's first caller, run on *every* login, not only the first) — every rejection before provisioning, so a forged or malformed callback can never touch `users`/`external_identities`/`role_assignments`. It returns the provisioned `User`, not a minted token — minting one (`api/tokens.py`'s `issue_token`, issue #39's first HTTP-reachable caller) is deliberately left to `api/routes/oidc.py`, since `ansina.auth` never imports from `ansina.api` anywhere else in this codebase and doing so here would be a circular import (`ansina.api`'s own package `__init__` imports `create_app`, which imports back from `ansina.auth`); `clock`/`token_ttl_seconds` are exposed as read-only properties so the route mints with the exact clock the service validated against. Provisioning (`_provision_user`) matches on `(provider, subject)` first (reuse), refusing a tombstoned or deactivated linked user; on a miss, it derives a username (`preferred_username` → `email` → `sub`) and, on a *username* match against an existing local user, **links** the IdP subject onto that account rather than refusing or auto-disambiguating — a deliberate choice (an operator can migrate an existing local user onto the IdP with no separate step) logged as a `logger.warning` naming both identities, since it confers that account's roles on the IdP subject; refused outright for a tombstoned/deactivated/bootstrap-identity target. `build_oidc_login_service(db, settings, *, client=None, clock=utc_now)` returns `None` when `[security.oidc] enabled = false` — the same shape `heart`/`brain` factories use — and performs no network call at assembly time, unlike Heart/Brain: an unreachable or misconfigured IdP only ever fails an individual login, never boot. New base dependencies: `pyjwt[crypto]` (ID-token signature validation, pulling `cryptography` — already a base dep since #41) and `httpx` (the login exchange's transport — previously only a transitive/dev dependency, now declared directly since it's used for real).
- `src/ansina/logging/`: JSON structured logging via `logging.config.dictConfig`. Redaction runs inside `JsonFormatter`, not at call sites — never bypass it by formatting log strings yourself. Request/correlation ids via `contextvars` (`request_id_scope()`). Boot with `configure_logging(load_settings())`, then use `get_logger(__name__)` everywhere else, never bare `logging.getLogger()`.
- `src/ansina/heart/` (issue #10): the in-process Heart runtime. `runtime.py`'s `HeartRuntime` is a structural `Protocol` (`load`/`generate`/`token_count`/`unload`/`is_healthy`) plus `BaseHeartRuntime`, an ABC owning the loaded-state guard and the 8k context-budget refusal shared by every adapter — subclasses only implement four `_*` backend hooks. `models.py`'s `resolve_model()` resolves an explicit `[heart] model_path` (wins, no network) or downloads `model_repo` from Hugging Face into `cache_dir` (download-once cache); `selection.py`'s `build_heart_runtime()` is the capability probe — MLX is viable only on `darwin`/`arm64` with `mlx_lm` importable (import success alone isn't enough: `mlx` also ships manylinux wheels), and any other host gets a loud `HeartUnavailableError`, never a silent fallback. `adapters/mlx.py` is the only adapter shipped — a second, non-Apple-Silicon adapter is deferred to a follow-up issue (no llama-cpp-python-compatible GPU was available to prove it against). Every backend import (`mlx_lm`, `huggingface_hub`) happens inside function bodies, never at module scope, so `ansina.heart` stays importable without the optional `ansina[mlx]` extra installed. `[heart] enabled` defaults to `false` — off, none of this runs.
- `src/ansina/heart/tick/` (issue #11): the autonomic tick loop, the Heart's one day-one duty and the first caller of `HeartRuntime.generate()`. `loop.py`'s `TickLoop` schedules `tick_once()` on a fixed cadence (`start + n*interval`, recomputed each cycle so a slow tick can't drift future ticks or burst-fire missed slots — see `_next_tick_number`), guarded against overlap by an in-flight flag, with `pause()`/`resume()` as the kill switch and any tick exception logged and swallowed so one failure can't end the loop. `snapshot.py` builds the bounded prompt: a `StateSnapshotSource` `Protocol` (structural, like `HeartRuntime`) contributes `SnapshotItem`s, and `build_prompt()` measures with the runtime's own `token_count` and drops lowest-priority items until the prompt fits `context_tokens - max_output_tokens` — enforced before `generate()` is ever called, not left to `HeartContextOverflowError` as the mechanism. No source is registered yet (no pending-work/schedule/event domain exists — `storage/` ships only `schema_version`); a later issue registers one the same way milestones register a `Readiness` check. `decision.py`'s `parse_decision()` turns the Heart's raw reply into `TickDecision.IDLE/ACT/ESCALATE`, defaulting to `IDLE` on anything unparseable. `act` and `escalate` both dispatch through a `DecisionHandler` `Protocol`; the shipped `LoggingDecisionHandler` only logs — there is nothing to act on yet, and although `BrainProvider` now exists (issue #12, `src/ansina/brain/`), nothing wires `escalate` to it yet — that hand-off is a follow-up issue, not part of #12's scope. `[heart.tick] enabled` defaults to `true` but is inert unless `[heart] enabled` is also `true`.
- `src/ansina/brain/` (issue #12): the remote Brain provider port — no in-process backend to guard, unlike `heart/`, but the same shape: a structural `Protocol` (`provider.py`'s `BrainProvider`, `stream`/`aclose`) plus a `BaseBrainProvider` ABC owning invariants every adapter shares. The load-bearing one, taken from OpenClaw (`docs/architecture/blueprint.md` §1): `stream()` returns synchronously (a plain method, not `async def`) and **never throws after invocation** — every failure arrives as a terminal `BrainErrorEvent` (`events.py`), never a raised exception into the caller's `async for`; only construction/selection-time failures raise (`BrainUnavailableError`). `BaseBrainProvider` also owns bounded retry (`retry.py`'s `backoff_seconds`, capped exponential backoff) — retried only while no `BrainTextDelta` has reached the caller yet, and only for a `RETRYABLE_ERROR_CLASSES`-classified failure — and explicit generator cleanup (`gen.aclose()` in a `finally`) so a caller cancelling mid-stream closes the adapter's in-flight HTTP request promptly rather than waiting on GC. `adapters/openai_compat.py`'s `OpenAICompatibleBrainProvider` is the only adapter shipped, working against any OpenAI-compatible chat-completions endpoint; `classify_openai_error()` maps the SDK's exception hierarchy to `BrainErrorClass`, and token/cost accounting (`BrainUsage`) is authoritative when the provider's own usage totals arrive, else an estimated (non-authoritative) char-based fallback. `selection.py`'s `build_brain_provider()` refuses to build (`BrainUnavailableError`) a keyless request against the *default* OpenAI host — a keyless custom `base_url` (a local OpenAI-compatible server) is left alone. Nothing calls `stream()` yet: wiring the tick loop's `escalate` branch to this port is a follow-up issue, not part of #12.

Ships `ansina-tui` (`[project.scripts]`) and `python -m ansina_tui`, both resolving to `ansina_tui.main:app`. `main.py`'s root `@app.callback(invoke_without_command=True)` is the no-args rule, the milestone's defining behavior: bare invocation on a TTY calls `launch_tui()`; any argument at all (a subcommand, `--help`, `--version`) is the CLI and never reaches it; bare invocation on a non-TTY prints help to **stderr** and exits `USAGE` (2) — Typer's rich-formatted `ctx.get_help()` prints to stdout as a side effect of formatting rather than just returning a string, so `clihelp.py`'s `print_help_to_stderr()` swaps `sys.stdout` for the call's duration instead of trusting `echo(..., err=True)` alone; issue #32's `commands/auth/__init__.py` reuses the same helper for its own two bare-invocation usage errors (`auth`, `auth token`) below. Global options (`--host`/`-H`, `--json`, `--verbose`, `--version`) are root-level like `git`'s or `docker`'s — they precede the subcommand, not follow it — resolved once into a frozen `context.AppContext` on `ctx.obj`. `exits.py`'s `ExitCode` is the sole source of the exit-code table: `0` ok, `1` request failed, `2` usage/local-config error, `3` not authenticated, `4` forbidden/sudo required, `5` host unreachable, `6` daemon not ready, `7` daemon not healthy — the last two extend issue #31's own 0–5 table (a reachable-but-unhealthy/not-ready daemon is neither "ok" nor "request failed"); `/healthz` is always checked before `/readyz`, so an unhealthy daemon exits `7`, never `6`. `config.py` is the XDG credential store (`$XDG_CONFIG_HOME/ansina`, else `~/.config/ansina`): `config.toml` (non-secret `default_host`, written by `save_config()`, issue #32) and `hosts.toml` (per-host `token`/`token_id`/`username`/`roles`/`sudo_token`/`sudo_expires_at` — `token_id`, issue #32, is set only when `auth token mint` stores the token it just minted, letting `auth token revoke` detect and warn on self-revocation), written via `os.open(..., 0o600)` and refused on read if group/other-readable (`InsecureCredentialsFileError`, naming the `chmod 600` fix) — serialized by a hand-rolled `_dump_toml` since 3.14's stdlib `tomllib` is read-only and no TOML-writer dependency was added for this one narrow schema. `ANSINA_TOKEN`/`ANSINA_HOST` (`resolve_token`/`resolve_host`) are resolved separately from `HostEntry`, so they can never be written back to disk. `client.py`'s `ApiClient` wraps `httpx.Client`: bearer auth, `X-Sudo-Token` attached only while an injectable-clock-checked grant is unexpired (`parse_expiry`, exported — issue #32's `session.py` reuses the exact same parse rather than duplicating it), and the daemon's echoed `X-Request-Id` (`ansina.api.middleware`) captured onto every `ApiResponse` for log correlation; `httpx.TransportError` becomes `HostUnreachableError` (exit 5). `problems.py` parses `application/problem+json` into `ApiProblem`, with a hand-copied (not imported — `tui/` can't import `ansina`) table of recognized `ansina.*` codes to human messages — issue #32 adds `ansina.auth.bootstrap_identity` (names the real fix: log in as the configured admin or an ordinary Admin), `ansina.auth.token_already_issued`, and `ansina.auth.not_found`. `output.py`'s `Emitter` is the output-discipline seam: with `--json`, stdout carries JSON and **nothing else** (a plain `sys.stdout.write`, never through `rich`) — every diagnostic goes to stderr; issue #32 adds `verbose`-gated `debug()` (so a request id can be shown without ever risking a secret), `warn()`, and a headered multi-column `table()` (`auth token list`). Issue #32 also adds the credential/session layer above `config.py` and the `auth` command surface built on it. `session.py`'s `Session` is the resolved host/config/credential state for one invocation; `resolve_session()` loads `config.toml`+`hosts.toml` and resolves `--host`/`ANSINA_HOST`/`ANSINA_TOKEN` precedence, scrubbing an *expired* sudo grant onto `Session.entry` in memory (never sent, never re-persisted) while `Session.hosts` keeps the raw, unscrubbed table so `auth sudo --status` can still tell "expired" apart from "never stored". `build_client()` is the single `ApiClient` construction point (and the one seam `tests/conftest.py`'s `patch_transport` fixture patches, replacing #31's `patch_status_transport` now that `commands/status.py` is built on this module too) — its `token=` override lets `auth login` authenticate with a just-supplied token before anything is stored. `save_entry()`/`remove_entry()` write `hosts.toml` back (the former also sets `default_host` on first login); `sudo_state()` classifies a `HostEntry`'s grant as `none`/`expired`/`active`. `secret_input.py`'s `read_token()`/`read_password()` are the "never argv" seam pinned by `tests/unit/test_argv_safety.py`'s walk of the whole Click command tree (vendored inside Typer, `typer._click` — no separate `click` import): `--with-token`/a piped non-TTY stdin is read directly, otherwise a `typer.prompt(hide_input=True)`; both resolve `sys.stdin` inside the function body, never as a `= sys.stdin` default-argument value, which would bind once at import time and miss `CliRunner`'s per-invocation stdin swap (the same trap `main.py`'s `_is_interactive` already documents). `failures.py`'s `report()` is the shared non-2xx renderer every command calls: the recognized message from `problems.py` (or a per-call override — `auth sudo` overrides `ansina.unauthorized`'s generic "run `auth login`" text, since that code means "wrong step-up password" at `POST /auth/sudo`), the request id under `--verbose`, and a rendered `Retry-After` figure from the problem body's own `retry_after_seconds` extension member (issue #26's sudo lockout, 429). `commands/auth/` (package) holds `login.py` (`login`/`logout`), `status.py` (`auth_status_command` — always a live `GET /auth/me`, no cache fallback), `sudo.py` (`sudo_command`: `--revoke`/`--status`, the latter local-only and self-healing an expired grant it finds), and `tokens.py` (`mint`/`list`/`revoke` over `/auth/me/tokens`, #28 — `mint` shows the raw token once, reusing #24's bootstrap-banner framing, and offers to store it; `revoke` warns and confirms before revoking the id currently in use). `commands/auth/__init__.py` wires `auth_app` (+ nested `token_app`) into `main.py`'s root app via `add_typer`; bare `auth`/`auth token` is a usage error (exit 2), not silent success. `commands/status.py` (day-0, issue #31) is now built on `session.py` the same way: `GET /healthz` → `/readyz` → `/version`, works with **no token at all** (both health routes are public), `/version` 401 degrades to `"unknown"` rather than an error. `commands/api.py` (issue #33) is `ansina-tui api [-X METHOD] <path>` — the raw REST wrapper reaching any daemon route with no per-route special-casing and no allow-list to keep in sync, and the milestone's CI/CD surface (so it never blocks for input). It required two small, additive extensions rather than a new foundation: `client.py`'s `ApiResponse` gained `text` (the body verbatim) and `headers` (the response headers, for `-i`), and `ApiClient.request()` gained `content=` (a raw body, alongside the existing `json_body=`; httpx's own `encode_request` checks `content` before `json`, so the two never conflict) and `headers=` (a caller's own headers merged in) — critically, `Authorization`/`X-Sudo-Token` are now set by plain assignment *after* merging a caller's headers, never `setdefault`, so a `-H` can never silently replace either (when no token is configured at all, a caller-supplied `Authorization` still passes through unharmed). `RESERVED_HEADERS` (`authorization`, `x-sudo-token`) is exported so `commands/api.py` can warn, not just silently override. `output.py` gained `Emitter.body()`, a plain `sys.stdout.write` (never through `rich`, same discipline as `Emitter.json`) for the response body verbatim — deliberately not `Emitter.json`, which re-serializes a `Mapping` with `sort_keys=True` and would reorder the daemon's fields or reject a non-object body. `api_command` itself: `-f/--field key=value` (repeatable) assembles a JSON object body whose values are always JSON strings — a typed field goes through `--input <file|->` instead, mutually exclusive with `-f`; method defaults to `GET`, or `POST` when either supplies a body (the `gh api` convention). Output follows `_stdout_is_tty()` (its own function, patched in tests, for the same `CliRunner`-swaps-`sys.stdout` reason `main._is_interactive` is): pretty-printed JSON on a TTY with no `--json`, raw under `--json` or a piped stdout — and the body is written whether or not the response was 2xx, so `--json | jq` works on a problem document too. `-i/--include` (status line + response headers) is rendered via `emitter.line()`, so it is itself suppressed under the same `--json`/piped-stdout condition, keeping the two rules from conflicting. `pyproject.toml` gained `[tool.ruff.lint.flake8-bugbear] extend-immutable-calls = ["typer.Option", "typer.Argument"]` — without it, ruff's B008 misfires on the standard Typer idiom for a repeatable option (`fields`/`raw_headers` here) as if it were a mutable default. `fetcher` is constructor-injectable so widget tests drive every designed state without a transport. A panel with rows renders as a borderless `rich.table.Table`; a message-only panel as plain text; a fully empty panel (a whole-tab failure) as a `"—"` placeholder — never blank. ## Layer 3: Data Flow & Entry Points
- Entry points: `python -m ansina` and the `ansina` console script (`[project.scripts]`), both resolving to `src/ansina/__main__.py:main` — the daemon, unchanged by M4. A second, independent entry point (M4, `tui/`): `python -m ansina_tui` and the `ansina-tui` console script, both resolving to `tui/src/ansina_tui/main.py:app`, from a separate distribution (`ansina-tui`, package `ansina_tui`) that never shadows or imports `ansina` — it reaches the daemon over HTTP only (pinned by `tui/tests/unit/test_isolation.py`: no `ansina`/`ansina.*` module in `sys.modules` after a full CLI run). Its dispatch rule inverts the usual CLI default: bare invocation on a TTY launches the Textual TUI; any argument at all (a subcommand, `--help`, `--version`) is the CLI instead, writing to stdout/stderr; bare invocation on a non-TTY prints help to stderr and exits `2` (Textual can't render into a pipe).
- Boot sequence: `load_settings()` → `configure_logging(settings)` → `create_app(settings)` (`src/ansina/api/app.py`) → `uvicorn.run(...)`. A `ConfigError` during boot prints the aggregated report to stderr and exits non-zero, never a traceback. `create_app` also builds `oidc = oidc_factory(db, resolved_settings)` (default `auth.build_oidc_login_service`, issue #43) alongside `sudo`/`authenticators` — `app.state.oidc` is `None` when `[security.oidc] enabled = false` (the default), the same shape `heart`/`brain` use, but unlike either, building it performs no network call and has no boot-time failure mode: an unreachable or misconfigured IdP only ever fails an individual login attempt. `load_settings()` itself refuses to construct `Settings` (issue #5, updated by #24) when `server.host` isn't loopback and `security.enabled` is `False` — that invariant is unbypassable since it lives on `Settings`, not in `create_app`; `api_token` being unset no longer factors in (issue #24 makes it optional even with auth enabled — Ansina generates its own bootstrap token instead). `api_token`, when set, must itself look securely generated: `_TOKEN_MIN_LENGTH` (32), `_TOKEN_CHARSET` (base64url only, so a human-typed phrase is rejected outright), `_TOKEN_MIN_ENTROPY_BITS_PER_CHAR` (2.5, a best-effort predictability deterrent, not a cryptographic guarantee) all in `config/settings.py`. After every router is included, `create_app` calls `api/route_audit.py`'s `audit_route_coverage(app)` (issue #25) — a `RouteCoverageError` there aborts boot the same "fail loudly before uvicorn binds a port" way a `ConfigError` does — and stashes its returned `ResourceSpec`s on `app.state.resource_specs`. `create_app`'s FastAPI `lifespan` opens the `Database` and runs `run_migrations()` on startup (a `MigrationError` there aborts boot the same way), then — issue #24, in this fixed order because each step depends on the last — `sync_resources()` catalogs `app.state.resource_specs` (issue #24 seeded this from a hand-written constant; #25 replaced that argument with the route audit's real walk, `sync_resources()`'s own contract unchanged), `reconcile_builtin_roles()` grants the four builtin roles against that catalog, `ensure_bootstrap_admin()` provisions the synthetic Admin identity, and (issue #28) `ensure_configured_admin()` provisions the second, ordinary Admin from `ANSINA_SECURITY__ADMIN_USERNAME`/`API_TOKEN` if set (see `src/ansina/auth/` below for both functions' full shape — order between the last two no longer matters functionally, since #28's "first boot" check for the second is independent of it, but it runs second to keep the narrative order); an `AuthError` from any of the four aborts boot the same way. `Database` is closed on shutdown; `Readiness` gets a `"database"` check backed by `Database.is_healthy()` (no dedicated `/readyz` check for the RBAC seeding — `database` already covers its only failure mode). When `[heart] enabled` is true, `create_app` calls `build_heart_runtime()` *before* the lifespan even starts — a `HeartUnavailableError` (issue #10) surfaces the same way a `ConfigError` does, before uvicorn ever binds a port; the lifespan then loads the model and registers a `"heart"` readiness check, unloading it on shutdown alongside the database close. When disabled (the default), `app.state.heart` is `None` and `/readyz` carries no `heart` key at all. When the Heart is also enabled and `[heart.tick] enabled` is true (issue #11, its own default), `create_app` builds a `TickLoop` (`build_tick_loop`) the same way, and the lifespan `start()`s it after `heart.load()` and registers a `"heart_tick"` readiness check, `stop()`ing it on shutdown before `heart.unload()`. `app.state.tick_loop` is `None` unless both flags are true. When `[brain] enabled` is true (issue #12, independent of `[heart] enabled`), `create_app` calls `build_brain_provider()` the same "fail loudly before uvicorn binds a port" way (`BrainUnavailableError`); the lifespan `await`s `brain.aclose()` on shutdown alongside `heart.unload()`/`db.close()`. `app.state.brain` is `None` when disabled. No `/readyz` check is registered for it — the only meaningful liveness signal for a remote provider is a real network round-trip, and paying for one on every `/readyz` poll is the wrong trade.
- Request flow: `RequestIdMiddleware` (outermost) binds/echoes a request id (feeding `logging`'s correlation-id contextvar) → `BearerAuthMiddleware` (401 `problem+json` if the route isn't in `PUBLIC_PATHS` — issue #43 widens this to `/auth/oidc/login`/`/auth/oidc/callback`, the first non-health-probe entries, since a caller cannot hold a bearer token before it has logged in — and the bearer token doesn't resolve a `Principal` through the `Authenticator` chain; issue #26: a resolved `Principal` carrying a live `X-Sudo-Token` is additionally elevated here) → the route's `require(resource)` dependency (403 `problem+json` if the resolved `Principal` holds no role granting `request.method` on that resource — issue #25, dev mode/`security.enabled=False` skips this too; 403 `CODE_SUDO_REQUIRED` if the resource is `sensitive=True`, the role is anything but `admin` (issue #37 — previously only `maintain`), and no elevation happened above) → route → response, or an exception mapped to `application/problem+json` by the handlers in `api/exception_handlers.py`. The `auth.*` management routes (issue #27) split `sensitive` by verb on the same resource rather than per-route: `GET /auth/users`/`/auth/groups`/`/auth/roles`/`/auth/permissions` are `sensitive=False` (Maintain reaches them with no grant), every mutating verb on `auth.users`/`auth.groups`/`auth.role_assignments` is `sensitive=True`. `me.tokens` (issue #28) is never `sensitive=True` at all, matching `me.profile`'s carve-out. A successful match against the `Authenticator` chain (issue #28) also coalesces a `last_used_at` write onto the matched credential — at most once per `[security] token_last_used_resolution_seconds`, not per request, since the lookup already full-scans `credentials` on every request.

## Layer 4: External Integrations
- **SQLite** (`src/ansina/storage/`, issue #6): the only runtime dependency in M0. One file on disk, WAL journal mode, path set via `[database] path` / `ANSINA_DATABASE__PATH` (defaults to `./ansina.db`; WAL adds `-wal`/`-shm` sidecars next to it). No network service, no separate process.
- **argon2-cffi** (`src/ansina/auth/hashing.py`, issue #24): a *base* dependency, not an optional extra — same reasoning as `openai` above: auth is not optional, and both CI legs must exercise password hashing. Ships prebuilt wheels for macos-arm64 and linux-x86_64, so neither CI leg compiles from source.
- **cryptography** (`src/ansina/auth/encryption.py`, issue #41): a *base* dependency, same reasoning as `argon2-cffi` above — AES-GCM-encrypting a TOTP secret at rest is not optional once the credential type exists, and both CI legs must exercise it. Approved during M3 planning alongside `pyjwt[crypto]` (issue #43's OIDC signature validation, which pulls the same package) — landed here first since #41 shipped ahead of #43 on this branch, so #43 added no new wheel-compilation cost. Ships prebuilt wheels for macos-arm64 and linux-x86_64, so neither CI leg compiles from source.
- **PyJWT** (`src/ansina/auth/oidc.py`, issue #43): a *base* dependency — ID-token signature/claim validation for the OIDC login exchange is not optional once `[security.oidc]` exists, and both CI legs must exercise it. `algorithms` is pinned to an asymmetric-only tuple (never trusts the token's own `alg` header) — see Layer 2's `auth/oidc.py` entry.
- **httpx** (`src/ansina/auth/oidc.py`, issue #43): a *base* dependency — the OIDC login exchange's transport for discovery/JWKS/token-endpoint calls. Until this issue it was only a transitive dependency (via `openai`/`huggingface-hub`) and a `[dependency-groups] dev` pin for `tests/e2e`; declaring it directly makes that already-resolved dependency honest rather than adding real new surface — the duplicate dev-group floor was removed so the two can't drift.
- **MLX / Hugging Face** (`src/ansina/heart/`, issue #10): optional — the `ansina[mlx]` extra (`mlx-lm`, `huggingface-hub`), not a base dependency, and never installed in CI (both legs run with the Heart disabled). - **OpenAI-compatible endpoint** (`src/ansina/brain/`, issue #12): the `openai` SDK is a *base* dependency (unlike `ansina[mlx]` above) — pure Python, installs and is exercised on every CI leg, since the Brain being off by default (`[brain] enabled = false`) is a config default, not a platform constraint. Calls a reusable workflow in `giacchetta/giacchetta.github.io` on every merged PR to generate a blog post; this repo passes PR/issue read access plus two secrets and owns no generation logic itself.

## Layer 5: Domain Blueprint
- **Heart** (≤4B, 8k ctx, in-process): owns the autonomic tick loop only — decide idle / act / escalate. Never answers user requests directly. Every prompt built for it must fit its 8k window; treat that as a hard constraint, not a target. The runtime port + MLX adapter (issue #10, `src/ansina/heart/`) and the tick loop (issue #11, `src/ansina/heart/tick/`) are wired into `create_app`'s lifespan; `TickLoop` is the first and only caller of `generate()`. Its snapshot has no real content yet (no pending-work/schedule/event domain exists), `act` has nothing to act on, and `escalate` — although `BrainProvider` now exists (issue #12) and is wired into `create_app` alongside it — still has no hand-off wired to it; all three remain injected seams with log-only defaults, not implemented behavior, until a follow-up issue connects `escalate` to `BrainProvider.stream()`.
- A portable, non-Apple-Silicon `HeartRuntime` adapter (originally scoped as llama-cpp-python in issue #10) is **deferred to a follow-up issue**: the only non-Apple hardware available at the time had no llama-cpp-python-compatible GPU, so an adapter there was unprovable and was cut rather than shipped untested. Until that lands, a non-Apple-Silicon host with `[heart] enabled = true` fails loudly at boot (`HeartUnavailableError`) rather than silently degrading.
- **Brain** (35B+, remote via `BrainProvider` port): owns all real reasoning. The Heart never replaces it or bypasses it for substantive answers. The port + its OpenAI-compatible adapter (issue #12, `src/ansina/brain/`) are implemented and wired into `create_app`'s lifespan the same way the Heart is, gated by `[brain] enabled` independently of `[heart] enabled` — but nothing calls `BrainProvider.stream()` yet; a local 35B adapter and multi-provider routing/fallback chains are explicitly out of scope, deferred the same "unprovable on hardware at hand" way the llama-cpp-python fallback above was.
- Three additional Heart duties (request triage, context curation, structured extraction) are **deliberately not implemented**. Prior embedded-model attempts produced low-quality output — each duty is a gated experiment (`Backlog — Experiments` milestone) requiring a benchmark win over a stated baseline before adoption. Do not fold this logic into the tick loop without that gate passing.
- **Control surface** (M4, `tui/`): `ansina-tui` is the only operator UI Ansina will ever have — no internal WebUI, permanently, per §2's channel refusal in `docs/architecture/blueprint.md`. It is a dependency-isolated client over the REST API only (never imports `ansina`), read-only in M4 (no pause/resume, no user/role management — mutations stay CLI-side, where confirmation and sudo prompting are unambiguous), with `ansina-tui api` as the universal wrapper reaching every route with no allow-list to drift. The authorization model now has three resource policy classes, named together here since no other single place does: ordinary resources (Read=GET, Write=+POST/PUT/PATCH, Maintain/Admin=+DELETE), `auth.*` (Maintain/Admin only, every mutation additionally sudo-gated for `Maintain`), and `me.*` (every verb, every role — the subject of a `me.*` action is always the caller, so it is never an escalation).
- **Issue #35 (done)** is M4's last issue and is documentation-only (no code change): it brought `README.md` (a new control-surface section plus the `me.*` cross-reference), `docs/architecture/blueprint.md` (a control-surface rationale in §3, M3+M4 added to the §4 roadmap with M4 explicitly ordered before M3, and a third testing-strategy layer in §5 for `tui/tests/unit/`), this file's Layers 3–5, and the M3 milestone body's open-considerations section into alignment with what #30/#28/#31–#34 actually shipped. Two things #35 scoped as work turned out to already be in place by the time it was picked up: `README.md`'s API table already listed `GET /auth/me` and the three `/auth/me/tokens` routes (landed with #30/#28), and the M3 milestone body already carried a `🔄 M4 alignment` block covering the `me.*`-as-third-class and fail-closed-sudo cross-check inputs this issue was meant to hand it — only item #11's own strike-through and a "shipped" addendum were still needed there.
- No channel concept anywhere (no Discord/WhatsApp/etc., and no `ChannelId`-shaped abstraction either) — see `docs/architecture/blueprint.md` §2 for why this is refused deliberately, not an oversight.
- Primary deployment target is a Mac Mini (Apple M4, 16 GB unified memory) — adapter and performance decisions prioritize that hardware, not the local dev machine.
- **RBAC identity & access control** (M2 milestone, complete — `src/ansina/auth/` + `api/authorization.py`/`api/route_audit.py`/`api/routes/{sudo,users,groups,role_assignments,roles,permissions,me}.py`): replaces #5's one-shared-secret model with real `User`/`Group` identity and a permission model keyed on data, not code — "is there a `role_permissions` row granting (a role, a resource, a verb)?" is the entire authorization question, for both builtin and (future) admin-defined roles. M3's issue #43 (done) is the milestone's last originally-scoped piece: federated login via OAuth 2.0/OIDC, shaped as a **login exchange** (`POST /auth/oidc/login` + `GET /auth/oidc/callback`) rather than a per-request authenticator — M3's open consideration #5's resolution. The authorization-code + PKCE flow runs once per login: discover the IdP, mint/persist `state`/`nonce`/`code_verifier`, redeem the code, validate the ID token (signature pinned to asymmetric algorithms only, issuer, audience, expiry, and nonce — each an independent rejection, all checked before anything else runs), JIT-provision or link the Ansina user, refresh its `role_mappings`-derived roles via #42's `sync_mapped_roles` on *every* login (not only the first), and mint a short-lived `api_token` via #39's `ttl_seconds` seam — the first HTTP-reachable caller of it. Username-collision handling on JIT provisioning was a real design decision, not an oversight: a claims-derived username matching an existing *local* user **links** the IdP subject onto that account (letting an operator migrate a local user onto the IdP with no separate step) rather than refusing or auto-disambiguating, logged as a `logger.warning` naming both identities since it confers that account's roles on the IdP subject — narrowed by three refusals (tombstoned, deactivated, or the bootstrap identity). See Layer 2's `auth/oidc.py`/`auth/oidc_login.py`/`api/routes/oidc.py` entries for the full mechanics. PKCE (RFC 7636, S256) is included though not named in the issue's own written scope — a deliberate widening, not scope creep by omission. Out of scope, as originally planned: any identity provider beyond OIDC-compliant ones, and an OIDC re-auth `StepUpVerifier` (dropped during M3 planning — #41's TOTP covers the same "no local password forced on a federated user" intent without a second code flow).

M3's issue #47 (done) is a narrow follow-up filed out of #38's own review, closing the one gap #38 deliberately left open: #38 made `GET /auth/permissions` report only each resource's actually-served verbs (`resources.verbs`), but left `reconcile_builtin_roles` (`auth/reconciler.py`) still materializing every `permitted_verbs()`-predicted grant regardless of what a route serves — so a builtin role could hold e.g. `system.version:DELETE` in `role_permissions` even though no route answers `DELETE /version`, a discoverability inconsistency `GET /auth/roles` would otherwise surface. The fix is a one-line change in scope: the reconciler's desired-grant set is now `permitted_verbs(slug, resource.name) & resource.verbs`, so a builtin role's materialized grants can never exceed what the served-verb catalog admits — see Layer 2's `auth/reconciler.py` entry above for the mechanics. `auth.policy.permitted_verbs`'s own signature and policy semantics are untouched (out of scope by design), and custom-role grant validation at request time remains #40's own `assert_grants_grantable`, unaffected by this issue. The first boot after this ships is a deliberate one-time visible diff, called out here as the issue itself required: any builtin role holding a pre-#47 over-grant loses it via the reconciler's existing prune loop.

Out of scope, called out so the absence reads as a decision: any login route (#50 — this issue only changes how a password is *set*, never how it's spent), revoking existing API tokens on a password change (an `api_token` is an independent `credentials` row, not a session derived from the password — `DELETE /auth/me/tokens/{id}` from #28 is the existing revocation path), and re-validating already-stored password hashes (policy applies at set time only; an existing weak password keeps working until it's next changed).
