# 🏛️ Local Architecture Blueprint

## Layer 1: Foundations
- **Repository Purpose**: Ansina is a self-owned AI agent exposing a single internal REST API — no chat channels — built around a small always-on "Heart" model (in-process, ≤4B/8k-ctx) and a large remote "Brain" model (35B+) for actual reasoning.
- **Tech Stack**: Python ≥ 3.14 / FastAPI / SQLite. Embedded inference in-process via MLX (the only `HeartRuntime` adapter shipped so far, Apple-Silicon-only); a portable, non-Apple-Silicon fallback (originally scoped as llama-cpp-python) is deferred to a follow-up issue — see Layer 5. See `docs/architecture/blueprint.md` for the full rationale and the OpenClaw comparison this design departs from.

## Layer 2: Directory Layout
- `Makefile`: dev-workflow entry point — bootstraps `uv` (Astral installer, macOS/Linux) if missing, wraps `sync`/`lint`/`format`/`typecheck`/`test`/`check`/`clean`.
- `src/ansina/`: Core application source code (src-layout package, `py.typed` marker for downstream type-checking).
- `src/ansina/__main__.py`: Process entry point (`python -m ansina` / the `ansina` console script). Loads config, configures logging, builds the app via `create_app()`, hands it to uvicorn.
- `src/ansina/api/`: REST API surface (issue #4). `create_app()` in `api/app.py` is the FastAPI factory. `api/middleware.py` assigns/echoes the request id and feeds `logging`'s correlation-id contextvar. `api/auth.py` (issue #5) enforces a static bearer token via `hmac.compare_digest`, deny-by-default — every route needs the token except `PUBLIC_PATHS` (`/healthz`, `/readyz`); a `None` token (dev mode) disables enforcement, and `config.settings` refuses to boot at all if that's paired with a non-loopback bind. `api/problems.py` + `api/exception_handlers.py` map every error door (`AnsinaError`, HTTP errors, validation errors, unhandled exceptions) to RFC 9457 `application/problem+json`. `api/readiness.py` is a named-check registry backing `GET /readyz`; later milestones register their own checks there instead of editing the route. `api/routes/health.py` holds the M0 routes: `/healthz`, `/readyz`, `/version`. `api/routes/heart.py` (issue #11) holds Ansina's first non-health, non-public routes: `GET /heart/tick` (status), `POST /heart/tick/pause`/`/resume` (the tick loop's kill switch) — all deny-by-default like everything else, and all return 503 `problem+json` (`CODE_HEART_DISABLED`) when `app.state.tick_loop` is `None`.
- `src/ansina/config/`: Typed `Settings` (pydantic-settings). Layering: defaults → `ansina.toml` → `ANSINA_*` env vars. Load via `load_settings()`, never `os.getenv()` directly. Secrets are env-only — a `SecretStr` field set in the TOML file is a startup error. `database.path` is normalized (`~` expanded, relative paths resolved against CWD) by a `field_validator`, so every consumer sees one already-absolute path regardless of how it was configured.
- `ansina.example.toml`: documents the config file shape; copy to `ansina.toml` (gitignored) to use.
- `src/ansina/errors.py`: `AnsinaError` base exception with a stable, machine-readable `code` (`ClassVar[str]`); every subclass must declare its own `code` or class creation raises. `ansina.config.ConfigError` and `ansina.errors.StorageError` subclass it.
- `src/ansina/storage/`: SQLite persistence foundation (issue #6). `database.py`'s `Database` hands out one connection per thread (`threading.local`) rather than a single shared connection — sub-agents (later milestone) will read this database concurrently, and WAL lets those reads proceed unblocked by the writer; writes still serialize, per SQLite. Every connection gets `PRAGMA foreign_keys=ON` (per-connection state) and `PRAGMA busy_timeout` (so a second writer retries instead of failing instantly); `PRAGMA journal_mode=WAL` is per-database and verified once at `connect()`. `migrator.py`'s `run_migrations()` is a forward-only runner backed by a `schema_version` table, rejecting out-of-order or skipped versions; migrations themselves are plain numbered `.sql` files under `storage/migrations/` (currently just `0001_init.sql`, which creates `schema_version` — no domain tables in M0). Both are driven from `api/app.py`'s lifespan, never called ad hoc elsewhere.
- `src/ansina/logging/`: JSON structured logging via `logging.config.dictConfig`. Redaction runs inside `JsonFormatter`, not at call sites — never bypass it by formatting log strings yourself. Request/correlation ids via `contextvars` (`request_id_scope()`). Boot with `configure_logging(load_settings())`, then use `get_logger(__name__)` everywhere else, never bare `logging.getLogger()`.
- `src/ansina/heart/` (issue #10): the in-process Heart runtime. `runtime.py`'s `HeartRuntime` is a structural `Protocol` (`load`/`generate`/`token_count`/`unload`/`is_healthy`) plus `BaseHeartRuntime`, an ABC owning the loaded-state guard and the 8k context-budget refusal shared by every adapter — subclasses only implement four `_*` backend hooks. `models.py`'s `resolve_model()` resolves an explicit `[heart] model_path` (wins, no network) or downloads `model_repo` from Hugging Face into `cache_dir` (download-once cache); `selection.py`'s `build_heart_runtime()` is the capability probe — MLX is viable only on `darwin`/`arm64` with `mlx_lm` importable (import success alone isn't enough: `mlx` also ships manylinux wheels), and any other host gets a loud `HeartUnavailableError`, never a silent fallback. `adapters/mlx.py` is the only adapter shipped — a second, non-Apple-Silicon adapter is deferred to a follow-up issue (no llama-cpp-python-compatible GPU was available to prove it against). Every backend import (`mlx_lm`, `huggingface_hub`) happens inside function bodies, never at module scope, so `ansina.heart` stays importable without the optional `ansina[mlx]` extra installed. `[heart] enabled` defaults to `false` — off, none of this runs.
- `src/ansina/heart/tick/` (issue #11): the autonomic tick loop, the Heart's one day-one duty and the first caller of `HeartRuntime.generate()`. `loop.py`'s `TickLoop` schedules `tick_once()` on a fixed cadence (`start + n*interval`, recomputed each cycle so a slow tick can't drift future ticks or burst-fire missed slots — see `_next_tick_number`), guarded against overlap by an in-flight flag, with `pause()`/`resume()` as the kill switch and any tick exception logged and swallowed so one failure can't end the loop. `snapshot.py` builds the bounded prompt: a `StateSnapshotSource` `Protocol` (structural, like `HeartRuntime`) contributes `SnapshotItem`s, and `build_prompt()` measures with the runtime's own `token_count` and drops lowest-priority items until the prompt fits `context_tokens - max_output_tokens` — enforced before `generate()` is ever called, not left to `HeartContextOverflowError` as the mechanism. No source is registered yet (no pending-work/schedule/event domain exists — `storage/` ships only `schema_version`); a later issue registers one the same way milestones register a `Readiness` check. `decision.py`'s `parse_decision()` turns the Heart's raw reply into `TickDecision.IDLE/ACT/ESCALATE`, defaulting to `IDLE` on anything unparseable. `act` and `escalate` both dispatch through a `DecisionHandler` `Protocol`; the shipped `LoggingDecisionHandler` only logs — there is nothing to act on yet and `BrainProvider` (issue #12) doesn't exist, so escalate has nowhere to hand off to. `[heart.tick] enabled` defaults to `true` but is inert unless `[heart] enabled` is also `true`.
- `tests/conftest.py`: suite-wide fixture root above the `unit/`/`e2e/` split. `tests/unit/`: mirrors `src/ansina/` 1:1 (issue #16), e.g. `api/routes/test_health.py` for `api/routes/health.py` — every module gets its own test module, coverage held at 100% (`pyproject.toml`'s `[tool.coverage.report] fail_under = 100`), never just incidental coverage through a higher-level test. `tests/e2e/`: black-box, launches `python -m ansina` as a subprocess, run with `--no-cov` (a boot gate, not a coverage source).
- `README.md`: human front door — quick start, API table, links to `docs/`. `docs/architecture/`: `blueprint.md` — architecture rationale and roadmap.
- `.agents/`: Synced central prompts, guardrails, and protocols. Gitignored — never committed here, re-synced locally by `.githooks/sync.sh` (see below).
- `.githooks/`: `post-merge` hook runs `sync.sh`, which re-pulls `.agents/` from the central hub repo (`giacchetta/lead-agentic-ai-coding`) after every merge.
- `.github/workflows/ci.yml`: CI gate (issue #7) — `check` (ruff / ruff-format / mypy --strict / `pytest tests/unit`) then `e2e` (`needs: check`), both on `ubuntu-24.04` × `macos-26` (Apple Silicon, mirroring the M4 deployment target; the arm64 leg is required, not optional), Python 3.14 via `uv sync --locked --all-groups`. `.pre-commit-config.yaml` runs the identical checks through `uv run`, so the pinned tool versions come from `uv.lock` for both — never pin a linter separately in the pre-commit config.
- `.github/workflows/post-on-merge.yml`: thin caller into a reusable pipeline hosted in `giacchetta/giacchetta.github.io`; this repo owns only the trigger and the `merged == true` gate, all generation logic lives upstream.

## Layer 3: Data Flow & Entry Points
- Entry points: `python -m ansina` and the `ansina` console script (`[project.scripts]`), both resolving to `src/ansina/__main__.py:main`.
- Boot sequence: `load_settings()` → `configure_logging(settings)` → `create_app(settings)` (`src/ansina/api/app.py`) → `uvicorn.run(...)`. A `ConfigError` during boot prints the aggregated report to stderr and exits non-zero, never a traceback. `load_settings()` itself refuses to construct `Settings` (issue #5) when `server.host` isn't loopback and no `security.api_token` is configured — that invariant is unbypassable since it lives on `Settings`, not in `create_app`. `create_app`'s FastAPI `lifespan` opens the `Database` and runs `run_migrations()` on startup (a `MigrationError` there aborts boot the same way a `ConfigError` does) and closes it on shutdown; `Readiness` gets a `"database"` check backed by `Database.is_healthy()`. When `[heart] enabled` is true, `create_app` calls `build_heart_runtime()` *before* the lifespan even starts — a `HeartUnavailableError` (issue #10) surfaces the same way a `ConfigError` does, before uvicorn ever binds a port; the lifespan then loads the model and registers a `"heart"` readiness check, unloading it on shutdown alongside the database close. When disabled (the default), `app.state.heart` is `None` and `/readyz` carries no `heart` key at all. When the Heart is also enabled and `[heart.tick] enabled` is true (issue #11, its own default), `create_app` builds a `TickLoop` (`build_tick_loop`) the same way, and the lifespan `start()`s it after `heart.load()` and registers a `"heart_tick"` readiness check, `stop()`ing it on shutdown before `heart.unload()`. `app.state.tick_loop` is `None` unless both flags are true.
- Request flow: `RequestIdMiddleware` (outermost) binds/echoes a request id (feeding `logging`'s correlation-id contextvar) → `BearerAuthMiddleware` (401 `problem+json` if the route isn't in `PUBLIC_PATHS` and the bearer token is missing/wrong) → route → response, or an exception mapped to `application/problem+json` by the handlers in `api/exception_handlers.py`.

## Layer 4: External Integrations
- **SQLite** (`src/ansina/storage/`, issue #6): the only runtime dependency in M0. One file on disk, WAL journal mode, path set via `[database] path` / `ANSINA_DATABASE__PATH` (defaults to `./ansina.db`; WAL adds `-wal`/`-shm` sidecars next to it). No network service, no separate process.
- **MLX / Hugging Face** (`src/ansina/heart/`, issue #10): optional — the `ansina[mlx]` extra (`mlx-lm`, `huggingface-hub`), not a base dependency, and never installed in CI (both legs run with the Heart disabled). Apple-Silicon-only; a HF repo id is fetched into a local on-disk cache on first use (`[heart] cache_dir`) and reused after.
- **Cross-repo CI pipeline** (`.github/workflows/post-on-merge.yml`): CI-time only, not a runtime dependency. Calls a reusable workflow in `giacchetta/giacchetta.github.io` on every merged PR to generate a blog post; this repo passes PR/issue read access plus two secrets and owns no generation logic itself.

## Layer 5: Domain Blueprint
- **Heart** (≤4B, 8k ctx, in-process): owns the autonomic tick loop only — decide idle / act / escalate. Never answers user requests directly. Every prompt built for it must fit its 8k window; treat that as a hard constraint, not a target. The runtime port + MLX adapter (issue #10, `src/ansina/heart/`) and the tick loop (issue #11, `src/ansina/heart/tick/`) are wired into `create_app`'s lifespan; `TickLoop` is the first and only caller of `generate()`. Its snapshot has no real content yet (no pending-work/schedule/event domain exists), `act` has nothing to act on, and `escalate` has no `BrainProvider` (issue #12) to hand off to — all three are injected seams with log-only defaults, not implemented behavior.
- A portable, non-Apple-Silicon `HeartRuntime` adapter (originally scoped as llama-cpp-python in issue #10) is **deferred to a follow-up issue**: the only non-Apple hardware available at the time had no llama-cpp-python-compatible GPU, so an adapter there was unprovable and was cut rather than shipped untested. Until that lands, a non-Apple-Silicon host with `[heart] enabled = true` fails loudly at boot (`HeartUnavailableError`) rather than silently degrading.
- **Brain** (35B+, remote via `BrainProvider` port): owns all real reasoning. The Heart never replaces it or bypasses it for substantive answers.
- Three additional Heart duties (request triage, context curation, structured extraction) are **deliberately not implemented**. Prior embedded-model attempts produced low-quality output — each duty is a gated experiment (`Backlog — Experiments` milestone) requiring a benchmark win over a stated baseline before adoption. Do not fold this logic into the tick loop without that gate passing.
- No channel concept anywhere (no Discord/WhatsApp/etc., and no `ChannelId`-shaped abstraction either) — see `docs/architecture/blueprint.md` §2 for why this is refused deliberately, not an oversight.
- Primary deployment target is a Mac Mini (Apple M4, 16 GB unified memory) — adapter and performance decisions prioritize that hardware, not the local dev machine.
