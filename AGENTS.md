# 🏛️ Local Architecture Blueprint

## Layer 1: Foundations
- **Repository Purpose**: Ansina is a self-owned AI agent exposing a single internal REST API — no chat channels — built around a small always-on "Heart" model (in-process, ≤4B/8k-ctx) and a large remote "Brain" model (35B+) for actual reasoning.
- **Tech Stack**: Python ≥ 3.14 / FastAPI / SQLite. Embedded inference in-process via MLX (the only `HeartRuntime` adapter shipped so far, Apple-Silicon-only); a portable, non-Apple-Silicon fallback (originally scoped as llama-cpp-python) is deferred to a follow-up issue — see Layer 5. See `docs/architecture/blueprint.md` for the full rationale and the OpenClaw comparison this design departs from.

## Layer 2: Directory Layout
- `Makefile`: dev-workflow entry point — bootstraps `uv` (Astral installer, macOS/Linux) if missing, wraps `sync`/`lint`/`format`/`typecheck`/`test`/`check`/`clean` for the daemon, plus a parallel `tui-*` set (`tui-sync`/`tui-lint`/`tui-format`/`tui-typecheck`/`tui-test`/`tui-check`, issue #31) for the standalone `tui/` project below — `check`/`tui-check` stay independent so `check` keeps mirroring the `check` CI job exactly; `check-all` runs both.
- `src/ansina/`: Core application source code (src-layout package, `py.typed` marker for downstream type-checking).
- `src/ansina/__main__.py`: Process entry point (`python -m ansina` / the `ansina` console script). Loads config, configures logging, builds the app via `create_app()`, hands it to uvicorn.
- `src/ansina/api/`: REST API surface (issue #4). `create_app()` in `api/app.py` is the FastAPI factory. `api/middleware.py` assigns/echoes the request id and feeds `logging`'s correlation-id contextvar. `api/auth.py` (issue #5, redesigned by #24, its chain formalized by #25, extended by #26) enforces a bearer token, deny-by-default — every route needs one except `PUBLIC_PATHS` (`/healthz`, `/readyz`). `BearerAuthMiddleware` walks an `Authenticator` chain (`auth.authenticator.build_authenticators(db, settings)` — issue #28 added `settings` so `ApiTokenAuthenticator` can read `[security] token_last_used_resolution_seconds`; a required constructor param, no in-middleware default, so a follow-up milestone's OIDC authenticator is an append, not a rewrite) rather than a comparison against one static config secret, resolving a full `auth.principal.Principal` (user + every role reachable direct-or-via-group) onto `request.state.principal` — offloaded via `anyio.to_thread.run_sync` so the blocking sqlite scan + per-row hash comparison never stalls the event loop. An inactive user's token stops authenticating (`auth.authenticator.resolve_principal`'s own check — `find_user_by_api_token` itself doesn't filter on `users.active`). `security.enabled = False` (not "no token configured" — that now means "auto-generate one") is the only way to disable enforcement, and `config.settings` refuses to boot at all if that's paired with a non-loopback bind. Once a `Principal` is resolved, an `X-Sudo-Token` header (issue #26) is additionally checked against `app.state.sudo` (`auth.sudo.SudoService`) and, on a live match, elevates it via `Principal.with_sudo()` — an absent/expired/wrong/revoked grant never turns into a 401 by itself, it just fails to elevate, leaving a sensitive route's own 403 `CODE_SUDO_REQUIRED` as the only signal. `api/authorization.py`'s `require(resource, *, sensitive=False)` (issue #25) is the FastAPI dependency every non-public route declares — the verb is read from `request.method`, not declared per-route — answering "does the caller's `Principal` hold a role with a `role_permissions` row for (this resource, this verb)" via `auth.authorization.authorize()`, offloaded the same way; denial raises `ForbiddenError`/`SudoRequiredError` (403, `CODE_FORBIDDEN`/`CODE_SUDO_REQUIRED`), distinguishable from `BearerAuthMiddleware`'s 401 (`CODE_UNAUTHORIZED`, no/invalid identity) without leaking which credential component was wrong; every decision (granted or denied) is audit-logged with actor/resource/verb. `api/route_audit.py`'s `audit_route_coverage()` (issue #25) walks `app.routes` at `create_app()` time and raises `RouteCoverageError` — same "fail loudly before uvicorn binds a port" pattern as `HeartUnavailableError` — if any non-public route lacks exactly one `require(...)` declaration; its surviving declarations are also the `resources` catalog's entire source (replacing #24's `BOOTSTRAP_RESOURCES` seed constant, since deleted). `api/problems.py` + `api/exception_handlers.py` map every error door (`AnsinaError`, HTTP errors, validation errors, unhandled exceptions) to RFC 9457 `application/problem+json`. `api/readiness.py` is a named-check registry backing `GET /readyz`; later milestones register their own checks there instead of editing the route. `api/routes/health.py` holds the M0 routes: `/healthz`, `/readyz`, `/version` (`GET /version` gated `require("system.version")`). `api/routes/heart.py` (issue #11) holds Ansina's first non-health, non-public routes: `GET /heart/tick` (status), `POST /heart/tick/pause`/`/resume` (the tick loop's kill switch) — all gated `require("heart.tick")`, and all return 503 `problem+json` (`CODE_HEART_DISABLED`) when `app.state.tick_loop` is `None` (only once authorization already passed — a caller without a grant gets 403 without ever learning whether the Heart is even enabled). `api/routes/openapi.py` (issue #25) serves `GET /openapi.json` behind `require("system.openapi")` as a real, gated `APIRoute` — `create_app` passes `openapi_url=None, docs_url=None, redoc_url=None` to the `FastAPI` constructor, since the framework's default `/docs`/`/redoc`/`/docs/oauth2-redirect` are plain Starlette routes that can't carry a `require(...)` declaration (and are non-functional with auth enabled anyway — no `fastapi.security` scheme is declared for Swagger UI's "Authorize" button, since auth here is middleware-level). `api/routes/sudo.py` (issue #26) holds `POST /auth/sudo` (step up via `app.state.sudo.step_up()`, gated `require("auth.sudo")`), `DELETE /auth/sudo` (revoke your own grant, same resource), and the break-glass `DELETE /auth/sudo/grants` (revoke every active grant, gated `require("auth.sudo.grants", sensitive=True)` — reaching it already requires a live grant); all three are `auth.*` resources so `auth.policy.permitted_verbs` restricts them to Maintain/Admin with no policy change. `api/routes/users.py`/`groups.py`/`role_assignments.py`/`roles.py`/`permissions.py` (issue #27) round out the RBAC management surface Users/Groups/Roles the rest of M2 exists to protect. `users.py` (`GET`/`POST /auth/users`, `GET`/`PATCH`/`DELETE /auth/users/{id}`, `PUT /auth/users/{id}/password`, `POST`/`GET /auth/users/{id}/tokens`, `DELETE /auth/users/{id}/tokens/{token_id}`) and `groups.py` (`GET`/`POST /auth/groups`, `GET`/`PATCH`/`DELETE /auth/groups/{id}`, `PUT`/`DELETE /auth/groups/{id}/members/{user_id}`) each gate `GET` `sensitive=False` and every mutation `sensitive=True` on one resource (`auth.users`/`auth.groups` respectively); `DELETE /auth/users/{id}` is a one-way tombstone (`UserRepository.soft_delete`), never a row removal. Issue #28 narrows `POST .../tokens`: it mints a user's *first* `api_token` credential, never a second (`auth.management.assert_no_existing_api_token` — 409 otherwise, checked ahead of the bootstrap-identity guard below since its message actively misleads that identity); beyond the first, the user mints their own via `POST /auth/me/tokens`, and revoking their last token drops the count back to zero, making the admin route double as the lost-credential recovery path. All three token routes build on `api/tokens.py` (issue #28) — `TokenOut`/`IssueTokenRequest`/`IssuedTokenResponse` plus `issue_token()`/`list_tokens()`/`revoke_token()`, shared with `me.py` below, lifted out the same way `api/identity.py` was once a second router needed the identical shape. `issue_token()`/`revoke_token()` both call `auth.management.assert_not_bootstrap_identity()` — the bootstrap identity holds exactly one `api_token`, ever, so neither route can mint it a second one or delete the one it has (403 `ansina.auth.bootstrap_identity`); its `GET` is unaffected. `role_assignments.py` holds the four nested attach/detach routes (`POST`/`DELETE /auth/users/{id}/roles/{role_id}` and the `/auth/groups/...` equivalent, resource `auth.role_assignments`, always `sensitive=True`) and additionally runs every assignment through `auth.management.assert_may_assign_role` (skipped only when `security.enabled = False` leaves no resolved `Principal` to check against). `roles.py`/`permissions.py` are the read-only discovery pair: `GET /auth/roles` (every role with its current `role_permissions` grants — no create/update/delete route exists, by omission not by a stub that 403s) and `GET /auth/permissions` (the `resources` catalog crossed with every `Verb` — the full grantable space a future custom-role editor needs). `api/identity.py` (issue #30) holds the shared request-identity helpers — `current_principal(request)` (`request.state.principal` if `BearerAuthMiddleware` resolved one, else `None`) and `no_identity_response()` (the 401 `problem+json` for when it didn't) — lifted out of `routes/sudo.py`'s and `routes/role_assignments.py`'s own private copies once a third caller needed them; both now import from here instead. `api/routes/me.py` (issue #30, extended by #28) holds `GET /auth/me`, gated `require("me.profile")`: the first route on the `me.*` self-resource policy class (`auth.policy.is_self_resource`), reachable by every builtin role including `Read` and never sudo-gated, returning the already-resolved `Principal` (user, roles, sudo status) with no extra database read — note the resource is `me.profile` while the path stays `/auth/me`, since a resource is a stable, dotted, URL-independent name, never the path. Issue #28 adds `POST`/`GET /auth/me/tokens` and `DELETE /auth/me/tokens/{token_id}` on a second self-resource, `me.tokens` — self-service issuance/listing/revocation of the caller's own tokens, built on `api/tokens.py` (see the `users.py` entry above), refused (403 `ansina.auth.bootstrap_identity`) for the bootstrap identity on `POST`/`DELETE` but not `GET`.
- `src/ansina/config/`: Typed `Settings` (pydantic-settings). Layering: defaults → `ansina.toml` → `ANSINA_*` env vars. Load via `load_settings()`, never `os.getenv()` directly. Secrets are env-only — a `SecretStr` field set in the TOML file is a startup error. `database.path` is normalized (`~` expanded, relative paths resolved against CWD) by a `field_validator`, so every consumer sees one already-absolute path regardless of how it was configured.
- `ansina.example.toml`: documents the config file shape; copy to `ansina.toml` (gitignored) to use.
- `src/ansina/errors.py`: `AnsinaError` base exception with a stable, machine-readable `code` (`ClassVar[str]`); every subclass must declare its own `code` or class creation raises. `ansina.config.ConfigError` and `ansina.errors.StorageError` subclass it.
- `src/ansina/storage/`: SQLite persistence foundation (issue #6). `database.py`'s `Database` hands out one connection per thread (`threading.local`) rather than a single shared connection — sub-agents (later milestone) will read this database concurrently, and WAL lets those reads proceed unblocked by the writer; writes still serialize, per SQLite. Every connection gets `PRAGMA foreign_keys=ON` (per-connection state) and `PRAGMA busy_timeout` (so a second writer retries instead of failing instantly); `PRAGMA journal_mode=WAL` is per-database and verified once at `connect()`. `migrator.py`'s `run_migrations()` is a forward-only runner backed by a `schema_version` table, rejecting out-of-order or skipped versions; migrations themselves are plain numbered `.sql` files under `storage/migrations/`: `0001_init.sql` creates `schema_version` (no domain tables in M0); `0002_rbac.sql` (issue #24) adds the RBAC identity/permission schema — `roles`, `resources`, `role_permissions`, `users`, `"groups"` (always quoted — `GROUPS` is a SQLite keyword), `user_groups`, `role_assignments`, `credentials`, `external_identities`, `role_mappings`; `0003_sudo.sql` (issue #26) adds `sudo_grants` (one active grant per user, hash/salt never the raw token) and `sudo_lockouts` (at most one row per user, driven entirely by caller-supplied timestamps from an injectable clock — never a SQL-side `now`); `0004_user_tombstone.sql` (issue #27) adds `users.deleted_at` — a one-way marker distinct from `active`'s suspend/resume flag, set once by `UserRepository.soft_delete` and never cleared by any route. Both `Database` and `run_migrations()` are driven from `api/app.py`'s lifespan, never called ad hoc elsewhere.
- `src/ansina/auth/` (issue #24, extended by #25, #27, #28, #30): the RBAC identity & permission domain layer — data + repositories + the authorization decision itself; the HTTP routes built on top of it live in `api/routes/{sudo,users,groups,role_assignments,roles,permissions,me}.py` and `api/tokens.py`, described in Layer 2's `api/` entry above. Permissions are rows, not an enum: every authorization check is a `role_permissions` lookup for (a role, a resource, a verb), so a future admin-defined custom role is an `INSERT`, not a rewrite. `models.py` holds one frozen dataclass per table (each with a `from_row(sqlite3.Row)` classmethod) plus the `StrEnum`s (`Verb`, `RoleSlug`, `SubjectType`, `CredentialType`) that constrain them — `User.deleted_at` (issue #27) is the one-way tombstone marker, distinct from `active`'s suspend/resume flag. `hashing.py` ships two deliberately different credential-hashing paths: passwords use argon2id (`Argon2Params`, tuned via `[security.password]`) because a stolen hash must stay expensive to brute-force; API tokens use per-row-salted SHA-256 + `hmac.compare_digest` because `api/auth.py`'s middleware verifies one on every authenticated request, and argon2's deliberate work factor has no payoff against a high-entropy machine secret. `clock.py` (issue #28) holds a shared injectable `Clock` plus `utc_now()`/`iso()`/`parse_iso()` — moved out of `sudo.py` once a second caller (`authenticator.py`'s coalesced `last_used_at` bookkeeping) needed the exact same millisecond-precision-ISO-8601-sorts-as-text formatting `SudoGrantRepository.find_active`'s `expires_at > ?` comparison already relied on; `sudo.py` and `api/routes/users.py`'s own `_now_iso` copy both import from here now instead of keeping their own. `policy.py`'s `permitted_verbs()` is the *one* place the fixed builtin-role policy is expressed (any `me.*` resource=every verb, every role, checked first — issue #30's self-resource carve-out, not an escalation since the subject of a `me.*` action is always the caller themselves; Read=GET; Write=+POST/PUT/PATCH; Maintain/Admin=all verbs; any `auth.*` resource=Maintain/Admin only); its `BOOTSTRAP_RESOURCES` seed constant is gone as of #25 — `api/route_audit.py`'s real `app.routes` walk is now the `resources` catalog's only source, without changing `reconciler.py`'s `sync_resources()` contract. `repositories.py` is the first domain repository in the codebase, built directly on `Database.connection()`/`Database.transaction()` (no ORM) — `UserRepository.create()` structurally guarantees the "every M2 user gets exactly one `provider="local"` `external_identities` row" invariant in the same transaction (skippable via `local_identity=False` for the one caller that provides its own, `auth.bootstrap`); `RoleRepository` refuses to delete or demote a `builtin=1` role. `CredentialRepository` (issue #28 additions): `find_api_token_credential()` is the constant-time-scan primitive now returning the whole `Credential` row (not just the user), which `find_user_by_api_token()` delegates to so the scan exists in exactly one place; `list_api_tokens()`, `delete_api_token()` (scoped by both id and `user_id` — that scoping is what stops a caller revoking someone else's token), and `touch_last_used()` back the self-service token surface. `reconciler.py` seeds the four builtin roles and reconciles their `role_permissions` grants against the catalog at every boot, scoped to `builtin=1` roles only — a custom role's grants are never touched. `bootstrap.py` holds two independent boot-time provisioning functions (issue #24, redesigned by #28). `ensure_bootstrap_admin()` provisions a single synthetic Admin identity on first boot with zero users (its own `provider="local-bootstrap"` `external_identities` row — the one deliberate exception to the "local" rule) as a permanent break-glass credential: always auto-generates a high-entropy token, prints it to stdout **exactly once** via a plain `print(..., flush=True)` that deliberately bypasses `logging` (never redacted-into-`***`, never captured by log aggregation), and stores only its hash — created once and never touched again by any code path (no override, no rotation, as of #28) except `security.bootstrap_admin_enabled`: `false` revokes the credential while keeping the user/identity for audit attribution, and `true` regenerates one *only* if the identity is currently credential-less (closing a gap #28 found — previously, disabling then re-enabling never restored a credential once the identity row existed), never touching a live one. The generated token is also registered with `logging.redaction` as defense in depth even though nothing is designed to log it. `ensure_configured_admin()` (issue #28, new) provisions a second, ordinary `provider="local"` Admin user, once, from `ANSINA_SECURITY__ADMIN_USERNAME` + `ANSINA_SECURITY__API_TOKEN` (`config.settings.SecuritySettings` guarantees they're set together or neither is) — the "configured admin," which a scripted install or CI uses to get a known, reproducible credential without touching the bootstrap identity or scraping its banner; unlike the bootstrap identity it self-mints/revokes additional tokens the ordinary way via `POST`/`DELETE /auth/me/tokens`. Its "first boot" gate is "no user *other than* the bootstrap identity exists yet," not "`users` is empty" — `ensure_bootstrap_admin()` runs first in `create_app`'s lifespan and, on a genuine first boot, has already inserted the bootstrap identity's own `users` row by the time this runs, so the naive empty-table check would never fire, on every first boot. `is_bootstrap_identity()` (issue #28) is one indexed lookup against `external_identities`, used by `auth.management.assert_not_bootstrap_identity` to keep the bootstrap identity locked to exactly one `api_token` at the route layer — the configured admin is deliberately not subject to it. `principal.py` (issue #25, extended by #26) holds `Principal` (resolved user + role ids/slugs + `auth_method` + `sudo_active`/`sudo_grant_id`) and `AuthMethod`; `with_sudo(grant_id)` returns an elevated copy, the one place `sudo_active` ever becomes `True`. `authenticator.py` (issue #25, extended by #28) formalizes #24's inline DB-backed lookup behind a real `Authenticator` `Protocol` — `ApiTokenAuthenticator` wraps `CredentialRepository.find_api_token_credential` (issue #28: returns the credential row, not just the user, so the authenticator has the id/`last_used_at` it needs), `build_authenticators(db, settings)` returns the chain `api/auth.py`'s middleware walks, and `resolve_principal()` fills a `Principal`'s roles from `RoleAssignmentRepository.roles_for_user()`, rejecting an inactive or (issue #27) tombstoned (`deleted_at is not None`) user. Issue #28's coalesced `last_used_at` bookkeeping lives in `ApiTokenAuthenticator.authenticate()`: touches the credential's `last_used_at` only when the stored value is older than `[security] token_last_used_resolution_seconds` (default 300s, `0` means every request) — a **string** comparison against `clock.iso(now - resolution)`, not a parse, reusing the same lexicographic-sort property `SudoGrantRepository.find_active` already relies on — via an injectable `clock` (`auth.clock`) so the staleness threshold is testable without real sleeping. `authorization.py` (issue #25) is `authorize(db, principal, resource, verb, *, sensitive=False)`, the pure decision `api/authorization.py`'s `require()` dependency wraps: `ForbiddenError` (no role grants the verb) is checked before `SudoRequiredError` (right role, `maintain`-not-`admin`, no live sudo grant on a `sensitive=True` resource) — the latter is live as of #26. `step_up.py` (issue #26) is the pluggable `StepUpVerifier` `Protocol` (`verify(principal, payload) -> bool`) behind `POST /auth/sudo` — `PasswordStepUpVerifier` (M2's only implementation) re-checks a `payload["password"]` against `CredentialRepository.verify_password`; `StepUpRegistry.for_principal()` resolves which verifier applies (fixed to the one configured verifier in M2, a per-user choice in a follow-up milestone) without `auth.sudo` ever naming a concrete verifier. `sudo.py` (issue #26) is `SudoService` — issuance (`step_up()`, minting a `secrets.token_urlsafe` grant via `SudoGrantRepository`), the read side `BearerAuthMiddleware` calls (`resolve()`), revocation (`revoke_for_user()`/`revoke_all()`), and the failed-attempt lockout (`SudoLockoutRepository`-backed, `[security.sudo] max_failed_attempts` consecutive failures within `attempt_window_seconds` locks out for `lockout_seconds`, raising `SudoLockedOutError` mapped to 429 with a real `Retry-After` header) — driven by an injectable clock throughout (`auth.clock`, issue #28 — moved out of this module once `authenticator.py` needed the identical `Clock`/`iso`/`parse_iso` shape), so TTL/lockout expiry is tested without real sleeping. `management.py` (issue #27, extended by #28) holds the server-side guards the management routes need beyond `authorize()` itself, pure domain logic mirroring how `authorization.py` sits under `api/authorization.py`: `assert_may_assign_role()` (a caller can never grant a `role_permissions` row it does not itself effectively hold — the `admin` role and any `auth.*`-granting role are checked directly first, since `Maintain`/`Admin` hold identical grants under M2's fixed policy and a bare subset check alone wouldn't catch a sudo'd `Maintain` minting a fresh `Admin`; the general case is a subset-of-grants check, so it keeps working unchanged once non-builtin roles exist) and `assert_admin_remains()` (refuses — `LastAdminError`, 409 — to leave zero active, non-deleted holders of the `admin` role; called from every route that deletes, deactivates, or demotes a user, directly or via a group). Issue #28 adds two more: `assert_not_bootstrap_identity()` (`BootstrapIdentityError`, 403 — the bootstrap identity's one-token-ever invariant, checked by `api/tokens.py`'s `issue_token()`/`revoke_token()` and, ahead of the next guard, by `api/routes/users.py`'s own issuing route) and `assert_no_existing_api_token()` (`TokenAlreadyIssuedError`, 409 — an Admin issues a user's *first* token, never a second; called by `POST /auth/users/{id}/tokens` alone, since a user is always free to hold many of their own self-minted ones via `me.tokens`). `repositories.py` gained, for issue #27: `UserRepository.soft_delete()` (the one-way purge — credentials, role assignments, group memberships, sudo grants, all in one transaction, keeping only the `users` row and its identity for audit attribution) and `.set_display_name()`; `GroupRepository.update()`/`.delete()` (also explicitly clears the group's `role_assignments`, since `subject_id` there is deliberately not a foreign key)/`.remove_member()`/`.list_members()`/`.groups_for_user()`; `RoleAssignmentRepository.list_for_subject()` (direct-only, unlike `roles_for_user`'s group-following union) and `.user_ids_with_role()` (the inverse union query, filtered to active/non-deleted — backs `assert_admin_remains`); `RolePermissionRepository.grants_for_roles()` (the whole `(resource, verb)` grant set for a set of roles, not scoped to one resource like `effective_verbs` — backs `assert_may_assign_role`).
- `src/ansina/logging/`: JSON structured logging via `logging.config.dictConfig`. Redaction runs inside `JsonFormatter`, not at call sites — never bypass it by formatting log strings yourself. Request/correlation ids via `contextvars` (`request_id_scope()`). Boot with `configure_logging(load_settings())`, then use `get_logger(__name__)` everywhere else, never bare `logging.getLogger()`.
- `src/ansina/heart/` (issue #10): the in-process Heart runtime. `runtime.py`'s `HeartRuntime` is a structural `Protocol` (`load`/`generate`/`token_count`/`unload`/`is_healthy`) plus `BaseHeartRuntime`, an ABC owning the loaded-state guard and the 8k context-budget refusal shared by every adapter — subclasses only implement four `_*` backend hooks. `models.py`'s `resolve_model()` resolves an explicit `[heart] model_path` (wins, no network) or downloads `model_repo` from Hugging Face into `cache_dir` (download-once cache); `selection.py`'s `build_heart_runtime()` is the capability probe — MLX is viable only on `darwin`/`arm64` with `mlx_lm` importable (import success alone isn't enough: `mlx` also ships manylinux wheels), and any other host gets a loud `HeartUnavailableError`, never a silent fallback. `adapters/mlx.py` is the only adapter shipped — a second, non-Apple-Silicon adapter is deferred to a follow-up issue (no llama-cpp-python-compatible GPU was available to prove it against). Every backend import (`mlx_lm`, `huggingface_hub`) happens inside function bodies, never at module scope, so `ansina.heart` stays importable without the optional `ansina[mlx]` extra installed. `[heart] enabled` defaults to `false` — off, none of this runs.
- `src/ansina/heart/tick/` (issue #11): the autonomic tick loop, the Heart's one day-one duty and the first caller of `HeartRuntime.generate()`. `loop.py`'s `TickLoop` schedules `tick_once()` on a fixed cadence (`start + n*interval`, recomputed each cycle so a slow tick can't drift future ticks or burst-fire missed slots — see `_next_tick_number`), guarded against overlap by an in-flight flag, with `pause()`/`resume()` as the kill switch and any tick exception logged and swallowed so one failure can't end the loop. `snapshot.py` builds the bounded prompt: a `StateSnapshotSource` `Protocol` (structural, like `HeartRuntime`) contributes `SnapshotItem`s, and `build_prompt()` measures with the runtime's own `token_count` and drops lowest-priority items until the prompt fits `context_tokens - max_output_tokens` — enforced before `generate()` is ever called, not left to `HeartContextOverflowError` as the mechanism. No source is registered yet (no pending-work/schedule/event domain exists — `storage/` ships only `schema_version`); a later issue registers one the same way milestones register a `Readiness` check. `decision.py`'s `parse_decision()` turns the Heart's raw reply into `TickDecision.IDLE/ACT/ESCALATE`, defaulting to `IDLE` on anything unparseable. `act` and `escalate` both dispatch through a `DecisionHandler` `Protocol`; the shipped `LoggingDecisionHandler` only logs — there is nothing to act on yet, and although `BrainProvider` now exists (issue #12, `src/ansina/brain/`), nothing wires `escalate` to it yet — that hand-off is a follow-up issue, not part of #12's scope. `[heart.tick] enabled` defaults to `true` but is inert unless `[heart] enabled` is also `true`.
- `src/ansina/brain/` (issue #12): the remote Brain provider port — no in-process backend to guard, unlike `heart/`, but the same shape: a structural `Protocol` (`provider.py`'s `BrainProvider`, `stream`/`aclose`) plus a `BaseBrainProvider` ABC owning invariants every adapter shares. The load-bearing one, taken from OpenClaw (`docs/architecture/blueprint.md` §1): `stream()` returns synchronously (a plain method, not `async def`) and **never throws after invocation** — every failure arrives as a terminal `BrainErrorEvent` (`events.py`), never a raised exception into the caller's `async for`; only construction/selection-time failures raise (`BrainUnavailableError`). `BaseBrainProvider` also owns bounded retry (`retry.py`'s `backoff_seconds`, capped exponential backoff) — retried only while no `BrainTextDelta` has reached the caller yet, and only for a `RETRYABLE_ERROR_CLASSES`-classified failure — and explicit generator cleanup (`gen.aclose()` in a `finally`) so a caller cancelling mid-stream closes the adapter's in-flight HTTP request promptly rather than waiting on GC. `adapters/openai_compat.py`'s `OpenAICompatibleBrainProvider` is the only adapter shipped, working against any OpenAI-compatible chat-completions endpoint; `classify_openai_error()` maps the SDK's exception hierarchy to `BrainErrorClass`, and token/cost accounting (`BrainUsage`) is authoritative when the provider's own usage totals arrive, else an estimated (non-authoritative) char-based fallback. `selection.py`'s `build_brain_provider()` refuses to build (`BrainUnavailableError`) a keyless request against the *default* OpenAI host — a keyless custom `base_url` (a local OpenAI-compatible server) is left alone. Nothing calls `stream()` yet: wiring the tick loop's `escalate` branch to this port is a follow-up issue, not part of #12.
- `tests/conftest.py`: suite-wide fixture root above the `unit/`/`e2e/` split. `tests/unit/`: mirrors `src/ansina/` 1:1 (issue #16), e.g. `api/routes/test_health.py` for `api/routes/health.py` — every module gets its own test module, coverage held at 100% (`pyproject.toml`'s `[tool.coverage.report] fail_under = 100`), never just incidental coverage through a higher-level test. `tests/e2e/`: black-box, launches `python -m ansina` as a subprocess, run with `--no-cov` (a boot gate, not a coverage source).
- `README.md`: human front door — quick start, API table, links to `docs/`. `docs/architecture/`: `blueprint.md` — architecture rationale and roadmap.
- `.agents/`: Synced central prompts, guardrails, and protocols. Gitignored — never committed here, re-synced locally by `.githooks/sync.sh` (see below).
- `.githooks/`: `post-merge` hook runs `sync.sh`, which re-pulls `.agents/` from the central hub repo (`giacchetta/lead-agentic-ai-coding`) after every merge.
- `.github/workflows/ci.yml`: CI gate (issue #7) — `check` (ruff / ruff-format / mypy --strict / `pytest tests/unit`) then `e2e` (`needs: check`), both on `ubuntu-24.04` × `macos-26` (Apple Silicon, mirroring the M4 deployment target; the arm64 leg is required, not optional), Python 3.14 via `uv sync --locked --all-groups`. A third job, `tui` (issue #31), runs the identical checks for the standalone `tui/` project — its own `working-directory`/`cache-dependency-glob: tui/uv.lock` — independent of (no `needs:` on) `check`/`e2e`, since `tui/` never imports `ansina`. `.pre-commit-config.yaml` runs the identical checks through `uv run`, so the pinned tool versions come from `uv.lock` for both — never pin a linter separately in the pre-commit config; `tui/`'s hooks (`tui-ruff`/`tui-ruff-format`/`tui-mypy`/`tui-pytest`) are the same pattern against `tui/uv.lock`, using `--project tui` for the file-driven ruff hooks (so pre-commit's repo-root-relative paths still resolve) and `--directory tui` for mypy/pytest (`pass_filenames: false`, so cwd must actually be `tui/` for their own config's relative paths — e.g. `--cov=src/ansina_tui` — to resolve correctly).
- `.github/workflows/post-on-merge.yml`: thin caller into a reusable pipeline hosted in `giacchetta/giacchetta.github.io`; this repo owns only the trigger and the `merged == true` gate, all generation logic lives upstream.
- `tui/` (issue #31): the `ansina-tui` control-surface client — a standalone, dependency-isolated project (own `pyproject.toml`/`uv.lock`/`.venv`/CI job) that **never imports `ansina`**, talking HTTP only like any third-party client (pinned by `tests/unit/test_isolation.py`, asserting no `ansina`/`ansina.*` module in `sys.modules` after a CLI run). Ships `ansina-tui` (`[project.scripts]`) and `python -m ansina_tui`, both resolving to `ansina_tui.main:app`. `main.py`'s root `@app.callback(invoke_without_command=True)` is the no-args rule, the milestone's defining behavior: bare invocation on a TTY calls `launch_tui()`; any argument at all (a subcommand, `--help`, `--version`) is the CLI and never reaches it; bare invocation on a non-TTY prints help to **stderr** and exits `USAGE` (2) — Typer's rich-formatted `ctx.get_help()` prints to stdout as a side effect of formatting rather than just returning a string, so `clihelp.py`'s `print_help_to_stderr()` swaps `sys.stdout` for the call's duration instead of trusting `echo(..., err=True)` alone; issue #32's `commands/auth/__init__.py` reuses the same helper for its own two bare-invocation usage errors (`auth`, `auth token`) below. Global options (`--host`/`-H`, `--json`, `--verbose`, `--version`) are root-level like `git`'s or `docker`'s — they precede the subcommand, not follow it — resolved once into a frozen `context.AppContext` on `ctx.obj`. `exits.py`'s `ExitCode` is the sole source of the exit-code table: `0` ok, `1` request failed, `2` usage/local-config error, `3` not authenticated, `4` forbidden/sudo required, `5` host unreachable, `6` daemon not ready, `7` daemon not healthy — the last two extend issue #31's own 0–5 table (a reachable-but-unhealthy/not-ready daemon is neither "ok" nor "request failed"); `/healthz` is always checked before `/readyz`, so an unhealthy daemon exits `7`, never `6`. `config.py` is the XDG credential store (`$XDG_CONFIG_HOME/ansina`, else `~/.config/ansina`): `config.toml` (non-secret `default_host`, written by `save_config()`, issue #32) and `hosts.toml` (per-host `token`/`token_id`/`username`/`roles`/`sudo_token`/`sudo_expires_at` — `token_id`, issue #32, is set only when `auth token mint` stores the token it just minted, letting `auth token revoke` detect and warn on self-revocation), written via `os.open(..., 0o600)` and refused on read if group/other-readable (`InsecureCredentialsFileError`, naming the `chmod 600` fix) — serialized by a hand-rolled `_dump_toml` since 3.14's stdlib `tomllib` is read-only and no TOML-writer dependency was added for this one narrow schema. `ANSINA_TOKEN`/`ANSINA_HOST` (`resolve_token`/`resolve_host`) are resolved separately from `HostEntry`, so they can never be written back to disk. `client.py`'s `ApiClient` wraps `httpx.Client`: bearer auth, `X-Sudo-Token` attached only while an injectable-clock-checked grant is unexpired (`parse_expiry`, exported — issue #32's `session.py` reuses the exact same parse rather than duplicating it), and the daemon's echoed `X-Request-Id` (`ansina.api.middleware`) captured onto every `ApiResponse` for log correlation; `httpx.TransportError` becomes `HostUnreachableError` (exit 5). `problems.py` parses `application/problem+json` into `ApiProblem`, with a hand-copied (not imported — `tui/` can't import `ansina`) table of recognized `ansina.*` codes to human messages — issue #32 adds `ansina.auth.bootstrap_identity` (names the real fix: log in as the configured admin or an ordinary Admin), `ansina.auth.token_already_issued`, and `ansina.auth.not_found`. `output.py`'s `Emitter` is the output-discipline seam: with `--json`, stdout carries JSON and **nothing else** (a plain `sys.stdout.write`, never through `rich`) — every diagnostic goes to stderr; issue #32 adds `verbose`-gated `debug()` (so a request id can be shown without ever risking a secret), `warn()`, and a headered multi-column `table()` (`auth token list`). Issue #32 also adds the credential/session layer above `config.py` and the `auth` command surface built on it. `session.py`'s `Session` is the resolved host/config/credential state for one invocation; `resolve_session()` loads `config.toml`+`hosts.toml` and resolves `--host`/`ANSINA_HOST`/`ANSINA_TOKEN` precedence, scrubbing an *expired* sudo grant onto `Session.entry` in memory (never sent, never re-persisted) while `Session.hosts` keeps the raw, unscrubbed table so `auth sudo --status` can still tell "expired" apart from "never stored". `build_client()` is the single `ApiClient` construction point (and the one seam `tests/conftest.py`'s `patch_transport` fixture patches, replacing #31's `patch_status_transport` now that `commands/status.py` is built on this module too) — its `token=` override lets `auth login` authenticate with a just-supplied token before anything is stored. `save_entry()`/`remove_entry()` write `hosts.toml` back (the former also sets `default_host` on first login); `sudo_state()` classifies a `HostEntry`'s grant as `none`/`expired`/`active`. `secret_input.py`'s `read_token()`/`read_password()` are the "never argv" seam pinned by `tests/unit/test_argv_safety.py`'s walk of the whole Click command tree (vendored inside Typer, `typer._click` — no separate `click` import): `--with-token`/a piped non-TTY stdin is read directly, otherwise a `typer.prompt(hide_input=True)`; both resolve `sys.stdin` inside the function body, never as a `= sys.stdin` default-argument value, which would bind once at import time and miss `CliRunner`'s per-invocation stdin swap (the same trap `main.py`'s `_is_interactive` already documents). `failures.py`'s `report()` is the shared non-2xx renderer every command calls: the recognized message from `problems.py` (or a per-call override — `auth sudo` overrides `ansina.unauthorized`'s generic "run `auth login`" text, since that code means "wrong step-up password" at `POST /auth/sudo`), the request id under `--verbose`, and a rendered `Retry-After` figure from the problem body's own `retry_after_seconds` extension member (issue #26's sudo lockout, 429). `commands/auth/` (package) holds `login.py` (`login`/`logout`), `status.py` (`auth_status_command` — always a live `GET /auth/me`, no cache fallback), `sudo.py` (`sudo_command`: `--revoke`/`--status`, the latter local-only and self-healing an expired grant it finds), and `tokens.py` (`mint`/`list`/`revoke` over `/auth/me/tokens`, #28 — `mint` shows the raw token once, reusing #24's bootstrap-banner framing, and offers to store it; `revoke` warns and confirms before revoking the id currently in use). `commands/auth/__init__.py` wires `auth_app` (+ nested `token_app`) into `main.py`'s root app via `add_typer`; bare `auth`/`auth token` is a usage error (exit 2), not silent success. `commands/status.py` (day-0, issue #31) is now built on `session.py` the same way: `GET /healthz` → `/readyz` → `/version`, works with **no token at all** (both health routes are public), `/version` 401 degrades to `"unknown"` rather than an error. `commands/api.py` (issue #33) is `ansina-tui api [-X METHOD] <path>` — the raw REST wrapper reaching any daemon route with no per-route special-casing and no allow-list to keep in sync, and the milestone's CI/CD surface (so it never blocks for input). It required two small, additive extensions rather than a new foundation: `client.py`'s `ApiResponse` gained `text` (the body verbatim) and `headers` (the response headers, for `-i`), and `ApiClient.request()` gained `content=` (a raw body, alongside the existing `json_body=`; httpx's own `encode_request` checks `content` before `json`, so the two never conflict) and `headers=` (a caller's own headers merged in) — critically, `Authorization`/`X-Sudo-Token` are now set by plain assignment *after* merging a caller's headers, never `setdefault`, so a `-H` can never silently replace either (when no token is configured at all, a caller-supplied `Authorization` still passes through unharmed). `RESERVED_HEADERS` (`authorization`, `x-sudo-token`) is exported so `commands/api.py` can warn, not just silently override. `output.py` gained `Emitter.body()`, a plain `sys.stdout.write` (never through `rich`, same discipline as `Emitter.json`) for the response body verbatim — deliberately not `Emitter.json`, which re-serializes a `Mapping` with `sort_keys=True` and would reorder the daemon's fields or reject a non-object body. `api_command` itself: `-f/--field key=value` (repeatable) assembles a JSON object body whose values are always JSON strings — a typed field goes through `--input <file|->` instead, mutually exclusive with `-f`; method defaults to `GET`, or `POST` when either supplies a body (the `gh api` convention). Output follows `_stdout_is_tty()` (its own function, patched in tests, for the same `CliRunner`-swaps-`sys.stdout` reason `main._is_interactive` is): pretty-printed JSON on a TTY with no `--json`, raw under `--json` or a piped stdout — and the body is written whether or not the response was 2xx, so `--json | jq` works on a problem document too. `-i/--include` (status line + response headers) is rendered via `emitter.line()`, so it is itself suppressed under the same `--json`/piped-stdout condition, keeping the two rules from conflicting. `pyproject.toml` gained `[tool.ruff.lint.flake8-bugbear] extend-immutable-calls = ["typer.Option", "typer.Argument"]` — without it, ruff's B008 misfires on the standard Typer idiom for a repeatable option (`fields`/`raw_headers` here) as if it were a mutable default. Issue #34 replaces #31's placeholder shell with the real Overview tab and adds `daemon_state.py`, the module holding the whole of "what the daemon says about itself" as a pure, synchronous, **never-raising** function — `fetch_overview(app_context, env=...)` re-resolves a `Session`/`ApiClient` via `session.resolve_session()`/`build_client()` on every call (the same construction point and `patch_transport` test seam every CLI command already uses) and turns `HostUnreachableError`/`InsecureCredentialsFileError` into a designed `OverviewSnapshot` (`host`, `connection: "connected"|"unreachable"|"config error"`, a whole-tab `error`, and one `Panel` — `rows`/`message` — per section: `health`/`readiness`/`version`/`identity`) rather than letting either propagate; that's load-bearing because Textual's `@work` defaults to `exit_on_error=True`, so a raise out of a worker would crash the app instead of rendering an empty state. `readiness_checks()`/`version_display()` moved here from `commands/status.py` (which now imports them) so the CLI and the TUI agree on exactly what a "check" is and how a version renders. `ui/tabs.py`'s `RefreshableTab(VerticalScroll)` is the one-method contract (`TAB_ID`/`TAB_TITLE` class vars, an `__init__(app_context)` every subclass must keep positionally compatible, and `request_refresh()`) that lets `ui/app.py`'s `AnsinaTuiApp` compose a `TABS: ClassVar[tuple[type[RefreshableTab], ...]]` generically and dispatch `r` via `self.query(RefreshableTab)` (Textual's widget query matches subclasses) — adding a second tab is an append to `TABS`, no other change to `app.py`. `CSS_PATH` is set to an absolute `Path(__file__).parent / "app.tcss"` rather than a bare relative string, since Textual resolves a relative `CSS_PATH` against the *actual* (sub)class's module (`inspect.getfile(type(self))`), which would otherwise break for any test harness subclassing the app from a different directory. `ui/overview.py`'s `OverviewTab(RefreshableTab)` is the one tab M4 ships: `compose()` mounts one `Static` per section, `on_mount()` fires an immediate `request_refresh()` and `set_interval(app_context.refresh, ...)`, and `request_refresh()` drives an `@work(exclusive=True, group="overview")` worker (`asyncio.to_thread` around the synchronous `fetch_overview`) that updates those same widgets in place — never re-mounting — so a refresh never flickers or duplicates content; `fetcher` is constructor-injectable so widget tests drive every designed state without a transport. A panel with rows renders as a borderless `rich.table.Table`; a message-only panel as plain text; a fully empty panel (a whole-tab failure) as a `"—"` placeholder — never blank. The tab also keeps `App.sub_title` current (`"<host> · <connection>"`) on every refresh, which is how host/connection state stays visible in the header. `context.AppContext` gained `refresh: float = 5.0` — TUI-only, but resolved as a root-level `--refresh` option in `main.py` (the no-args rule leaves no subcommand to carry it) and validated (`> 0`) only on an actual TUI launch, after the interactivity check, so `--refresh 0 status` is untouched by the validation. `tests/unit/` mirrors `src/ansina_tui/` 1:1 at the same 100%-coverage bar as the daemon; shared test helpers live as `tests/conftest.py` **fixtures**, never a plain module-level import — `tests/` has no `__init__.py`, so cross-file `from tests.conftest import ...` isn't reliable under `--import-mode=importlib`.

## Layer 3: Data Flow & Entry Points
- Entry points: `python -m ansina` and the `ansina` console script (`[project.scripts]`), both resolving to `src/ansina/__main__.py:main`.
- Boot sequence: `load_settings()` → `configure_logging(settings)` → `create_app(settings)` (`src/ansina/api/app.py`) → `uvicorn.run(...)`. A `ConfigError` during boot prints the aggregated report to stderr and exits non-zero, never a traceback. `load_settings()` itself refuses to construct `Settings` (issue #5, updated by #24) when `server.host` isn't loopback and `security.enabled` is `False` — that invariant is unbypassable since it lives on `Settings`, not in `create_app`; `api_token` being unset no longer factors in (issue #24 makes it optional even with auth enabled — Ansina generates its own bootstrap token instead). `api_token`, when set, must itself look securely generated: `_TOKEN_MIN_LENGTH` (32), `_TOKEN_CHARSET` (base64url only, so a human-typed phrase is rejected outright), `_TOKEN_MIN_ENTROPY_BITS_PER_CHAR` (2.5, a best-effort predictability deterrent, not a cryptographic guarantee) all in `config/settings.py`. After every router is included, `create_app` calls `api/route_audit.py`'s `audit_route_coverage(app)` (issue #25) — a `RouteCoverageError` there aborts boot the same "fail loudly before uvicorn binds a port" way a `ConfigError` does — and stashes its returned `ResourceSpec`s on `app.state.resource_specs`. `create_app`'s FastAPI `lifespan` opens the `Database` and runs `run_migrations()` on startup (a `MigrationError` there aborts boot the same way), then — issue #24, in this fixed order because each step depends on the last — `sync_resources()` catalogs `app.state.resource_specs` (issue #24 seeded this from a hand-written constant; #25 replaced that argument with the route audit's real walk, `sync_resources()`'s own contract unchanged), `reconcile_builtin_roles()` grants the four builtin roles against that catalog, `ensure_bootstrap_admin()` provisions the synthetic Admin identity, and (issue #28) `ensure_configured_admin()` provisions the second, ordinary Admin from `ANSINA_SECURITY__ADMIN_USERNAME`/`API_TOKEN` if set (see `src/ansina/auth/` below for both functions' full shape — order between the last two no longer matters functionally, since #28's "first boot" check for the second is independent of it, but it runs second to keep the narrative order); an `AuthError` from any of the four aborts boot the same way. `Database` is closed on shutdown; `Readiness` gets a `"database"` check backed by `Database.is_healthy()` (no dedicated `/readyz` check for the RBAC seeding — `database` already covers its only failure mode). When `[heart] enabled` is true, `create_app` calls `build_heart_runtime()` *before* the lifespan even starts — a `HeartUnavailableError` (issue #10) surfaces the same way a `ConfigError` does, before uvicorn ever binds a port; the lifespan then loads the model and registers a `"heart"` readiness check, unloading it on shutdown alongside the database close. When disabled (the default), `app.state.heart` is `None` and `/readyz` carries no `heart` key at all. When the Heart is also enabled and `[heart.tick] enabled` is true (issue #11, its own default), `create_app` builds a `TickLoop` (`build_tick_loop`) the same way, and the lifespan `start()`s it after `heart.load()` and registers a `"heart_tick"` readiness check, `stop()`ing it on shutdown before `heart.unload()`. `app.state.tick_loop` is `None` unless both flags are true. When `[brain] enabled` is true (issue #12, independent of `[heart] enabled`), `create_app` calls `build_brain_provider()` the same "fail loudly before uvicorn binds a port" way (`BrainUnavailableError`); the lifespan `await`s `brain.aclose()` on shutdown alongside `heart.unload()`/`db.close()`. `app.state.brain` is `None` when disabled. No `/readyz` check is registered for it — the only meaningful liveness signal for a remote provider is a real network round-trip, and paying for one on every `/readyz` poll is the wrong trade.
- Request flow: `RequestIdMiddleware` (outermost) binds/echoes a request id (feeding `logging`'s correlation-id contextvar) → `BearerAuthMiddleware` (401 `problem+json` if the route isn't in `PUBLIC_PATHS` and the bearer token doesn't resolve a `Principal` through the `Authenticator` chain; issue #26: a resolved `Principal` carrying a live `X-Sudo-Token` is additionally elevated here) → the route's `require(resource)` dependency (403 `problem+json` if the resolved `Principal` holds no role granting `request.method` on that resource — issue #25, dev mode/`security.enabled=False` skips this too; 403 `CODE_SUDO_REQUIRED` if the resource is `sensitive=True`, the role is `maintain`-not-`admin`, and no elevation happened above) → route → response, or an exception mapped to `application/problem+json` by the handlers in `api/exception_handlers.py`. The `auth.*` management routes (issue #27) split `sensitive` by verb on the same resource rather than per-route: `GET /auth/users`/`/auth/groups`/`/auth/roles`/`/auth/permissions` are `sensitive=False` (Maintain reaches them with no grant), every mutating verb on `auth.users`/`auth.groups`/`auth.role_assignments` is `sensitive=True`. `me.tokens` (issue #28) is never `sensitive=True` at all, matching `me.profile`'s carve-out. A successful match against the `Authenticator` chain (issue #28) also coalesces a `last_used_at` write onto the matched credential — at most once per `[security] token_last_used_resolution_seconds`, not per request, since the lookup already full-scans `credentials` on every request.

## Layer 4: External Integrations
- **SQLite** (`src/ansina/storage/`, issue #6): the only runtime dependency in M0. One file on disk, WAL journal mode, path set via `[database] path` / `ANSINA_DATABASE__PATH` (defaults to `./ansina.db`; WAL adds `-wal`/`-shm` sidecars next to it). No network service, no separate process.
- **argon2-cffi** (`src/ansina/auth/hashing.py`, issue #24): a *base* dependency, not an optional extra — same reasoning as `openai` above: auth is not optional, and both CI legs must exercise password hashing. Ships prebuilt wheels for macos-arm64 and linux-x86_64, so neither CI leg compiles from source.
- **MLX / Hugging Face** (`src/ansina/heart/`, issue #10): optional — the `ansina[mlx]` extra (`mlx-lm`, `huggingface-hub`), not a base dependency, and never installed in CI (both legs run with the Heart disabled). Apple-Silicon-only; a HF repo id is fetched into a local on-disk cache on first use (`[heart] cache_dir`) and reused after.
- **OpenAI-compatible endpoint** (`src/ansina/brain/`, issue #12): the `openai` SDK is a *base* dependency (unlike `ansina[mlx]` above) — pure Python, installs and is exercised on every CI leg, since the Brain being off by default (`[brain] enabled = false`) is a config default, not a platform constraint. Works against any endpoint speaking the OpenAI chat-completions protocol (OpenAI itself, an Anthropic-via-compat-shim, OpenRouter, a self-hosted server), configured via `[brain] base_url`/`api_key`/`model` — never hardcoded to one vendor. `api_key` is env-only (`ANSINA_BRAIN__API_KEY`), same as `security.api_token`.
- **Cross-repo CI pipeline** (`.github/workflows/post-on-merge.yml`): CI-time only, not a runtime dependency. Calls a reusable workflow in `giacchetta/giacchetta.github.io` on every merged PR to generate a blog post; this repo passes PR/issue read access plus two secrets and owns no generation logic itself.

## Layer 5: Domain Blueprint
- **Heart** (≤4B, 8k ctx, in-process): owns the autonomic tick loop only — decide idle / act / escalate. Never answers user requests directly. Every prompt built for it must fit its 8k window; treat that as a hard constraint, not a target. The runtime port + MLX adapter (issue #10, `src/ansina/heart/`) and the tick loop (issue #11, `src/ansina/heart/tick/`) are wired into `create_app`'s lifespan; `TickLoop` is the first and only caller of `generate()`. Its snapshot has no real content yet (no pending-work/schedule/event domain exists), `act` has nothing to act on, and `escalate` — although `BrainProvider` now exists (issue #12) and is wired into `create_app` alongside it — still has no hand-off wired to it; all three remain injected seams with log-only defaults, not implemented behavior, until a follow-up issue connects `escalate` to `BrainProvider.stream()`.
- A portable, non-Apple-Silicon `HeartRuntime` adapter (originally scoped as llama-cpp-python in issue #10) is **deferred to a follow-up issue**: the only non-Apple hardware available at the time had no llama-cpp-python-compatible GPU, so an adapter there was unprovable and was cut rather than shipped untested. Until that lands, a non-Apple-Silicon host with `[heart] enabled = true` fails loudly at boot (`HeartUnavailableError`) rather than silently degrading.
- **Brain** (35B+, remote via `BrainProvider` port): owns all real reasoning. The Heart never replaces it or bypasses it for substantive answers. The port + its OpenAI-compatible adapter (issue #12, `src/ansina/brain/`) are implemented and wired into `create_app`'s lifespan the same way the Heart is, gated by `[brain] enabled` independently of `[heart] enabled` — but nothing calls `BrainProvider.stream()` yet; a local 35B adapter and multi-provider routing/fallback chains are explicitly out of scope, deferred the same "unprovable on hardware at hand" way the llama-cpp-python fallback above was.
- Three additional Heart duties (request triage, context curation, structured extraction) are **deliberately not implemented**. Prior embedded-model attempts produced low-quality output — each duty is a gated experiment (`Backlog — Experiments` milestone) requiring a benchmark win over a stated baseline before adoption. Do not fold this logic into the tick loop without that gate passing.
- No channel concept anywhere (no Discord/WhatsApp/etc., and no `ChannelId`-shaped abstraction either) — see `docs/architecture/blueprint.md` §2 for why this is refused deliberately, not an oversight.
- Primary deployment target is a Mac Mini (Apple M4, 16 GB unified memory) — adapter and performance decisions prioritize that hardware, not the local dev machine.
- **RBAC identity & access control** (M2 milestone, complete — `src/ansina/auth/` + `api/authorization.py`/`api/route_audit.py`/`api/routes/{sudo,users,groups,role_assignments,roles,permissions,me}.py`): replaces #5's one-shared-secret model with real `User`/`Group` identity and a permission model keyed on data, not code — "is there a `role_permissions` row granting (a role, a resource, a verb)?" is the entire authorization question, for both builtin and (future) admin-defined roles. Issue #24 shipped the data model, hashing, the builtin-role reconciler, and — pulled forward from #25's original scope, since the alternative was an unauthenticatable server (an auto-generated bootstrap token, by design, is never in config for a static comparison to check) — `api/auth.py`'s DB-backed bearer-token verification. Issue #25 built the rest on top: a formal `Authenticator` chain (`auth.authenticator`, formalizing #24's inline lookup — pluggable, an OIDC authenticator is a future append, not a rewrite), the request-scoped `Principal`, the `require(resource)` authorization dependency (403 on no matching `role_permissions` row, distinguishable from `BearerAuthMiddleware`'s 401 without leaking which credential component was wrong), and the mandatory startup route-coverage audit that also became the `resources` catalog's real source (replacing #24's `BOOTSTRAP_RESOURCES` seed, since deleted) — retrofitted onto every existing route (`system.version`, `heart.tick`, and #25's own `system.openapi`). Issue #26 shipped sudo step-up for `Maintain` on sensitive `auth.*` actions: a pluggable `StepUpVerifier` port (`auth.step_up`, one password implementation in M2) behind `POST /auth/sudo`, grant issuance/TTL/revocation/lockout in `auth.sudo.SudoService` (verifier-agnostic — a follow-up milestone's second verifier is a new `StepUpVerifier`, not a rewrite), elevation via `BearerAuthMiddleware` reading `X-Sudo-Token`, and the break-glass `DELETE /auth/sudo/grants` — the first route to actually pass `sensitive=True`, proving `authorize()`'s `SudoRequiredError` branch end to end before #27 (Users/Groups/Roles management, the routes this mechanism actually exists for) had landed. Issue #27 (done) closes the milestone: Users/Groups/Roles management over the REST API itself (`api/routes/users.py`/`groups.py`/`role_assignments.py`/`roles.py`/`permissions.py`), `Admin`/`Maintain` only with every mutation sudo-gated for `Maintain` — the first routes to declare an `auth.*` resource beyond `auth.sudo`/`auth.sudo.grants`, and the first to make that sudo gate protect something other than a break-glass route. Two guards in `auth.management` (`assert_may_assign_role`, `assert_admin_remains`) enforce server-side, not just documented, that no caller can grant a permission it doesn't itself hold and that the last `Admin` can never be removed; `DELETE /auth/users/{id}` is a one-way tombstone (`0004_user_tombstone.sql`'s `users.deleted_at`), never a row removal. `GET /auth/roles`/`GET /auth/permissions` are read-only discovery — no role write route exists in M2. Custom admin-defined roles and any external identity provider are explicitly out of scope for the whole M2 milestone, deferred to a follow-up that adds rows to #24's tables rather than reworking them.

M4's issue #30 — the first of M4's two daemon-side issues (the milestone is otherwise a client, `tui/`) — extends this policy with a third resource class: `me.*`, self-resources whose subject is always the authenticated caller, granted every verb by every builtin role unconditionally (`auth.policy.is_self_resource`, checked first in `permitted_verbs()`) — not an escalation, since a `me.*` route can never reach another user's data by construction. `GET /auth/me` (`api/routes/me.py`, resource `me.profile`) is the first route on it, returning the already-resolved `Principal` with no database read and never sudo-gated. `api/identity.py` (new) holds `current_principal()`/`no_identity_response()`, the shared "resolved `Principal` or a 401" helpers `sudo.py`, `role_assignments.py`, and `me.py` all now share.

M4's issue #28 (done) adds `me.tokens` on the same prefix — self-service API token issuance/listing/revocation (`POST`/`GET /auth/me/tokens`, `DELETE /auth/me/tokens/{id}`), plus the admin-on-behalf-of equivalents on `auth.users` (`GET /auth/users/{id}/tokens`, `DELETE /auth/users/{id}/tokens/{token_id}`, and a narrowed `POST` — first-credential-only, 409 on a second) — and, while reviewing how the bootstrap credential's rotation worked, redesigns the bootstrap identity itself: it splits into a permanent, never-overridable, never-rotated **bootstrap identity** (auto-generated every first boot, capped at exactly one `api_token` ever) and a separate, ordinary **configured admin** (`ANSINA_SECURITY__ADMIN_USERNAME`+`API_TOKEN`, required together, provisioned once at first boot) that a scripted install or CI actually wants a reproducible credential from — see `docs/architecture/blueprint.md`'s "Bootstrap identity vs. configured admin" for the full reasoning, and Layer 2's `auth/bootstrap.py`/`auth/management.py` entries above for the mechanics. `last_used_at` bookkeeping (also #28) is coalesced, not per-request, per `[security] token_last_used_resolution_seconds`.

Issue #31 (done) lands the client side's foundation: `tui/` itself (see Layer 2), proven end to end by one real command, `ansina-tui status`, against a live daemon. Everything #32 (`auth`), #33 (`api`), and #34 (the TUI shell's Overview tab) build on — `client.py`, `config.py`, `problems.py`, the no-args dispatch rule, the exit-code table — is already in place; those three issues add commands and UI on top of it, not new foundations.

Issue #32 (done) lands `ansina-tui auth`: `login`/`status`/`logout`/`sudo`/`token mint|list|revoke` — see Layer 2's `tui/` entry for the mechanics (`session.py`, `secret_input.py`, `failures.py`, `commands/auth/`). #32 was written before #28 landed, so its scope was adjusted in four ways #28 made necessary rather than optional: (1) the bootstrap identity's `POST`/`DELETE /auth/me/tokens` 403 (`ansina.auth.bootstrap_identity`) gets a client-side recognized message naming the real fix, since it's the first thing anyone hits minting with the bootstrap token — no daemon change; (2) a user can hold many tokens (#28), so `auth token revoke` needed a way to detect revoking the credential currently in use — `HostEntry.token_id`, set on `mint`; (3) `auth token list`'s `last_used_at` is documented as coalesced, not exact, matching #28's `token_last_used_resolution_seconds`; (4) `auth token mint`/`revoke` is documented as the configured admin's actual credential-rotation recipe, not just a convenience. `auth status` makes a live `GET /auth/me` (no cache fallback — unreachable exits 5 like every other command), and `commands/status.py` was refactored onto the new `session.py` layer so both share one credential-resolution path and one test seam.

Issue #33 (done) lands `ansina-tui api`, the raw REST wrapper — see Layer 2's `tui/` entry for the mechanics (`client.py`'s `content=`/`headers=`/`RESERVED_HEADERS`, `output.py`'s `Emitter.body`, `commands/api.py`). It is why M4 ships only three CLI commands (`status`, `auth`, `api`) without leaving anything unreachable: every route family — `health`, `version`, `openapi`, `heart`, `auth/*`, `me/*` — goes through the same command with no per-route special-casing, so a route a later milestone adds is reachable the day it merges. It is also the milestone's CI/CD surface, which is why a sensitive `auth.*` route with no live sudo grant fails fast (403 `ansina.auth.sudo_required` → the `auth sudo` hint, exit 4) rather than ever prompting mid-request — dedicated `heart`/`user`/`group`/`role` subcommands are deliberately deferred, since everything is already reachable here. Both dependencies (#31, #32) were already closed when #33 landed, so it needed no new foundation — only the two additive `client.py`/`output.py` extensions above.

Issue #34 (done) is the last code issue in M4 (#35 is docs-only) and lands the TUI shell + Overview tab — bare `ansina-tui` on a TTY now opens a `TabbedContent` with one working tab instead of #31's placeholder status line. See Layer 2's `tui/` entry for the mechanics (`daemon_state.py`, `ui/tabs.py`, `ui/overview.py`).
