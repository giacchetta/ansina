# 🏛️ Local Architecture Blueprint

## Layer 1: Foundations
- **Repository Purpose**: Ansina is a self-owned AI agent exposing a single internal REST API — no chat channels — built around a small always-on "Heart" model (in-process, ≤4B/8k-ctx) and a large remote "Brain" model (35B+) for actual reasoning.
- **Tech Stack**: Python ≥ 3.14 / FastAPI / SQLite. Embedded inference in-process via MLX (the only `HeartRuntime` adapter shipped so far, Apple-Silicon-only); a portable, non-Apple-Silicon fallback (originally scoped as llama-cpp-python) is deferred to a follow-up issue — see Layer 5. See `docs/architecture/blueprint.md` for the full rationale and the OpenClaw comparison this design departs from.

## Layer 2: Directory Layout
- `Makefile`: dev-workflow entry point — bootstraps `uv` (Astral installer, macOS/Linux) if missing, wraps `sync`/`lint`/`format`/`typecheck`/`test`/`check`/`clean`.
- `src/ansina/`: Core application source code (src-layout package, `py.typed` marker for downstream type-checking).
- `src/ansina/__main__.py`: Process entry point (`python -m ansina` / the `ansina` console script). Loads config, configures logging, builds the app via `create_app()`, hands it to uvicorn.
- `src/ansina/api/`: REST API surface (issue #4). `create_app()` in `api/app.py` is the FastAPI factory. `api/middleware.py` assigns/echoes the request id and feeds `logging`'s correlation-id contextvar. `api/auth.py` (issue #5, redesigned by #24, its chain formalized by #25, extended by #26) enforces a bearer token, deny-by-default — every route needs one except `PUBLIC_PATHS` (`/healthz`, `/readyz`). `BearerAuthMiddleware` walks an `Authenticator` chain (`auth.authenticator.build_authenticators`, injectable via its own `authenticators` constructor param so a follow-up milestone's OIDC authenticator is an append, not a rewrite) rather than a comparison against one static config secret, resolving a full `auth.principal.Principal` (user + every role reachable direct-or-via-group) onto `request.state.principal` — offloaded via `anyio.to_thread.run_sync` so the blocking sqlite scan + per-row hash comparison never stalls the event loop. An inactive user's token stops authenticating (`auth.authenticator.resolve_principal`'s own check — `find_user_by_api_token` itself doesn't filter on `users.active`). `security.enabled = False` (not "no token configured" — that now means "auto-generate one") is the only way to disable enforcement, and `config.settings` refuses to boot at all if that's paired with a non-loopback bind. Once a `Principal` is resolved, an `X-Sudo-Token` header (issue #26) is additionally checked against `app.state.sudo` (`auth.sudo.SudoService`) and, on a live match, elevates it via `Principal.with_sudo()` — an absent/expired/wrong/revoked grant never turns into a 401 by itself, it just fails to elevate, leaving a sensitive route's own 403 `CODE_SUDO_REQUIRED` as the only signal. `api/authorization.py`'s `require(resource, *, sensitive=False)` (issue #25) is the FastAPI dependency every non-public route declares — the verb is read from `request.method`, not declared per-route — answering "does the caller's `Principal` hold a role with a `role_permissions` row for (this resource, this verb)" via `auth.authorization.authorize()`, offloaded the same way; denial raises `ForbiddenError`/`SudoRequiredError` (403, `CODE_FORBIDDEN`/`CODE_SUDO_REQUIRED`), distinguishable from `BearerAuthMiddleware`'s 401 (`CODE_UNAUTHORIZED`, no/invalid identity) without leaking which credential component was wrong; every decision (granted or denied) is audit-logged with actor/resource/verb. `api/route_audit.py`'s `audit_route_coverage()` (issue #25) walks `app.routes` at `create_app()` time and raises `RouteCoverageError` — same "fail loudly before uvicorn binds a port" pattern as `HeartUnavailableError` — if any non-public route lacks exactly one `require(...)` declaration; its surviving declarations are also the `resources` catalog's entire source (replacing #24's `BOOTSTRAP_RESOURCES` seed constant, since deleted). `api/problems.py` + `api/exception_handlers.py` map every error door (`AnsinaError`, HTTP errors, validation errors, unhandled exceptions) to RFC 9457 `application/problem+json`. `api/readiness.py` is a named-check registry backing `GET /readyz`; later milestones register their own checks there instead of editing the route. `api/routes/health.py` holds the M0 routes: `/healthz`, `/readyz`, `/version` (`GET /version` gated `require("system.version")`). `api/routes/heart.py` (issue #11) holds Ansina's first non-health, non-public routes: `GET /heart/tick` (status), `POST /heart/tick/pause`/`/resume` (the tick loop's kill switch) — all gated `require("heart.tick")`, and all return 503 `problem+json` (`CODE_HEART_DISABLED`) when `app.state.tick_loop` is `None` (only once authorization already passed — a caller without a grant gets 403 without ever learning whether the Heart is even enabled). `api/routes/openapi.py` (issue #25) serves `GET /openapi.json` behind `require("system.openapi")` as a real, gated `APIRoute` — `create_app` passes `openapi_url=None, docs_url=None, redoc_url=None` to the `FastAPI` constructor, since the framework's default `/docs`/`/redoc`/`/docs/oauth2-redirect` are plain Starlette routes that can't carry a `require(...)` declaration (and are non-functional with auth enabled anyway — no `fastapi.security` scheme is declared for Swagger UI's "Authorize" button, since auth here is middleware-level). `api/routes/sudo.py` (issue #26) holds `POST /auth/sudo` (step up via `app.state.sudo.step_up()`, gated `require("auth.sudo")`), `DELETE /auth/sudo` (revoke your own grant, same resource), and the break-glass `DELETE /auth/sudo/grants` (revoke every active grant, gated `require("auth.sudo.grants", sensitive=True)` — reaching it already requires a live grant); all three are `auth.*` resources so `auth.policy.permitted_verbs` restricts them to Maintain/Admin with no policy change. `api/routes/users.py`/`groups.py`/`role_assignments.py`/`roles.py`/`permissions.py` (issue #27) round out the RBAC management surface Users/Groups/Roles the rest of M2 exists to protect. `users.py` (`GET`/`POST /auth/users`, `GET`/`PATCH`/`DELETE /auth/users/{id}`, `PUT /auth/users/{id}/password`, `POST /auth/users/{id}/tokens`) and `groups.py` (`GET`/`POST /auth/groups`, `GET`/`PATCH`/`DELETE /auth/groups/{id}`, `PUT`/`DELETE /auth/groups/{id}/members/{user_id}`) each gate `GET` `sensitive=False` and every mutation `sensitive=True` on one resource (`auth.users`/`auth.groups` respectively); `DELETE /auth/users/{id}` is a one-way tombstone (`UserRepository.soft_delete`), never a row removal. `role_assignments.py` holds the four nested attach/detach routes (`POST`/`DELETE /auth/users/{id}/roles/{role_id}` and the `/auth/groups/...` equivalent, resource `auth.role_assignments`, always `sensitive=True`) and additionally runs every assignment through `auth.management.assert_may_assign_role` (skipped only when `security.enabled = False` leaves no resolved `Principal` to check against). `roles.py`/`permissions.py` are the read-only discovery pair: `GET /auth/roles` (every role with its current `role_permissions` grants — no create/update/delete route exists, by omission not by a stub that 403s) and `GET /auth/permissions` (the `resources` catalog crossed with every `Verb` — the full grantable space a future custom-role editor needs).
- `src/ansina/config/`: Typed `Settings` (pydantic-settings). Layering: defaults → `ansina.toml` → `ANSINA_*` env vars. Load via `load_settings()`, never `os.getenv()` directly. Secrets are env-only — a `SecretStr` field set in the TOML file is a startup error. `database.path` is normalized (`~` expanded, relative paths resolved against CWD) by a `field_validator`, so every consumer sees one already-absolute path regardless of how it was configured.
- `ansina.example.toml`: documents the config file shape; copy to `ansina.toml` (gitignored) to use.
- `src/ansina/errors.py`: `AnsinaError` base exception with a stable, machine-readable `code` (`ClassVar[str]`); every subclass must declare its own `code` or class creation raises. `ansina.config.ConfigError` and `ansina.errors.StorageError` subclass it.
- `src/ansina/storage/`: SQLite persistence foundation (issue #6). `database.py`'s `Database` hands out one connection per thread (`threading.local`) rather than a single shared connection — sub-agents (later milestone) will read this database concurrently, and WAL lets those reads proceed unblocked by the writer; writes still serialize, per SQLite. Every connection gets `PRAGMA foreign_keys=ON` (per-connection state) and `PRAGMA busy_timeout` (so a second writer retries instead of failing instantly); `PRAGMA journal_mode=WAL` is per-database and verified once at `connect()`. `migrator.py`'s `run_migrations()` is a forward-only runner backed by a `schema_version` table, rejecting out-of-order or skipped versions; migrations themselves are plain numbered `.sql` files under `storage/migrations/`: `0001_init.sql` creates `schema_version` (no domain tables in M0); `0002_rbac.sql` (issue #24) adds the RBAC identity/permission schema — `roles`, `resources`, `role_permissions`, `users`, `"groups"` (always quoted — `GROUPS` is a SQLite keyword), `user_groups`, `role_assignments`, `credentials`, `external_identities`, `role_mappings`; `0003_sudo.sql` (issue #26) adds `sudo_grants` (one active grant per user, hash/salt never the raw token) and `sudo_lockouts` (at most one row per user, driven entirely by caller-supplied timestamps from an injectable clock — never a SQL-side `now`); `0004_user_tombstone.sql` (issue #27) adds `users.deleted_at` — a one-way marker distinct from `active`'s suspend/resume flag, set once by `UserRepository.soft_delete` and never cleared by any route. Both `Database` and `run_migrations()` are driven from `api/app.py`'s lifespan, never called ad hoc elsewhere.
- `src/ansina/auth/` (issue #24, extended by #25, #27): the RBAC identity & permission domain layer — data + repositories + the authorization decision itself; the HTTP routes built on top of it live in `api/routes/{sudo,users,groups,role_assignments,roles,permissions}.py`, described in Layer 2's `api/` entry above. Permissions are rows, not an enum: every authorization check is a `role_permissions` lookup for (a role, a resource, a verb), so a future admin-defined custom role is an `INSERT`, not a rewrite. `models.py` holds one frozen dataclass per table (each with a `from_row(sqlite3.Row)` classmethod) plus the `StrEnum`s (`Verb`, `RoleSlug`, `SubjectType`, `CredentialType`) that constrain them — `User.deleted_at` (issue #27) is the one-way tombstone marker, distinct from `active`'s suspend/resume flag. `hashing.py` ships two deliberately different credential-hashing paths: passwords use argon2id (`Argon2Params`, tuned via `[security.password]`) because a stolen hash must stay expensive to brute-force; API tokens use per-row-salted SHA-256 + `hmac.compare_digest` because `api/auth.py`'s middleware verifies one on every authenticated request, and argon2's deliberate work factor has no payoff against a high-entropy machine secret. `policy.py`'s `permitted_verbs()` is the *one* place the fixed builtin-role policy is expressed (Read=GET; Write=+POST/PUT/PATCH; Maintain/Admin=all verbs; any `auth.*` resource=Maintain/Admin only); its `BOOTSTRAP_RESOURCES` seed constant is gone as of #25 — `api/route_audit.py`'s real `app.routes` walk is now the `resources` catalog's only source, without changing `reconciler.py`'s `sync_resources()` contract. `repositories.py` is the first domain repository in the codebase, built directly on `Database.connection()`/`Database.transaction()` (no ORM) — `UserRepository.create()` structurally guarantees the "every M2 user gets exactly one `provider="local"` `external_identities` row" invariant in the same transaction (skippable via `local_identity=False` for the one caller that provides its own, `auth.bootstrap`); `RoleRepository` refuses to delete or demote a `builtin=1` role. `reconciler.py` seeds the four builtin roles and reconciles their `role_permissions` grants against the catalog at every boot, scoped to `builtin=1` roles only — a custom role's grants are never touched. `bootstrap.py`'s `ensure_bootstrap_admin()` provisions a single synthetic Admin identity on first boot with zero users (its own `provider="local-bootstrap"` `external_identities` row — the one deliberate exception to the "local" rule), sourced one of two ways: no `security.api_token` configured (the recommended path) generates a high-entropy token, prints it to stdout **exactly once** via a plain `print(..., flush=True)` that deliberately bypasses `logging` (never redacted-into-`***`, never captured by log aggregation), and stores only its hash — stable across restarts, never silently rotated, and also registered with `logging.redaction` as defense in depth even though nothing is designed to log it; an explicit `security.api_token` override is instead re-synced onto the credential on *every* boot, which is what makes rotating `ANSINA_SECURITY__API_TOKEN` take effect. `security.bootstrap_admin_enabled=false` revokes the credential either way while keeping the user/identity for audit attribution. `principal.py` (issue #25, extended by #26) holds `Principal` (resolved user + role ids/slugs + `auth_method` + `sudo_active`/`sudo_grant_id`) and `AuthMethod`; `with_sudo(grant_id)` returns an elevated copy, the one place `sudo_active` ever becomes `True`. `authenticator.py` (issue #25) formalizes #24's inline DB-backed lookup behind a real `Authenticator` `Protocol` — `ApiTokenAuthenticator` wraps `CredentialRepository.find_user_by_api_token` unchanged, `build_authenticators()` returns the chain `api/auth.py`'s middleware walks, and `resolve_principal()` fills a `Principal`'s roles from `RoleAssignmentRepository.roles_for_user()`, rejecting an inactive or (issue #27) tombstoned (`deleted_at is not None`) user. `authorization.py` (issue #25) is `authorize(db, principal, resource, verb, *, sensitive=False)`, the pure decision `api/authorization.py`'s `require()` dependency wraps: `ForbiddenError` (no role grants the verb) is checked before `SudoRequiredError` (right role, `maintain`-not-`admin`, no live sudo grant on a `sensitive=True` resource) — the latter is live as of #26. `step_up.py` (issue #26) is the pluggable `StepUpVerifier` `Protocol` (`verify(principal, payload) -> bool`) behind `POST /auth/sudo` — `PasswordStepUpVerifier` (M2's only implementation) re-checks a `payload["password"]` against `CredentialRepository.verify_password`; `StepUpRegistry.for_principal()` resolves which verifier applies (fixed to the one configured verifier in M2, a per-user choice in a follow-up milestone) without `auth.sudo` ever naming a concrete verifier. `sudo.py` (issue #26) is `SudoService` — issuance (`step_up()`, minting a `secrets.token_urlsafe` grant via `SudoGrantRepository`), the read side `BearerAuthMiddleware` calls (`resolve()`), revocation (`revoke_for_user()`/`revoke_all()`), and the failed-attempt lockout (`SudoLockoutRepository`-backed, `[security.sudo] max_failed_attempts` consecutive failures within `attempt_window_seconds` locks out for `lockout_seconds`, raising `SudoLockedOutError` mapped to 429 with a real `Retry-After` header) — driven by an injectable clock throughout, so TTL/lockout expiry is tested without real sleeping. `management.py` (issue #27) holds the two server-side guards the management routes need beyond `authorize()` itself, pure domain logic mirroring how `authorization.py` sits under `api/authorization.py`: `assert_may_assign_role()` (a caller can never grant a `role_permissions` row it does not itself effectively hold — the `admin` role and any `auth.*`-granting role are checked directly first, since `Maintain`/`Admin` hold identical grants under M2's fixed policy and a bare subset check alone wouldn't catch a sudo'd `Maintain` minting a fresh `Admin`; the general case is a subset-of-grants check, so it keeps working unchanged once non-builtin roles exist) and `assert_admin_remains()` (refuses — `LastAdminError`, 409 — to leave zero active, non-deleted holders of the `admin` role; called from every route that deletes, deactivates, or demotes a user, directly or via a group). `repositories.py` gained, for issue #27: `UserRepository.soft_delete()` (the one-way purge — credentials, role assignments, group memberships, sudo grants, all in one transaction, keeping only the `users` row and its identity for audit attribution) and `.set_display_name()`; `GroupRepository.update()`/`.delete()` (also explicitly clears the group's `role_assignments`, since `subject_id` there is deliberately not a foreign key)/`.remove_member()`/`.list_members()`/`.groups_for_user()`; `RoleAssignmentRepository.list_for_subject()` (direct-only, unlike `roles_for_user`'s group-following union) and `.user_ids_with_role()` (the inverse union query, filtered to active/non-deleted — backs `assert_admin_remains`); `RolePermissionRepository.grants_for_roles()` (the whole `(resource, verb)` grant set for a set of roles, not scoped to one resource like `effective_verbs` — backs `assert_may_assign_role`).
- `src/ansina/logging/`: JSON structured logging via `logging.config.dictConfig`. Redaction runs inside `JsonFormatter`, not at call sites — never bypass it by formatting log strings yourself. Request/correlation ids via `contextvars` (`request_id_scope()`). Boot with `configure_logging(load_settings())`, then use `get_logger(__name__)` everywhere else, never bare `logging.getLogger()`.
- `src/ansina/heart/` (issue #10): the in-process Heart runtime. `runtime.py`'s `HeartRuntime` is a structural `Protocol` (`load`/`generate`/`token_count`/`unload`/`is_healthy`) plus `BaseHeartRuntime`, an ABC owning the loaded-state guard and the 8k context-budget refusal shared by every adapter — subclasses only implement four `_*` backend hooks. `models.py`'s `resolve_model()` resolves an explicit `[heart] model_path` (wins, no network) or downloads `model_repo` from Hugging Face into `cache_dir` (download-once cache); `selection.py`'s `build_heart_runtime()` is the capability probe — MLX is viable only on `darwin`/`arm64` with `mlx_lm` importable (import success alone isn't enough: `mlx` also ships manylinux wheels), and any other host gets a loud `HeartUnavailableError`, never a silent fallback. `adapters/mlx.py` is the only adapter shipped — a second, non-Apple-Silicon adapter is deferred to a follow-up issue (no llama-cpp-python-compatible GPU was available to prove it against). Every backend import (`mlx_lm`, `huggingface_hub`) happens inside function bodies, never at module scope, so `ansina.heart` stays importable without the optional `ansina[mlx]` extra installed. `[heart] enabled` defaults to `false` — off, none of this runs.
- `src/ansina/heart/tick/` (issue #11): the autonomic tick loop, the Heart's one day-one duty and the first caller of `HeartRuntime.generate()`. `loop.py`'s `TickLoop` schedules `tick_once()` on a fixed cadence (`start + n*interval`, recomputed each cycle so a slow tick can't drift future ticks or burst-fire missed slots — see `_next_tick_number`), guarded against overlap by an in-flight flag, with `pause()`/`resume()` as the kill switch and any tick exception logged and swallowed so one failure can't end the loop. `snapshot.py` builds the bounded prompt: a `StateSnapshotSource` `Protocol` (structural, like `HeartRuntime`) contributes `SnapshotItem`s, and `build_prompt()` measures with the runtime's own `token_count` and drops lowest-priority items until the prompt fits `context_tokens - max_output_tokens` — enforced before `generate()` is ever called, not left to `HeartContextOverflowError` as the mechanism. No source is registered yet (no pending-work/schedule/event domain exists — `storage/` ships only `schema_version`); a later issue registers one the same way milestones register a `Readiness` check. `decision.py`'s `parse_decision()` turns the Heart's raw reply into `TickDecision.IDLE/ACT/ESCALATE`, defaulting to `IDLE` on anything unparseable. `act` and `escalate` both dispatch through a `DecisionHandler` `Protocol`; the shipped `LoggingDecisionHandler` only logs — there is nothing to act on yet, and although `BrainProvider` now exists (issue #12, `src/ansina/brain/`), nothing wires `escalate` to it yet — that hand-off is a follow-up issue, not part of #12's scope. `[heart.tick] enabled` defaults to `true` but is inert unless `[heart] enabled` is also `true`.
- `src/ansina/brain/` (issue #12): the remote Brain provider port — no in-process backend to guard, unlike `heart/`, but the same shape: a structural `Protocol` (`provider.py`'s `BrainProvider`, `stream`/`aclose`) plus a `BaseBrainProvider` ABC owning invariants every adapter shares. The load-bearing one, taken from OpenClaw (`docs/architecture/blueprint.md` §1): `stream()` returns synchronously (a plain method, not `async def`) and **never throws after invocation** — every failure arrives as a terminal `BrainErrorEvent` (`events.py`), never a raised exception into the caller's `async for`; only construction/selection-time failures raise (`BrainUnavailableError`). `BaseBrainProvider` also owns bounded retry (`retry.py`'s `backoff_seconds`, capped exponential backoff) — retried only while no `BrainTextDelta` has reached the caller yet, and only for a `RETRYABLE_ERROR_CLASSES`-classified failure — and explicit generator cleanup (`gen.aclose()` in a `finally`) so a caller cancelling mid-stream closes the adapter's in-flight HTTP request promptly rather than waiting on GC. `adapters/openai_compat.py`'s `OpenAICompatibleBrainProvider` is the only adapter shipped, working against any OpenAI-compatible chat-completions endpoint; `classify_openai_error()` maps the SDK's exception hierarchy to `BrainErrorClass`, and token/cost accounting (`BrainUsage`) is authoritative when the provider's own usage totals arrive, else an estimated (non-authoritative) char-based fallback. `selection.py`'s `build_brain_provider()` refuses to build (`BrainUnavailableError`) a keyless request against the *default* OpenAI host — a keyless custom `base_url` (a local OpenAI-compatible server) is left alone. Nothing calls `stream()` yet: wiring the tick loop's `escalate` branch to this port is a follow-up issue, not part of #12.
- `tests/conftest.py`: suite-wide fixture root above the `unit/`/`e2e/` split. `tests/unit/`: mirrors `src/ansina/` 1:1 (issue #16), e.g. `api/routes/test_health.py` for `api/routes/health.py` — every module gets its own test module, coverage held at 100% (`pyproject.toml`'s `[tool.coverage.report] fail_under = 100`), never just incidental coverage through a higher-level test. `tests/e2e/`: black-box, launches `python -m ansina` as a subprocess, run with `--no-cov` (a boot gate, not a coverage source).
- `README.md`: human front door — quick start, API table, links to `docs/`. `docs/architecture/`: `blueprint.md` — architecture rationale and roadmap.
- `.agents/`: Synced central prompts, guardrails, and protocols. Gitignored — never committed here, re-synced locally by `.githooks/sync.sh` (see below).
- `.githooks/`: `post-merge` hook runs `sync.sh`, which re-pulls `.agents/` from the central hub repo (`giacchetta/lead-agentic-ai-coding`) after every merge.
- `.github/workflows/ci.yml`: CI gate (issue #7) — `check` (ruff / ruff-format / mypy --strict / `pytest tests/unit`) then `e2e` (`needs: check`), both on `ubuntu-24.04` × `macos-26` (Apple Silicon, mirroring the M4 deployment target; the arm64 leg is required, not optional), Python 3.14 via `uv sync --locked --all-groups`. `.pre-commit-config.yaml` runs the identical checks through `uv run`, so the pinned tool versions come from `uv.lock` for both — never pin a linter separately in the pre-commit config.
- `.github/workflows/post-on-merge.yml`: thin caller into a reusable pipeline hosted in `giacchetta/giacchetta.github.io`; this repo owns only the trigger and the `merged == true` gate, all generation logic lives upstream.

## Layer 3: Data Flow & Entry Points
- Entry points: `python -m ansina` and the `ansina` console script (`[project.scripts]`), both resolving to `src/ansina/__main__.py:main`.
- Boot sequence: `load_settings()` → `configure_logging(settings)` → `create_app(settings)` (`src/ansina/api/app.py`) → `uvicorn.run(...)`. A `ConfigError` during boot prints the aggregated report to stderr and exits non-zero, never a traceback. `load_settings()` itself refuses to construct `Settings` (issue #5, updated by #24) when `server.host` isn't loopback and `security.enabled` is `False` — that invariant is unbypassable since it lives on `Settings`, not in `create_app`; `api_token` being unset no longer factors in (issue #24 makes it optional even with auth enabled — Ansina generates its own bootstrap token instead). `api_token`, when set, must itself look securely generated: `_TOKEN_MIN_LENGTH` (32), `_TOKEN_CHARSET` (base64url only, so a human-typed phrase is rejected outright), `_TOKEN_MIN_ENTROPY_BITS_PER_CHAR` (2.5, a best-effort predictability deterrent, not a cryptographic guarantee) all in `config/settings.py`. After every router is included, `create_app` calls `api/route_audit.py`'s `audit_route_coverage(app)` (issue #25) — a `RouteCoverageError` there aborts boot the same "fail loudly before uvicorn binds a port" way a `ConfigError` does — and stashes its returned `ResourceSpec`s on `app.state.resource_specs`. `create_app`'s FastAPI `lifespan` opens the `Database` and runs `run_migrations()` on startup (a `MigrationError` there aborts boot the same way), then — issue #24, in this fixed order because each step depends on the last — `sync_resources()` catalogs `app.state.resource_specs` (issue #24 seeded this from a hand-written constant; #25 replaced that argument with the route audit's real walk, `sync_resources()`'s own contract unchanged), `reconcile_builtin_roles()` grants the four builtin roles against that catalog, and `ensure_bootstrap_admin()` provisions the synthetic Admin identity (see `src/ansina/auth/` below for its two credential-sourcing paths); an `AuthError` from any of the three aborts boot the same way. `Database` is closed on shutdown; `Readiness` gets a `"database"` check backed by `Database.is_healthy()` (no dedicated `/readyz` check for the RBAC seeding — `database` already covers its only failure mode). When `[heart] enabled` is true, `create_app` calls `build_heart_runtime()` *before* the lifespan even starts — a `HeartUnavailableError` (issue #10) surfaces the same way a `ConfigError` does, before uvicorn ever binds a port; the lifespan then loads the model and registers a `"heart"` readiness check, unloading it on shutdown alongside the database close. When disabled (the default), `app.state.heart` is `None` and `/readyz` carries no `heart` key at all. When the Heart is also enabled and `[heart.tick] enabled` is true (issue #11, its own default), `create_app` builds a `TickLoop` (`build_tick_loop`) the same way, and the lifespan `start()`s it after `heart.load()` and registers a `"heart_tick"` readiness check, `stop()`ing it on shutdown before `heart.unload()`. `app.state.tick_loop` is `None` unless both flags are true. When `[brain] enabled` is true (issue #12, independent of `[heart] enabled`), `create_app` calls `build_brain_provider()` the same "fail loudly before uvicorn binds a port" way (`BrainUnavailableError`); the lifespan `await`s `brain.aclose()` on shutdown alongside `heart.unload()`/`db.close()`. `app.state.brain` is `None` when disabled. No `/readyz` check is registered for it — the only meaningful liveness signal for a remote provider is a real network round-trip, and paying for one on every `/readyz` poll is the wrong trade.
- Request flow: `RequestIdMiddleware` (outermost) binds/echoes a request id (feeding `logging`'s correlation-id contextvar) → `BearerAuthMiddleware` (401 `problem+json` if the route isn't in `PUBLIC_PATHS` and the bearer token doesn't resolve a `Principal` through the `Authenticator` chain; issue #26: a resolved `Principal` carrying a live `X-Sudo-Token` is additionally elevated here) → the route's `require(resource)` dependency (403 `problem+json` if the resolved `Principal` holds no role granting `request.method` on that resource — issue #25, dev mode/`security.enabled=False` skips this too; 403 `CODE_SUDO_REQUIRED` if the resource is `sensitive=True`, the role is `maintain`-not-`admin`, and no elevation happened above) → route → response, or an exception mapped to `application/problem+json` by the handlers in `api/exception_handlers.py`. The `auth.*` management routes (issue #27) split `sensitive` by verb on the same resource rather than per-route: `GET /auth/users`/`/auth/groups`/`/auth/roles`/`/auth/permissions` are `sensitive=False` (Maintain reaches them with no grant), every mutating verb on `auth.users`/`auth.groups`/`auth.role_assignments` is `sensitive=True`.

## Layer 4: External Integrations
- **SQLite** (`src/ansina/storage/`, issue #6): the only runtime dependency in M0. One file on disk, WAL journal mode, path set via `[database] path` / `ANSINA_DATABASE__PATH` (defaults to `./ansina.db`; WAL adds `-wal`/`-shm` sidecars next to it). No network service, no separate process.
- **argon2-cffi** (`src/ansina/auth/hashing.py`, issue #24): a *base* dependency, not an optional extra — same reasoning as `openai` above: auth is not optional, and both CI legs must exercise password hashing. Ships prebuilt wheels for macos-arm64 and linux-x86_64, so neither CI leg compiles from source.
- **MLX / Hugging Face** (`src/ansina/heart/`, issue #10): optional — the `ansina[mlx]` extra (`mlx-lm`, `huggingface-hub`), not a base dependency, and never installed in CI (both legs run with the Heart disabled). Apple-Silicon-only; a HF repo id is fetched into a local on-disk cache on first use (`[heart] cache_dir`) and reused after.
- **OpenAI-compatible endpoint** (`src/ansina/brain/`, issue #12): the `openai` SDK is a *base* dependency (unlike `ansina[mlx]` above) — pure Python, installs and is exercised on every CI leg, since the Brain being off by default (`[brain] enabled = false`) is a config default, not a platform constraint. Works against any endpoint speaking the OpenAI chat-completions protocol (OpenAI itself, an Anthropic-via-compat-shim, OpenRouter, a self-hosted server), configured via `[brain] base_url`/`api_key`/`model` — never hardcoded to one vendor. `api_key` is env-only (`ANSINA_BRAIN__API_KEY`), same as `security.api_token`.
- **Cross-repo CI pipeline** (`.github/workflows/post-on-merge.yml`): CI-time only, not a runtime dependency. Calls a reusable workflow in `giacchetta/giacchetta.github.io` on every merged PR to generate a blog post; this repo passes PR/issue read access plus two secrets and owns no generation logic itself.

## Layer 5: Domain Blueprint
- **Heart** (≤4B, 8k ctx, in-process): owns the autonomic tick loop only — decide idle / act / escalate. Never answers user requests directly. Every prompt built for it must fit its 8k window; treat that as a hard constraint, not a target. The runtime port + MLX adapter (issue #10, `src/ansina/heart/`) and the tick loop (issue #11, `src/ansina/heart/tick/`) are wired into `create_app`'s lifespan; `TickLoop` is the first and only caller of `generate()`. Its snapshot has no real content yet (no pending-work/schedule/event domain exists), `act` has nothing to act on, and `escalate` — although `BrainProvider` now exists (issue #12) and is wired into `create_app` alongside it — still has no hand-off wired to it; all three remain injected seams with log-only defaults, not implemented behavior, until a follow-up issue connects `escalate` to `BrainProvider.stream()`.
- A portable, non-Apple-Silicon `HeartRuntime` adapter (originally scoped as llama-cpp-python in issue #10) is **deferred to a follow-up issue**: the only non-Apple hardware available at the time had no llama-cpp-python-compatible GPU, so an adapter there was unprovable and was cut rather than shipped untested. Until that lands, a non-Apple-Silicon host with `[heart] enabled = true` fails loudly at boot (`HeartUnavailableError`) rather than silently degrading.
- **Brain** (35B+, remote via `BrainProvider` port): owns all real reasoning. The Heart never replaces it or bypasses it for substantive answers. The port + its OpenAI-compatible adapter (issue #12, `src/ansina/brain/`) are implemented and wired into `create_app`'s lifespan the same way the Heart is, gated by `[brain] enabled` independently of `[heart] enabled` — but nothing calls `BrainProvider.stream()` yet; a local 35B adapter and multi-provider routing/fallback chains are explicitly out of scope, deferred the same "unprovable on hardware at hand" way the llama-cpp-python fallback above was.
- Three additional Heart duties (request triage, context curation, structured extraction) are **deliberately not implemented**. Prior embedded-model attempts produced low-quality output — each duty is a gated experiment (`Backlog — Experiments` milestone) requiring a benchmark win over a stated baseline before adoption. Do not fold this logic into the tick loop without that gate passing.
- No channel concept anywhere (no Discord/WhatsApp/etc., and no `ChannelId`-shaped abstraction either) — see `docs/architecture/blueprint.md` §2 for why this is refused deliberately, not an oversight.
- Primary deployment target is a Mac Mini (Apple M4, 16 GB unified memory) — adapter and performance decisions prioritize that hardware, not the local dev machine.
- **RBAC identity & access control** (M2 milestone, complete — `src/ansina/auth/` + `api/authorization.py`/`api/route_audit.py`/`api/routes/{sudo,users,groups,role_assignments,roles,permissions}.py`): replaces #5's one-shared-secret model with real `User`/`Group` identity and a permission model keyed on data, not code — "is there a `role_permissions` row granting (a role, a resource, a verb)?" is the entire authorization question, for both builtin and (future) admin-defined roles. Issue #24 shipped the data model, hashing, the builtin-role reconciler, and — pulled forward from #25's original scope, since the alternative was an unauthenticatable server (an auto-generated bootstrap token, by design, is never in config for a static comparison to check) — `api/auth.py`'s DB-backed bearer-token verification. Issue #25 built the rest on top: a formal `Authenticator` chain (`auth.authenticator`, formalizing #24's inline lookup — pluggable, an OIDC authenticator is a future append, not a rewrite), the request-scoped `Principal`, the `require(resource)` authorization dependency (403 on no matching `role_permissions` row, distinguishable from `BearerAuthMiddleware`'s 401 without leaking which credential component was wrong), and the mandatory startup route-coverage audit that also became the `resources` catalog's real source (replacing #24's `BOOTSTRAP_RESOURCES` seed, since deleted) — retrofitted onto every existing route (`system.version`, `heart.tick`, and #25's own `system.openapi`). Issue #26 shipped sudo step-up for `Maintain` on sensitive `auth.*` actions: a pluggable `StepUpVerifier` port (`auth.step_up`, one password implementation in M2) behind `POST /auth/sudo`, grant issuance/TTL/revocation/lockout in `auth.sudo.SudoService` (verifier-agnostic — a follow-up milestone's second verifier is a new `StepUpVerifier`, not a rewrite), elevation via `BearerAuthMiddleware` reading `X-Sudo-Token`, and the break-glass `DELETE /auth/sudo/grants` — the first route to actually pass `sensitive=True`, proving `authorize()`'s `SudoRequiredError` branch end to end before #27 (Users/Groups/Roles management, the routes this mechanism actually exists for) had landed. Issue #27 (done) closes the milestone: Users/Groups/Roles management over the REST API itself (`api/routes/users.py`/`groups.py`/`role_assignments.py`/`roles.py`/`permissions.py`), `Admin`/`Maintain` only with every mutation sudo-gated for `Maintain` — the first routes to declare an `auth.*` resource beyond `auth.sudo`/`auth.sudo.grants`, and the first to make that sudo gate protect something other than a break-glass route. Two guards in `auth.management` (`assert_may_assign_role`, `assert_admin_remains`) enforce server-side, not just documented, that no caller can grant a permission it doesn't itself hold and that the last `Admin` can never be removed; `DELETE /auth/users/{id}` is a one-way tombstone (`0004_user_tombstone.sql`'s `users.deleted_at`), never a row removal. `GET /auth/roles`/`GET /auth/permissions` are read-only discovery — no role write route exists in M2. Custom admin-defined roles and any external identity provider are explicitly out of scope for the whole M2 milestone, deferred to a follow-up that adds rows to #24's tables rather than reworking them.
