# 🏛️ Local Architecture Blueprint

## Layer 1: Foundations
- **Repository Purpose**: Ansina is a self-owned AI agent exposing a single internal REST API — no chat channels — built around a small always-on "Heart" model (in-process, ≤4B/8k-ctx) and a large remote "Brain" model (35B+) for actual reasoning.
- **Tech Stack**: Python ≥ 3.14 / FastAPI / SQLite. Embedded inference in-process via MLX (the only `HeartRuntime` adapter shipped so far, Apple-Silicon-only); a portable, non-Apple-Silicon fallback (originally scoped as llama-cpp-python) is deferred to a follow-up issue — see Layer 5. See `docs/architecture/blueprint.md` for the full rationale and the OpenClaw comparison this design departs from.

## Layer 2: Directory Layout
- `Makefile`: dev-workflow entry point — bootstraps `uv` (Astral installer, macOS/Linux) if missing, wraps `sync`/`lint`/`format`/`typecheck`/`test`/`check`/`clean` for the daemon, plus a parallel `tui-*` set (`tui-sync`/`tui-lint`/`tui-format`/`tui-typecheck`/`tui-test`/`tui-check`, issue #31) for the standalone `tui/` project below — `check`/`tui-check` stay independent so `check` keeps mirroring the `check` CI job exactly; `check-all` runs both. `heart-bench` (issue #53, Mac-only — no MLX adapter is viable on either CI leg) wraps `uv run --extra mlx python -m ansina.heart.eval $(ARGS)`, deliberately excluded from `check`/`check-all` the same way. `heart-bench-sync`/`remote-heart`/`remote-heart-tail`/`remote-heart-attach` (issue #58) are the real-hardware-bench driver's Make surface — `remote-heart` wraps `scripts/remote-heart.sh run`, the single plain command an agent needs to drive a bench on the Mac Mini (every ssh/pipe/detached-spawn command string lives inside that script and `scripts/remote-heart-run.sh`, never typed ad hoc); `heart-bench-sync` (`uv sync --extra mlx`) exists so the remote side reuses this Makefile's own `$(UV)` fallback resolution rather than hardcoding a path. None of the four join `check`/`check-all`, the same Mac-only reasoning as `heart-bench` itself. `remote-heart-journal-smoke`/`-tail`/`-attach` (issue #55) mirror that trio exactly, wrapping `scripts/heart-journal-smoke.sh` instead — a real daemon boot-and-verify check, not the eval harness, in its own tmux session so the two tools never collide; same Mac-only exclusion from `check`/`check-all`. `remote-heart-soak-start`/`-status`/`-fetch`/`-tail`/`-attach`/`-stop` (issue #56) wrap `scripts/heart-soak.sh`'s six subcommands for the milestone's multi-hour unattended soak — structurally different from the two trios above, since an 8-hour run can't sit inside one blocking `make` call: `-start` force-syncs and launches in its own tmux session (`ansina-soak`) and returns immediately, while `-status`/`-fetch`/`-tail`/`-attach`/`-stop` are separate, later invocations that can run from a different local session entirely. Same Mac-only exclusion from `check`/`check-all` as the other two trios. `heart-bench-publish` (issue #59) wraps `uv run --extra s3 python -m ansina.heart.eval.publish $(ARGS)` — the backlog migration + ongoing catch-up command, uploading every local bench/soak report not already in the configured `[telemetry.s3]` bucket; not Mac-only (it just mirrors local files, no MLX needed) but, like `heart-bench`, performs real network writes, so it's excluded from `check`/`check-all` the same way. `vector-validate` (issue #62) wraps `scripts/vector-validate.sh` — validates `deploy/vector.toml` against the real `vector` binary (installed on neither CI leg, so excluded from `check`/`check-all` the same way as `heart-bench`) with placeholder env values, no network. `dev-mode-smoke` (issue #62) wraps `scripts/dev-mode-smoke.sh` — the primary end-to-end verification for Dev Mode: boots `ansina --dev` against a scratch database/spool dir with whatever real `[telemetry.s3]` credentials this host already has configured, and verifies objects actually land in the bucket by reading them back out of it directly. Needs no GPU/Heart (`TelemetrySampler` runs independently of `[heart]`/`[heart.tick]`) so it runs unchanged on a plain Linux dev box as well as the Mac Mini — unlike `heart-bench`'s Mac-only family, excluded from `check`/`check-all` instead because it needs `vector` installed and real bucket credentials, the same reasoning as `heart-bench-publish`. `remote-dev-mode`/`-tail`/`-attach` (issue #62) wrap `scripts/remote-dev-mode.sh`'s three subcommands — the same force-sync-then-tmux shape as `remote-heart`, but deliberately thin: the remote side (`scripts/remote-dev-mode-run.sh`) just runs `make dev-mode-smoke` on the real target hardware, so no verification logic is duplicated between the local and remote paths.
- `src/ansina/`: Core application source code (src-layout package, `py.typed` marker for downstream type-checking).
- `src/ansina/__main__.py`: Process entry point (`python -m ansina` / the `ansina` console script). Loads config, configures logging, builds the app via `create_app()`, hands it to uvicorn.
- `src/ansina/api/`: REST API surface (issue #4). `create_app()` in `api/app.py` is the FastAPI factory. `api/middleware.py` assigns/echoes the request id and feeds `logging`'s correlation-id contextvar. `api/auth.py` (issue #5, redesigned by #24, its chain formalized by #25, extended by #26) enforces a bearer token, deny-by-default — every route needs one except `PUBLIC_PATHS` (`/healthz`, `/readyz`, `/auth/oidc/login`/`/auth/oidc/callback` — issue #43, the first non-health-probe entries — and `/auth/login` — issue #50, the same reasoning — since a caller cannot be authenticated before completing a login). `BearerAuthMiddleware` walks an `Authenticator` chain (`auth.authenticator.build_authenticators(db, settings)` — issue #28 added `settings` so `ApiTokenAuthenticator` can read `[security] token_last_used_resolution_seconds`; a required constructor param, no in-middleware default, so a follow-up milestone's OIDC authenticator is an append, not a rewrite) rather than a comparison against one static config secret, resolving a full `auth.principal.Principal` (user + every role reachable direct-or-via-group) onto `request.state.principal` — offloaded via `anyio.to_thread.run_sync` so the blocking sqlite scan + per-row hash comparison never stalls the event loop. An inactive user's token stops authenticating (`auth.authenticator.resolve_principal`'s own check — `find_user_by_api_token` itself doesn't filter on `users.active`). `security.enabled = False` (not "no token configured" — that now means "auto-generate one") is the only way to disable enforcement, and `config.settings` refuses to boot at all if that's paired with a non-loopback bind. Once a `Principal` is resolved, an `X-Sudo-Token` header (issue #26) is additionally checked against `app.state.sudo` (`auth.sudo.SudoService`) and, on a live match, elevates it via `Principal.with_sudo()` — an absent/expired/wrong/revoked grant never turns into a 401 by itself, it just fails to elevate, leaving a sensitive route's own 403 `CODE_SUDO_REQUIRED` as the only signal. `api/authorization.py`'s `require(resource, *, sensitive=False)` (issue #25) is the FastAPI dependency every non-public route declares — the verb is read from `request.method`, not declared per-route — answering "does the caller's `Principal` hold a role with a `role_permissions` row for (this resource, this verb)" via `auth.authorization.authorize()`, offloaded the same way; denial raises `ForbiddenError`/`SudoRequiredError` (403, `CODE_FORBIDDEN`/`CODE_SUDO_REQUIRED`), distinguishable from `BearerAuthMiddleware`'s 401 (`CODE_UNAUTHORIZED`, no/invalid identity) without leaking which credential component was wrong; every decision (granted or denied) is audit-logged with actor/resource/verb. `api/route_audit.py`'s `audit_route_coverage()` (issue #25) walks `app.routes` at `create_app()` time and raises `RouteCoverageError` — same "fail loudly before uvicorn binds a port" pattern as `HeartUnavailableError` — if any non-public route lacks exactly one `require(...)` declaration; its surviving declarations are also the `resources` catalog's entire source (replacing #24's `BOOTSTRAP_RESOURCES` seed constant, since deleted). Issue #38 has it additionally union each surviving route's `route.methods` into its resource's served-verb set (filtering out anything outside `Verb`, e.g. `OPTIONS` — never grantable, since `require()` itself 403s an unmapped verb), carried on `ResourceSpec.verbs` into the catalog alongside the name/description. `api/problems.py` + `api/exception_handlers.py` map every error door (`AnsinaError`, HTTP errors, validation errors, unhandled exceptions) to RFC 9457 `application/problem+json`. `api/readiness.py` is a named-check registry backing `GET /readyz`; later milestones register their own checks there instead of editing the route. `api/routes/health.py` holds the M0 routes: `/healthz`, `/readyz`, `/version` (`GET /version` gated `require("system.version")`). `api/routes/heart.py` (issue #11) holds Ansina's first non-health, non-public routes: `GET /heart/tick` (status), `POST /heart/tick/pause`/`/resume` (the tick loop's kill switch) — all gated `require("heart.tick")`, and all return 503 `problem+json` (`CODE_HEART_DISABLED`) when `app.state.tick_loop` is `None` (only once authorization already passed — a caller without a grant gets 403 without ever learning whether the Heart is even enabled). Issue #54 adds `TickStatus.paused_reason` — `None` for a manual `POST /heart/tick/pause` (no fault triggered it) or when not paused, and the human-readable trip condition when `TickLoop`'s own circuit breaker auto-paused it; deliberately no matching `/readyz` change, since `heart_tick`'s check means "the background task is alive," which stays true while paused. `api/routes/heart_journal.py` (issue #55) is a sibling module, not an addition to `heart.py` — `GET /heart/journal`, the Heart's durable trace (`heart.journal.HeartJournalRepository`), on its own `heart.journal` resource (ordinary policy class, Read-reachable like `heart.tick`, but served by exactly `GET` — no pause/resume-shaped mutation exists for it). Deliberately **no** 503-when-disabled branch, unlike every route in `heart.py`: the journal needs only `app.state.db`, not a live `TickLoop`, and keeps serving historical rows after `[heart] enabled` goes back to `false`, which is the whole point of a durable trace. `limit`/`since` query params page newest-first (`JournalPage.has_more`, computed by querying one extra row past `limit` rather than a cursor); a malformed `since` is refused 400 `ansina.request.invalid`. Issue #64 adds `JournalEntryOut.brain_status`/`brain_detail`/`brain_prompt_tokens`/`brain_completion_tokens` — `null`/`""` on every row with no Brain interaction, populated only on the second row `BrainEscalationHandler` appends for an `escalate` tick that actually reached (or was declined from reaching) the Brain. `api/routes/openapi.py` (issue #25) serves `GET /openapi.json` behind `require("system.openapi")` as a real, gated `APIRoute` — `create_app` passes `openapi_url=None, docs_url=None, redoc_url=None` to the `FastAPI` constructor, since the framework's default `/docs`/`/redoc`/`/docs/oauth2-redirect` are plain Starlette routes that can't carry a `require(...)` declaration (and are non-functional with auth enabled anyway — no `fastapi.security` scheme is declared for Swagger UI's "Authorize" button, since auth here is middleware-level). `api/routes/sudo.py` (issue #26, generalized by #37) holds `POST /auth/sudo` (step up via `app.state.sudo.step_up()`, gated `require("auth.sudo")`), `DELETE /auth/sudo` (revoke your own grant, same resource), and the break-glass `DELETE /auth/sudo/grants` (revoke every active grant, gated `require("auth.sudo.grants", sensitive=True)` — reaching it already requires a live grant); all three are `auth.*` resources so `auth.policy.permitted_verbs` restricts them to Maintain/Admin with no policy change. Issue #37 makes the sudo gate itself fail-closed — `auth.authorization.authorize()`'s `sensitive=True` branch now requires a live grant from any role but `Admin`, not only `maintain`, so a future custom role (#40) granting an `auth.*` permission can't bypass step-up by not being named `maintain` — and generalizes `auth.step_up.StepUpRegistry.for_principal` from one fixed verifier to every verifier the caller is actually enrolled in (`StepUpVerifier.is_enrolled`, backed by `auth.repositories.CredentialRepository.has_credential`); `SudoService._resolve_factor` picks among them via an optional `payload["factor"]`, raising the new `StepUpUnavailableError` (403 `ansina.auth.step_up_unavailable`) — before any failed-attempt bookkeeping runs — when zero factors are enrolled, an unrecognized `factor` is named, or 2+ are enrolled with none named to disambiguate. `api/routes/users.py`/`groups.py`/`role_assignments.py`/`roles.py`/`permissions.py` (issue #27) round out the RBAC management surface Users/Groups/Roles the rest of M2 exists to protect. `users.py` (`GET`/`POST /auth/users`, `GET`/`PATCH`/`DELETE /auth/users/{id}`, `PUT /auth/users/{id}/password`, `POST`/`GET /auth/users/{id}/tokens`, `DELETE /auth/users/{id}/tokens/{token_id}`) and `groups.py` (`GET`/`POST /auth/groups`, `GET`/`PATCH`/`DELETE /auth/groups/{id}`, `PUT`/`DELETE /auth/groups/{id}/members/{user_id}`) each gate `GET` `sensitive=False` and every mutation `sensitive=True` on one resource (`auth.users`/`auth.groups` respectively); `DELETE /auth/users/{id}` is a one-way tombstone (`UserRepository.soft_delete`), never a row removal. Issue #28 narrows `POST .../tokens`: it mints a user's *first* `api_token` credential, never a second (`auth.management.assert_no_existing_api_token` — 409 otherwise, checked ahead of the bootstrap-identity guard below since its message actively misleads that identity); beyond the first, the user mints their own via `POST /auth/me/tokens`, and revoking their last token drops the count back to zero, making the admin route double as the lost-credential recovery path. All three token routes build on `api/tokens.py` (issue #28) — `TokenOut`/`IssueTokenRequest`/`IssuedTokenResponse` plus `issue_token()`/`list_tokens()`/`revoke_token()`, shared with `me.py` below, lifted out the same way `api/identity.py` was once a second router needed the identical shape. `issue_token()`/`revoke_token()` both call `auth.management.assert_not_bootstrap_identity()` — the bootstrap identity holds exactly one `api_token`, ever, so neither route can mint it a second one or delete the one it has (403 `ansina.auth.bootstrap_identity`); its `GET` is unaffected. Issue #39: `TokenOut` gains `expires_at: str | None` (`null` for a never-expiring token, the response shape for every existing route today); `issue_token()` gains optional keyword-only `ttl_seconds`/`clock` params — unreachable from HTTP as of this issue (`me.py`/`users.py` call it positionally with no keywords, so every route-issued token still gets `expires_at=NULL`), the seam issue #43's OIDC-minted token is the first to actually pass, minting a genuinely short-lived credential. `ttl_seconds <= 0` raises `ValueError` rather than minting a token already expired at issuance. `role_assignments.py` holds the four nested attach/detach routes (`POST`/`DELETE /auth/users/{id}/roles/{role_id}` and the `/auth/groups/...` equivalent, resource `auth.role_assignments`, always `sensitive=True`) and additionally runs every assignment through `auth.management.assert_may_assign_role` (skipped only when `security.enabled = False` leaves no resolved `Principal` to check against). `roles.py` (issue #27, custom-role write routes added by #40) and `permissions.py` (issue #27, made trustworthy by #38) are the role/permission-catalog pair. `GET /auth/roles` lists every role with its current `role_permissions` grants; builtin roles stay permanently read-only (owned by `auth.reconciler.reconcile_builtin_roles`), but issue #40 adds `POST /auth/roles` (create a non-builtin role with an initial grant set), `PATCH /auth/roles/{id}` (replace a non-builtin role's grant set wholesale via `RolePermissionRepository.replace_for_role` — one transaction, not a diff), and `DELETE /auth/roles/{id}` — all three `sensitive=True` on the same `auth.roles` resource, so #37's fail-closed sudo gate covers them the same way it covers every other `auth.*` mutation. `PATCH`/`DELETE` refuse a `builtin=1` role (`BuiltinRoleError`, 409) regardless of caller; `DELETE` additionally refuses (`RoleInUseError`, 409) a role still referenced by any `role_assignments` row — checked in the repository layer before any `DELETE` statement runs, never left to `role_assignments.role_id`'s `ON DELETE CASCADE` to decide. Every mutation runs the submitted `(resource, verb)` grant set through two guards in `auth.management`, in order: `assert_grants_grantable` (issue #40 — is each grant catalogued, `grantable` per `auth.policy.is_grantable`, and a verb the resource actually serves per #38's `Resource.verbs`? An uncatalogued or non-grantable resource can never be an escalation, so this runs first) and `assert_may_grant_permissions` (issue #40's generalization of `assert_may_assign_role`'s own subset/`auth.*`/`admin` logic over a raw grant set rather than an existing role's — the same self-escalation check now runs at grant-*edit* time, not only at role-assignment time). `GET /auth/permissions` (issue #38): each catalogued resource with the verbs it's *actually served on* — not `list(Verb)` unconditionally — plus its `auth.policy.PolicyClass` (`ordinary`/`auth`/`self`) and a `grantable` flag, `False` for every `me.*` resource since every builtin role already holds every verb there — the discovery surface `POST`/`PATCH /auth/roles` (#40) builds on. `api/routes/role_mappings.py` (issue #42) is `GET`/`POST`/`DELETE /auth/role-mappings` on a single `auth.role_mappings` resource — no policy change needed, since it falls under `auth.policy`'s existing `auth.`-prefix rule the same way `auth.roles` does. `POST` treats a submitted mapping as a *deferred* role assignment: it runs `auth.management.assert_may_assign_role` against the mapped role (not `assert_may_grant_permissions` — a mapping names one role, not a raw grant set), so a sudo'd `Maintain` can't stage a mapping onto `admin` for a future login sync to later apply; a submitted `role_id` that doesn't exist is checked and refused (404) *ahead* of the insert, so a typo is never mistaken for `idx_role_mappings_tuple`'s own 409 (both `role_mappings.role_id` and `role_assignments.role_id` are foreign keys, and either would raise the identical `sqlite3.IntegrityError`). `api/routes/oidc.py` (issue #43) is `POST /auth/oidc/login` + `GET /auth/oidc/callback` — the OIDC federated-login exchange, and the only routes in `PUBLIC_PATHS` beyond the two health probes, since a caller cannot hold a bearer token before it has logged in; neither declares a `require(...)`, so `route_audit.audit_route_coverage` skips both the same way it already skips `/healthz`/`/readyz`, and neither contributes a `resources` catalog entry. Both answer 503 (`ansina.auth.oidc_disabled`) when `app.state.oidc is None` (`[security.oidc] enabled = false`, the default), mirroring `routes/heart.py`'s `CODE_HEART_DISABLED` shape. The route layer is thin: it validates the callback's own query parameters (`error=` present, or `code`/`state` missing, both 400 `ansina.auth.oidc_callback_failed`, checked before `ansina.auth.oidc.OidcLoginService` is even consulted) and, on success, mints the resulting `api_token` itself via `api/tokens.py`'s `issue_token(..., ttl_seconds=oidc.token_ttl_seconds, clock=oidc.clock)` — deliberately not inside the service, since `ansina.auth` (the package) never imports from `ansina.api` anywhere else in this codebase, and `ansina.api`'s own package `__init__` imports `create_app`, which imports back from `ansina.auth`; the service reaching into `api.tokens` would make that a circular import. `api/routes/login.py` (issue #50) is `POST /auth/login` — exchange a local username + password for an `api_token`, the third `PUBLIC_PATHS` entry beyond the two health probes and the two OIDC routes, same reasoning (a caller can't hold a bearer token before logging in) and same shape (no `require(...)`, no `resources` catalog entry). Ansina's first unauthenticated, brute-forceable route, so it carries two disciplines the rest of the API doesn't need: exactly one `problem_response(...)` call site produces the single 401 `ansina.unauthorized` body for every failure mode (unknown username, wrong password, password-less/inactive/tombstoned user, the bootstrap identity — refused explicitly, ahead of `api/tokens.py`'s `issue_token`, whose own `assert_not_bootstrap_identity` would otherwise leak a distinguishable 403), and every one of those paths runs a real argon2 verify — against `auth.hashing.dummy_password_hash` when there's no real credential to check — so the response *time* can't distinguish them either, closing a timing side channel the byte-identical body alone leaves open. Strict order (`LoginThrottle.check` (#49) → user lookup → refusals → verify → `record_success`/`record_failure`) mirrors the issue's own AC; mints via `issue_token(..., ttl_seconds=settings.security.login.token_ttl_seconds, clock=throttle.clock)`, labeled `"password login"` — #39's seam, its second HTTP-reachable caller after #43's OIDC route. `api/cors.py` (issue #51) is `add_cors_middleware(app, settings)` — wraps `starlette.middleware.cors.CORSMiddleware` (ships with FastAPI, no new dependency), adding it only when `[security.cors] enabled = true` (`config.settings.CorsSettings`, default `false`, same "off means nothing added" shape as `[security.oidc]`); `ALLOW_METHODS` is derived from `auth.models.Verb` plus `OPTIONS` so it can't drift from what a route can actually be gated on, `ALLOW_HEADERS` always includes `Authorization`/`X-Sudo-Token`, and `EXPOSE_HEADERS` always includes `X-Request-ID` (browser log-correlation, matching `tui/`'s `ApiClient`) and `Retry-After` (otherwise-hidden-from-JS visibility into #49's login throttle and #26's sudo lockout). `allow_credentials` is always `False` — Ansina authenticates with `Authorization`, never a cookie. `api/identity.py` (issue #30) holds the shared request-identity helpers — `current_principal(request)` (`request.state.principal` if `BearerAuthMiddleware` resolved one, else `None`) and `no_identity_response()` (the 401 `problem+json` for when it didn't) — lifted out of `routes/sudo.py`'s and `routes/role_assignments.py`'s own private copies once a third caller needed them; both now import from here instead. `api/routes/me.py` (issue #30, extended by #28 and #37) holds `GET /auth/me`, gated `require("me.profile")`: the first route on the `me.*` self-resource policy class (`auth.policy.is_self_resource`), reachable by every builtin role including `Read` and never sudo-gated, returning the already-resolved `Principal` (user, roles, sudo status) plus, as of #37, `step_up_factors` — the verifier names `SudoService.enrolled_factors()` reports the caller could currently succeed with, the one field on this route that costs a database read (a single indexed `credentials` lookup per enrolled-verifier check) beyond what `resolve_principal` already resolved — note the resource is `me.profile` while the path stays `/auth/me`, since a resource is a stable, dotted, URL-independent name, never the path. Issue #28 adds `POST`/`GET /auth/me/tokens` and `DELETE /auth/me/tokens/{token_id}` on a second self-resource, `me.tokens` — self-service issuance/listing/revocation of the caller's own tokens, built on `api/tokens.py` (see the `users.py` entry above), refused (403 `ansina.auth.bootstrap_identity`) for the bootstrap identity on `POST`/`DELETE` but not `GET`. Issue #41 adds a third self-resource, `me.totp` (`POST`/`GET`/`DELETE /auth/me/totp`) — the one `me.*` resource with a `sensitive=True` route: `authorize()`'s sensitivity check is a per-`require()`-call flag, not a name-pattern match, so `DELETE` (disable) can still demand a live sudo grant while `POST`(enroll)/`GET` (status) stay ungated, deliberately — requiring sudo to obtain a caller's *first* step-up factor would be an unsatisfiable chicken-and-egg lockout. `POST` generates a fresh RFC 6238 secret (`ansina.auth.totp`), stores it as an AES-GCM envelope (`ansina.auth.encryption.encrypt`) via `CredentialRepository.create_totp_secret`, and returns the raw secret plus an `otpauth://` URI exactly once — never recoverable afterward, same discipline as a minted API token; refused (409 `ansina.auth.totp_already_enrolled`) if already enrolled, and (503 `ansina.auth.encryption_key_missing`) if `[security.encryption] key` isn't configured. `DELETE` is idempotent (204 whether or not a credential existed), mirroring `SudoService.revoke_for_user`. `api/routes/users.py` gets the matching Admin recovery route, `DELETE /auth/users/{id}/totp` (`auth.users`, `sensitive=True`) — clears a lost-device enrollment on the user's behalf, reachable even though it shares no dependency with the user's own sudo state, so it's never itself blocked by the very lockout it exists to fix. Issue #48 adds a fourth self-resource, `me.password` (`PUT /auth/me/password`) — self-service password set/change, deliberately never `sensitive=True` either but for a different reason than `me.totp`'s enrollment: the request body's own `current_password` check *is* the proof-of-possession, the same one `PasswordStepUpVerifier` performs at `POST /auth/sudo`, so a sudo grant on top would mean requiring the password to change the password. A caller holding no password credential yet (the default shape of a user `POST /auth/users` creates without one) may omit `current_password` to set a first one, the same chicken-and-egg carve-out `POST /auth/me/totp` makes above. Both this route and `api/routes/users.py`'s two password-setting points (`CreateUserRequest.password`, `PUT /auth/users/{id}/password`) run the submitted password through `ansina.auth.password_policy.assert_password_acceptable` before it ever reaches `CredentialRepository.set_password`, refusing (400 `ansina.auth.weak_password`, `api/problems.py`) one that's too short, too long, contains the username, or is on the bundled common-password list.

M3's issue #43 (done) is the milestone's last piece — federated login via OAuth 2.0/OIDC, shaped as a **login exchange** rather than a per-request authenticator (M3's open consideration #5, resolved by not using `Authenticator` at all): `auth/oidc.py` is the pure protocol layer — an `OidcHttpClient` structural `Protocol` (`get_json`/`post_form`, same shape discipline as `HeartRuntime`/`BrainProvider`/`StepUpVerifier`) behind `discover()` (OIDC discovery, issuer-mismatch and missing-endpoint fail-closed, fetched fresh every login — no caching layer, so an IdP's key rotation takes effect on the very next login), `fetch_jwks()`, `exchange_code()` (the authorization-code + PKCE `code_verifier` redemption), and `validate_id_token()` — one `jwt.decode()` call with `algorithms` pinned to an asymmetric-only tuple (RS/PS/ES, never `none`, never `HS*` — closes the classic "algorithm confusion" forgery where a JWKS public key gets replayed back as an HMAC secret), `audience`/`issuer` checked, `options={"require": [...]}` making every claim's *presence* mandatory not just its value, and a separate `hmac.compare_digest` nonce check (no concept in `jwt.decode` itself). `HttpxOidcClient` is the one real `OidcHttpClient` — a fresh, short-lived `httpx.Client` per call (login is human-paced, not a hot path, so no persistent connection or `aclose()` lifecycle is worth keeping), with an injectable `transport` (`httpx.MockTransport`, part of `httpx` itself) letting its own unit tests exercise real success/non-2xx paths with no socket. `auth/oidc_login.py`'s `OidcLoginService` is the orchestration layer: `start_login()` discovers the authorization endpoint, mints `state`/`nonce`/PKCE `code_verifier`, persists them (sweeping previously-expired rows as a side effect), and returns the authorization URL; `complete_login(code, state)` runs, in strict order, single-use state lookup → code exchange → ID-token validation → user provisioning/linking → `sync_mapped_roles` (issue #42's first caller, run on *every* login, not only the first) — every rejection before provisioning, so a forged or malformed callback can never touch `users`/`external_identities`/`role_assignments`. It returns the provisioned `User`, not a minted token — minting one (`api/tokens.py`'s `issue_token`, issue #39's first HTTP-reachable caller) is deliberately left to `api/routes/oidc.py`, since `ansina.auth` never imports from `ansina.api` anywhere else in this codebase and doing so here would be a circular import (`ansina.api`'s own package `__init__` imports `create_app`, which imports back from `ansina.auth`); `clock`/`token_ttl_seconds` are exposed as read-only properties so the route mints with the exact clock the service validated against. Provisioning (`_provision_user`) matches on `(provider, subject)` first (reuse), refusing a tombstoned or deactivated linked user; on a miss, it derives a username (`preferred_username` → `email` → `sub`) and, on a *username* match against an existing local user, **links** the IdP subject onto that account rather than refusing or auto-disambiguating — a deliberate choice (an operator can migrate an existing local user onto the IdP with no separate step) logged as a `logger.warning` naming both identities, since it confers that account's roles on the IdP subject; refused outright for a tombstoned/deactivated/bootstrap-identity target. `build_oidc_login_service(db, settings, *, client=None, clock=utc_now)` returns `None` when `[security.oidc] enabled = false` — the same shape `heart`/`brain` factories use — and performs no network call at assembly time, unlike Heart/Brain: an unreachable or misconfigured IdP only ever fails an individual login, never boot. New base dependencies: `pyjwt[crypto]` (ID-token signature validation, pulling `cryptography` — already a base dep since #41) and `httpx` (the login exchange's transport — previously only a transitive/dev dependency, now declared directly since it's used for real).

`/healthz` is always checked before `/readyz`, so an unhealthy daemon exits `7`, never `6`. `config.py` is the XDG credential store (`$XDG_CONFIG_HOME/ansina`, else `~/.config/ansina`): `config.toml` (non-secret `default_host`, written by `save_config()`, issue #32) and `hosts.toml` (per-host `token`/`token_id`/`username`/`roles`/`sudo_token`/`sudo_expires_at` — `token_id`, issue #32, is set only when `auth token mint` stores the token it just minted, letting `auth token revoke` detect and warn on self-revocation), written via `os.open(..., 0o600)` and refused on read if group/other-readable (`InsecureCredentialsFileError`, naming the `chmod 600` fix) — serialized by a hand-rolled `_dump_toml` since 3.14's stdlib `tomllib` is read-only and no TOML-writer dependency was added for this one narrow schema. `ANSINA_TOKEN`/`ANSINA_HOST` (`resolve_token`/`resolve_host`) are resolved separately from `HostEntry`, so they can never be written back to disk. `client.py`'s `ApiClient` wraps `httpx.Client`: bearer auth, `X-Sudo-Token` attached only while an injectable-clock-checked grant is unexpired (`parse_expiry`, exported — issue #32's `session.py` reuses the exact same parse rather than duplicating it), and the daemon's echoed `X-Request-Id` (`ansina.api.middleware`) captured onto every `ApiResponse` for log correlation; `httpx.TransportError` becomes `HostUnreachableError` (exit 5). `problems.py` parses `application/problem+json` into `ApiProblem`, with a hand-copied (not imported — `tui/` can't import `ansina`) table of recognized `ansina.*` codes to human messages — issue #32 adds `ansina.auth.bootstrap_identity` (names the real fix: log in as the configured admin or an ordinary Admin), `ansina.auth.token_already_issued`, and `ansina.auth.not_found`. `output.py`'s `Emitter` is the output-discipline seam: with `--json`, stdout carries JSON and **nothing else** (a plain `sys.stdout.write`, never through `rich`) — every diagnostic goes to stderr; issue #32 adds `verbose`-gated `debug()` (so a request id can be shown without ever risking a secret), `warn()`, and a headered multi-column `table()` (`auth token list`). Issue #32 also adds the credential/session layer above `config.py` and the `auth` command surface built on it. `session.py`'s `Session` is the resolved host/config/credential state for one invocation; `resolve_session()` loads `config.toml`+`hosts.toml` and resolves `--host`/`ANSINA_HOST`/`ANSINA_TOKEN` precedence, scrubbing an *expired* sudo grant onto `Session.entry` in memory (never sent, never re-persisted) while `Session.hosts` keeps the raw, unscrubbed table so `auth sudo --status` can still tell "expired" apart from "never stored". `build_client()` is the single `ApiClient` construction point (and the one seam `tests/conftest.py`'s `patch_transport` fixture patches, replacing #31's `patch_status_transport` now that `commands/status.py` is built on this module too) — its `token=` override lets `auth login` authenticate with a just-supplied token before anything is stored. `save_entry()`/`remove_entry()` write `hosts.toml` back (the former also sets `default_host` on first login); `sudo_state()` classifies a `HostEntry`'s grant as `none`/`expired`/`active`. `secret_input.py`'s `read_token()`/`read_password()` are the "never argv" seam pinned by `tests/unit/test_argv_safety.py`'s walk of the whole Click command tree (vendored inside Typer, `typer._click` — no separate `click` import): `--with-token`/a piped non-TTY stdin is read directly, otherwise a `typer.prompt(hide_input=True)`; both resolve `sys.stdin` inside the function body, never as a `= sys.stdin` default-argument value, which would bind once at import time and miss `CliRunner`'s per-invocation stdin swap (the same trap `main.py`'s `_is_interactive` already documents). `failures.py`'s `report()` is the shared non-2xx renderer every command calls: the recognized message from `problems.py` (or a per-call override — `auth sudo` overrides `ansina.unauthorized`'s generic "run `auth login`" text, since that code means "wrong step-up password" at `POST /auth/sudo`), the request id under `--verbose`, and a rendered `Retry-After` figure from the problem body's own `retry_after_seconds` extension member (issue #26's sudo lockout, 429). `commands/auth/` (package) holds `login.py` (`login`/`logout`), `status.py` (`auth_status_command` — always a live `GET /auth/me`, no cache fallback), `sudo.py` (`sudo_command`: `--revoke`/`--status`, the latter local-only and self-healing an expired grant it finds), and `tokens.py` (`mint`/`list`/`revoke` over `/auth/me/tokens`, #28 — `mint` shows the raw token once, reusing #24's bootstrap-banner framing, and offers to store it; `revoke` warns and confirms before revoking the id currently in use). `commands/auth/__init__.py` wires `auth_app` (+ nested `token_app`) into `main.py`'s root app via `add_typer`; bare `auth`/`auth token` is a usage error (exit 2), not silent success. `commands/status.py` (day-0, issue #31) is now built on `session.py` the same way: `GET /healthz` → `/readyz` → `/version`, works with **no token at all** (both health routes are public), `/version` 401 degrades to `"unknown"` rather than an error. `commands/api.py` (issue #33) is `ansina-tui api [-X METHOD] <path>` — the raw REST wrapper reaching any daemon route with no per-route special-casing and no allow-list to keep in sync, and the milestone's CI/CD surface (so it never blocks for input). It required two small, additive extensions rather than a new foundation: `client.py`'s `ApiResponse` gained `text` (the body verbatim) and `headers` (the response headers, for `-i`), and `ApiClient.request()` gained `content=` (a raw body, alongside the existing `json_body=`; httpx's own `encode_request` checks `content` before `json`, so the two never conflict) and `headers=` (a caller's own headers merged in) — critically, `Authorization`/`X-Sudo-Token` are now set by plain assignment *after* merging a caller's headers, never `setdefault`, so a `-H` can never silently replace either (when no token is configured at all, a caller-supplied `Authorization` still passes through unharmed). `RESERVED_HEADERS` (`authorization`, `x-sudo-token`) is exported so `commands/api.py` can warn, not just silently override. `output.py` gained `Emitter.body()`, a plain `sys.stdout.write` (never through `rich`, same discipline as `Emitter.json`) for the response body verbatim — deliberately not `Emitter.json`, which re-serializes a `Mapping` with `sort_keys=True` and would reorder the daemon's fields or reject a non-object body. `api_command` itself: `-f/--field key=value` (repeatable) assembles a JSON object body whose values are always JSON strings — a typed field goes through `--input <file|->` instead, mutually exclusive with `-f`; method defaults to `GET`, or `POST` when either supplies a body (the `gh api` convention). Output follows `_stdout_is_tty()` (its own function, patched in tests, for the same `CliRunner`-swaps-`sys.stdout` reason `main._is_interactive` is): pretty-printed JSON on a TTY with no `--json`, raw under `--json` or a piped stdout — and the body is written whether or not the response was 2xx, so `--json | jq` works on a problem document too. `-i/--include` (status line + response headers) is rendered via `emitter.line()`, so it is itself suppressed under the same `--json`/piped-stdout condition, keeping the two rules from conflicting. `pyproject.toml` gained `[tool.ruff.lint.flake8-bugbear] extend-immutable-calls = ["typer.Option", "typer.Argument"]` — without it, ruff's B008 misfires on the standard Typer idiom for a repeatable option (`fields`/`raw_headers` here) as if it were a mutable default. Issue #34 replaces #31's placeholder shell with the real Overview tab and adds `daemon_state.py`, the module holding the whole of "what the daemon says about itself" as a pure, synchronous, **never-raising** function — `fetch_overview(app_context, env=...)` re-resolves a `Session`/`ApiClient` via `session.resolve_session()`/`build_client()` on every call (the same construction point and `patch_transport` test seam every CLI command already uses) and turns `HostUnreachableError`/`InsecureCredentialsFileError` into a designed `OverviewSnapshot` (`host`, `connection: "connected"|"unreachable"|"config error"`, a whole-tab `error`, and one `Panel` — `rows`/`message` — per section: `health`/`readiness`/`version`/`identity`) rather than letting either propagate; that's load-bearing because Textual's `@work` defaults to `exit_on_error=True`, so a raise out of a worker would crash the app instead of rendering an empty state. `readiness_checks()`/`version_display()` moved here from `commands/status.py` (which now imports them) so the CLI and the TUI agree on exactly what a "check" is and how a version renders. `ui/tabs.py`'s `RefreshableTab(VerticalScroll)` is the one-method contract (`TAB_ID`/`TAB_TITLE` class vars, an `__init__(app_context)` every subclass must keep positionally compatible, and `request_refresh()`) that lets `ui/app.py`'s `AnsinaTuiApp` compose a `TABS: ClassVar[tuple[type[RefreshableTab], ...]]` generically and dispatch `r` via `self.query(RefreshableTab)` (Textual's widget query matches subclasses) — adding a second tab is an append to `TABS`, no other change to `app.py`. `CSS_PATH` is set to an absolute `Path(__file__).parent / "app.tcss"` rather than a bare relative string, since Textual resolves a relative `CSS_PATH` against the *actual* (sub)class's module (`inspect.getfile(type(self))`), which would otherwise break for any test harness subclassing the app from a different directory. `ui/overview.py`'s `OverviewTab(RefreshableTab)` is the one tab M4 ships: `compose()` mounts one `Static` per section, `on_mount()` fires an immediate `request_refresh()` and `set_interval(app_context.refresh, ...)`, and `request_refresh()` drives an `@work(exclusive=True, group="overview")` worker (`asyncio.to_thread` around the synchronous `fetch_overview`) that updates those same widgets in place — never re-mounting — so a refresh never flickers or duplicates content; `fetcher` is constructor-injectable so widget tests drive every designed state without a transport. A panel with rows renders as a borderless `rich.table.Table`; a message-only panel as plain text; a fully empty panel (a whole-tab failure) as a `"—"` placeholder — never blank. The tab also keeps `App.sub_title` current (`"<host> · <connection>"`) on every refresh, which is how host/connection state stays visible in the header. `context.AppContext` gained `refresh: float = 5.0` — TUI-only, but resolved as a root-level `--refresh` option in `main.py` (the no-args rule leaves no subcommand to carry it) and validated (`> 0`) only on an actual TUI launch, after the interactivity check, so `--refresh 0 status` is untouched by the validation. `tests/unit/` mirrors `src/ansina_tui/` 1:1 at the same 100%-coverage bar as the daemon; shared test helpers live as `tests/conftest.py` **fixtures**, never a plain module-level import — `tests/` has no `__init__.py`, so cross-file `from tests.conftest import ...` isn't reliable under `--import-mode=importlib`. ## Layer 3: Data Flow & Entry Points
- Entry points: `python -m ansina` and the `ansina` console script (`[project.scripts]`), both resolving to `src/ansina/__main__.py:main` — the daemon, unchanged by M4. Issue #62 gives `main()` a keyword-only `argv: Sequence[str] | None = None` parameter (so the unit suite drives argv directly rather than depending on `sys.argv`) and one real flag, `--dev` (`argparse`), establishing Dev Mode's posture via `load_settings(overrides={"dev": {"enabled": True}})` before `uvicorn.run(...)` is ever called, itself wrapped in `ansina.dev.dev_mode(settings)`. A second, independent entry point (M4, `tui/`): `python -m ansina_tui` and the `ansina-tui` console script, both resolving to `tui/src/ansina_tui/main.py:app`, from a separate distribution (`ansina-tui`, package `ansina_tui`) that never shadows or imports `ansina` — it reaches the daemon over HTTP only (pinned by `tui/tests/unit/test_isolation.py`: no `ansina`/`ansina.*` module in `sys.modules` after a full CLI run). Its dispatch rule inverts the usual CLI default: bare invocation on a TTY launches the Textual TUI; any argument at all (a subcommand, `--help`, `--version`) is the CLI instead, writing to stdout/stderr; bare invocation on a non-TTY prints help to stderr and exits `2` (Textual can't render into a pipe).
- Boot sequence: parse argv (issue #62's `--dev`) → `load_settings(overrides=...)` → `configure_logging(settings)` → `create_app(settings)` (`src/ansina/api/app.py`) → `uvicorn.run(...)`, the last wrapped in `ansina.dev.dev_mode(settings)` — a byte-for-byte no-op unless `--dev` was passed, so this adds no observable step to the ordinary boot sequence below. A `ConfigError` during boot prints the aggregated report to stderr and exits non-zero, never a traceback. `create_app` also builds `oidc = oidc_factory(db, resolved_settings)` (default `auth.build_oidc_login_service`, issue #43) alongside `sudo`/`authenticators` — `app.state.oidc` is `None` when `[security.oidc] enabled = false` (the default), the same shape `heart`/`brain` use, but unlike either, building it performs no network call and has no boot-time failure mode: an unreachable or misconfigured IdP only ever fails an individual login attempt. `load_settings()` itself refuses to construct `Settings` (issue #5, updated by #24) when `server.host` isn't loopback and `security.enabled` is `False` — that invariant is unbypassable since it lives on `Settings`, not in `create_app`; `api_token` being unset no longer factors in (issue #24 makes it optional even with auth enabled — Ansina generates its own bootstrap token instead). `api_token`, when set, must itself look securely generated: `_TOKEN_MIN_LENGTH` (32), `_TOKEN_CHARSET` (base64url only, so a human-typed phrase is rejected outright), `_TOKEN_MIN_ENTROPY_BITS_PER_CHAR` (2.5, a best-effort predictability deterrent, not a cryptographic guarantee) all in `config/settings.py`. After every router is included, `create_app` calls `api/route_audit.py`'s `audit_route_coverage(app)` (issue #25) — a `RouteCoverageError` there aborts boot the same "fail loudly before uvicorn binds a port" way a `ConfigError` does — and stashes its returned `ResourceSpec`s on `app.state.resource_specs`. `create_app`'s FastAPI `lifespan` opens the `Database` and runs `run_migrations()` on startup (a `MigrationError` there aborts boot the same way), then — issue #24, in this fixed order because each step depends on the last — `sync_resources()` catalogs `app.state.resource_specs` (issue #24 seeded this from a hand-written constant; #25 replaced that argument with the route audit's real walk, `sync_resources()`'s own contract unchanged), `reconcile_builtin_roles()` grants the four builtin roles against that catalog, `ensure_bootstrap_admin()` provisions the synthetic Admin identity, and (issue #28) `ensure_configured_admin()` provisions the second, ordinary Admin from `ANSINA_SECURITY__ADMIN_USERNAME`/`API_TOKEN` if set (see `src/ansina/auth/` below for both functions' full shape — order between the last two no longer matters functionally, since #28's "first boot" check for the second is independent of it, but it runs second to keep the narrative order); an `AuthError` from any of the four aborts boot the same way. `Database` is closed on shutdown; `Readiness` gets a `"database"` check backed by `Database.is_healthy()` (no dedicated `/readyz` check for the RBAC seeding — `database` already covers its only failure mode). When `[heart] enabled` is true, `create_app` calls `build_heart_runtime()` *before* the lifespan even starts — a `HeartUnavailableError` (issue #10) surfaces the same way a `ConfigError` does, before uvicorn ever binds a port; the lifespan then loads the model and registers a `"heart"` readiness check, unloading it on shutdown alongside the database close. When disabled (the default), `app.state.heart` is `None` and `/readyz` carries no `heart` key at all. When `[brain] enabled` is true (issue #12, independent of `[heart] enabled`), `create_app` calls `build_brain_provider()` the same "fail loudly before uvicorn binds a port" way (`BrainUnavailableError`); the lifespan `await`s `brain.aclose()` on shutdown alongside `heart.unload()`/`db.close()`. `app.state.brain` is `None` when disabled. No `/readyz` check is registered for it — the only meaningful liveness signal for a remote provider is a real network round-trip, and paying for one on every `/readyz` poll is the wrong trade. `brain` is built *before* `tick_loop` (reordered by issue #64, no functional reason beyond needing it in hand for the next step) — when the Heart is also enabled and `[heart.tick] enabled` is true (issue #11, its own default), `create_app` builds a `TickLoop` (`build_tick_loop(resolved_settings, heart, db=db, readiness=readiness, brain=brain)` — issue #54 widened the call to pass the app's own `db`/`readiness` through so `build_tick_loop` can register its `DaemonStateSource`; issue #64 widens it again with `brain`, possibly `None`, so it can compose a `BrainEscalationHandler` when `[heart.tick] escalate_to_brain` is `True`) the same way, and the lifespan `start()`s it after `heart.load()` and registers a `"heart_tick"` readiness check, `stop()`ing it on shutdown before `heart.unload()`. `app.state.tick_loop` is `None` unless both flags are true. When `[telemetry] enabled` is true (issue #61), `create_app` calls `telemetry_factory(resolved_settings, tick=tick_loop)` (default `ansina.telemetry.sampler.build_telemetry_sampler`) independently of `heart.enabled`/`heart.tick.enabled` — `tick_loop` (possibly `None`) is passed straight through, since an operator may want RSS/uptime telemetry with the Heart disabled; `app.state.telemetry` is `None` when disabled, the same shape `heart`/`brain`/`oidc` use. The lifespan `start()`s it last, after the heart/tick-loop block (it only ever *observes* `tick_loop`'s state), and `stop()`s it first on shutdown — LIFO, "stop the observer before the thing it observes," the same reasoning already governing `brain.aclose()`'s position relative to `heart.unload()`. No `/readyz` check for it either (not asked for, and a cheap in-process gauge the Brain's own omission above covers no worse).
- Request flow: `CORSMiddleware` (issue #51, outermost of all — only when `[security.cors] enabled = true`, the default `false` adds no middleware at all here) → `RequestIdMiddleware` binds/echoes a request id (feeding `logging`'s correlation-id contextvar) → `BearerAuthMiddleware` (401 `problem+json` if the route isn't in `PUBLIC_PATHS` — issue #43 widens this to `/auth/oidc/login`/`/auth/oidc/callback`, the first non-health-probe entries, since a caller cannot hold a bearer token before it has logged in — and the bearer token doesn't resolve a `Principal` through the `Authenticator` chain; issue #26: a resolved `Principal` carrying a live `X-Sudo-Token` is additionally elevated here) → the route's `require(resource)` dependency (403 `problem+json` if the resolved `Principal` holds no role granting `request.method` on that resource — issue #25, dev mode/`security.enabled=False` skips this too; 403 `CODE_SUDO_REQUIRED` if the resource is `sensitive=True`, the role is anything but `admin` (issue #37 — previously only `maintain`), and no elevation happened above) → route → response, or an exception mapped to `application/problem+json` by the handlers in `api/exception_handlers.py`. CORS runs outermost, ahead of both, because a preflight `OPTIONS` carries no `Authorization` header by definition — any inner ordering would let `BearerAuthMiddleware` 401 it, and the browser would surface that as an opaque, undiagnosable CORS failure rather than a real 401; the cost is that a preflight never reaches `RequestIdMiddleware` either, so it carries no `X-Request-ID` and generates no "request completed" log line — every *real* request past the preflight still flows through both. The `auth.*` management routes (issue #27) split `sensitive` by verb on the same resource rather than per-route: `GET /auth/users`/`/auth/groups`/`/auth/roles`/`/auth/permissions` are `sensitive=False` (Maintain reaches them with no grant), every mutating verb on `auth.users`/`auth.groups`/`auth.role_assignments` is `sensitive=True`. `me.tokens` (issue #28) is never `sensitive=True` at all, matching `me.profile`'s carve-out. A successful match against the `Authenticator` chain (issue #28) also coalesces a `last_used_at` write onto the matched credential — at most once per `[security] token_last_used_resolution_seconds`, not per request, since the lookup already full-scans `credentials` on every request.

Known upstream risk, watched not solved: vectordotdev/vector#23875 (the `aws_s3` sink's disk buffer can grow unbounded in memory during a prolonged upload outage) — mitigated by issue #61's own spool byte cap (bounds how much source data can ever exist to buffer) and this issue's post-spawn liveness check (surfaces an outright-dead sidecar), neither a fix for the upstream issue itself.

Calls a reusable workflow in `giacchetta/giacchetta.github.io` on every merged PR to generate a blog post; this repo passes PR/issue read access plus two secrets and owns no generation logic itself.

## Layer 5: Domain Blueprint
- **Heart** (≤4B, 8k ctx, in-process): owns the autonomic tick loop only — decide idle / act / escalate. Never answers user requests directly. Every prompt built for it must fit its 8k window; treat that as a hard constraint, not a target. The runtime port + MLX adapter (issue #10, `src/ansina/heart/`) and the tick loop (issue #11, `src/ansina/heart/tick/`) are wired into `create_app`'s lifespan; `TickLoop` is the first and only caller of `generate()`. Its snapshot has no real content yet (no pending-work/schedule/event domain exists), and `act` has nothing to act on — both remain injected seams with log-only defaults, not implemented behavior. `escalate` is the exception as of issue #64: gated by `[heart.tick] escalate_to_brain` (default `false`, the same log-only-until-opted-in shape as `act`), it is wired to `BrainProvider.stream()` — see the `src/ansina/heart/tick/` Layer 2 entry's `BrainEscalationHandler` paragraph.
- A portable, non-Apple-Silicon `HeartRuntime` adapter (originally scoped as llama-cpp-python in issue #10) is **deferred to a follow-up issue**: the only non-Apple hardware available at the time had no llama-cpp-python-compatible GPU, so an adapter there was unprovable and was cut rather than shipped untested. Until that lands, a non-Apple-Silicon host with `[heart] enabled = true` fails loudly at boot (`HeartUnavailableError`) rather than silently degrading.
- **Brain** (35B+, remote via `BrainProvider` port): owns all real reasoning. The Heart never replaces it or bypasses it for substantive answers. The port + its OpenAI-compatible adapter (issue #12, `src/ansina/brain/`) are implemented and wired into `create_app`'s lifespan the same way the Heart is, gated by `[brain] enabled` independently of `[heart] enabled`. As of issue #64, the tick loop's `escalate` decision is the first real caller of `stream()` (`[heart.tick] escalate_to_brain`, default `false` — see the `src/ansina/heart/tick/` Layer 2 entry's `BrainEscalationHandler` paragraph); a local 35B adapter and multi-provider routing/fallback chains are explicitly out of scope, deferred the same "unprovable on hardware at hand" way the llama-cpp-python fallback above was.
- Three additional Heart duties (request triage, context curation, structured extraction) are **deliberately not implemented**. Prior embedded-model attempts produced low-quality output — each duty is a gated experiment (`Backlog — Experiments` milestone) requiring a benchmark win over a stated baseline before adoption. Do not fold this logic into the tick loop without that gate passing.
- **Control surface** (M4, `tui/`): `ansina-tui` is the only operator UI Ansina will ever have — no internal WebUI, permanently, per §2's channel refusal in `docs/architecture/blueprint.md`. It is a dependency-isolated client over the REST API only (never imports `ansina`), read-only in M4 (no pause/resume, no user/role management — mutations stay CLI-side, where confirmation and sudo prompting are unambiguous), with `ansina-tui api` as the universal wrapper reaching every route with no allow-list to drift. The authorization model now has three resource policy classes, named together here since no other single place does: ordinary resources (Read=GET, Write=+POST/PUT/PATCH, Maintain/Admin=+DELETE), `auth.*` (Maintain/Admin only, every mutation additionally sudo-gated for `Maintain`), and `me.*` (every verb, every role — the subject of a `me.*` action is always the caller, so it is never an escalation).
- **Issue #35 (done)** is M4's last issue and is documentation-only (no code change): it brought `README.md` (a new control-surface section plus the `me.*` cross-reference), `docs/architecture/blueprint.md` (a control-surface rationale in §3, M3+M4 added to the §4 roadmap with M4 explicitly ordered before M3, and a third testing-strategy layer in §5 for `tui/tests/unit/`), this file's Layers 3–5, and the M3 milestone body's open-considerations section into alignment with what #30/#28/#31–#34 actually shipped. Two things #35 scoped as work turned out to already be in place by the time it was picked up: `README.md`'s API table already listed `GET /auth/me` and the three `/auth/me/tokens` routes (landed with #30/#28), and the M3 milestone body already carried a `🔄 M4 alignment` block covering the `me.*`-as-third-class and fail-closed-sudo cross-check inputs this issue was meant to hand it — only item #11's own strike-through and a "shipped" addendum were still needed there.
- No channel concept anywhere (no Discord/WhatsApp/etc., and no `ChannelId`-shaped abstraction either) — see `docs/architecture/blueprint.md` §2 for why this is refused deliberately, not an oversight.
- Primary deployment target is a Mac Mini (Apple M4, 16 GB unified memory) — adapter and performance decisions prioritize that hardware, not the local dev machine.
- **RBAC identity & access control** (M2 milestone, complete — `src/ansina/auth/` + `api/authorization.py`/`api/route_audit.py`/`api/routes/{sudo,users,groups,role_assignments,roles,permissions,me}.py`): replaces #5's one-shared-secret model with real `User`/`Group` identity and a permission model keyed on data, not code — "is there a `role_permissions` row granting (a role, a resource, a verb)?" is the entire authorization question, for both builtin and (future) admin-defined roles. Issue #24 shipped the data model, hashing, the builtin-role reconciler, and — pulled forward from #25's original scope, since the alternative was an unauthenticatable server (an auto-generated bootstrap token, by design, is never in config for a static comparison to check) — `api/auth.py`'s DB-backed bearer-token verification. Issue #25 built the rest on top: a formal `Authenticator` chain (`auth.authenticator`, formalizing #24's inline lookup — pluggable, an OIDC authenticator is a future append, not a rewrite), the request-scoped `Principal`, the `require(resource)` authorization dependency (403 on no matching `role_permissions` row, distinguishable from `BearerAuthMiddleware`'s 401 without leaking which credential component was wrong), and the mandatory startup route-coverage audit that also became the `resources` catalog's real source (replacing #24's `BOOTSTRAP_RESOURCES` seed, since deleted) — retrofitted onto every existing route (`system.version`, `heart.tick`, and #25's own `system.openapi`). Issue #26 shipped sudo step-up for `Maintain` on sensitive `auth.*` actions: a pluggable `StepUpVerifier` port (`auth.step_up`, one password implementation in M2) behind `POST /auth/sudo`, grant issuance/TTL/revocation/lockout in `auth.sudo.SudoService` (verifier-agnostic — a follow-up milestone's second verifier is a new `StepUpVerifier`, not a rewrite), elevation via `BearerAuthMiddleware` reading `X-Sudo-Token`, and the break-glass `DELETE /auth/sudo/grants` — the first route to actually pass `sensitive=True`, proving `authorize()`'s `SudoRequiredError` branch end to end before #27 (Users/Groups/Roles management, the routes this mechanism actually exists for) had landed. Issue #27 (done) closes the milestone: Users/Groups/Roles management over the REST API itself (`api/routes/users.py`/`groups.py`/`role_assignments.py`/`roles.py`/`permissions.py`), `Admin`/`Maintain` only with every mutation sudo-gated for `Maintain` — the first routes to declare an `auth.*` resource beyond `auth.sudo`/`auth.sudo.grants`, and the first to make that sudo gate protect something other than a break-glass route. Two guards in `auth.management` (`assert_may_assign_role`, `assert_admin_remains`) enforce server-side, not just documented, that no caller can grant a permission it doesn't itself hold and that the last `Admin` can never be removed; `DELETE /auth/users/{id}` is a one-way tombstone (`0004_user_tombstone.sql`'s `users.deleted_at`), never a row removal. `GET /auth/roles`/`GET /auth/permissions` are read-only discovery — no role write route exists in M2. Custom admin-defined roles and any external identity provider are explicitly out of scope for the whole M2 milestone, deferred to a follow-up that adds rows to #24's tables rather than reworking them.

M3's issue #40 (done) is that follow-up's first half: `POST`/`PATCH`/`DELETE /auth/roles` let an `Admin` (or sudo'd `Maintain`, now that #37's fail-closed gate covers them) define a non-builtin role over the API itself — see Layer 2's `api/routes/roles.py` and `auth/management.py` entries above for the mechanics. Builtin roles remain exactly as read-only and reconciler-owned as M2 left them; only rows with `builtin=0` are ever created, edited, or deleted here. Federated identity (OIDC) and `role_mappings` management are still out of scope, deferred to the rest of M3 (#42–#45).

M3's issue #41 (done) adds the TOTP second factor: `POST`/`GET`/`DELETE /auth/me/totp` (self-service enroll/status/disable) and `DELETE /auth/users/{id}/totp` (the Admin lost-device recovery path) — see Layer 2's `api/routes/me.py`/`users.py`, `auth/totp.py`, `auth/encryption.py`, and `auth/step_up.py`'s `TotpStepUpVerifier` entries above for the mechanics. Reframed during M3 planning (see the milestone body's open-consideration #3 resolution below) as the universal step-up factor for any local, token-only user — not an OIDC-specific feature — since `CreateUserRequest.password` being optional makes password-less the default shape of an Admin-created user, and such a user has no other possible sudo factor. TOTP is step-up-only: it never appears at the bearer-token authentication path or (once #43 lands) at `POST /auth/oidc/*`.

M3's issue #42 (done) gives `role_mappings` — empty since M2 — its management API and a way to record provenance: `GET`/`POST`/`DELETE /auth/role-mappings` (resource `auth.role_mappings`, no policy change needed — see Layer 2's `api/routes/role_mappings.py` entry) and the standalone `auth.role_sync.sync_mapped_roles(db, user_id, provider, claims)` primitive, tested here against a synthetic claims dict, ahead of #43 giving it its first HTTP caller. The new `role_assignments.source` column (`'local'` or a provider identifier, `0007_role_mapping_provenance.sql`) is what lets #43's claims-based login sync reconcile exactly the assignments *it* created without ever reading, adding, or removing a manually (`'local'`) assigned role or another provider's — resolves M3's open considerations #2 (no provenance) and #10 (no management API/uniqueness). `POST /auth/role-mappings` is checked against the same self-escalation guard role assignment itself uses, treating a mapping as a deferred assignment onto the role it names.

M3's issue #43 (done) is the milestone's last originally-scoped piece: federated login via OAuth 2.0/OIDC, shaped as a **login exchange** (`POST /auth/oidc/login` + `GET /auth/oidc/callback`) rather than a per-request authenticator — M3's open consideration #5's resolution. The authorization-code + PKCE flow runs once per login: discover the IdP, mint/persist `state`/`nonce`/`code_verifier`, redeem the code, validate the ID token (signature pinned to asymmetric algorithms only, issuer, audience, expiry, and nonce — each an independent rejection, all checked before anything else runs), JIT-provision or link the Ansina user, refresh its `role_mappings`-derived roles via #42's `sync_mapped_roles` on *every* login (not only the first), and mint a short-lived `api_token` via #39's `ttl_seconds` seam — the first HTTP-reachable caller of it. Every later request stays on the unmodified `ApiTokenAuthenticator`; `Authenticator`, `BearerAuthMiddleware`, `resolve_principal`, and the entire `tui/` client are untouched by this issue. `/auth/oidc/login`/`/auth/oidc/callback` are the first non-health-probe entries in `api/auth.py`'s `PUBLIC_PATHS` — a caller cannot be authenticated before it has logged in — called out here plainly, as the milestone's own AC requires, rather than left implicit. Username-collision handling on JIT provisioning was a real design decision, not an oversight: a claims-derived username matching an existing *local* user **links** the IdP subject onto that account (letting an operator migrate a local user onto the IdP with no separate step) rather than refusing or auto-disambiguating, logged as a `logger.warning` naming both identities since it confers that account's roles on the IdP subject — narrowed by three refusals (tombstoned, deactivated, or the bootstrap identity). See Layer 2's `auth/oidc.py`/`auth/oidc_login.py`/`api/routes/oidc.py` entries for the full mechanics. PKCE (RFC 7636, S256) is included though not named in the issue's own written scope — a deliberate widening, not scope creep by omission. Out of scope, as originally planned: any identity provider beyond OIDC-compliant ones, and an OIDC re-auth `StepUpVerifier` (dropped during M3 planning — #41's TOTP covers the same "no local password forced on a federated user" intent without a second code flow).

M3's issue #47 (done) is a narrow follow-up filed out of #38's own review, closing the one gap #38 deliberately left open: #38 made `GET /auth/permissions` report only each resource's actually-served verbs (`resources.verbs`), but left `reconcile_builtin_roles` (`auth/reconciler.py`) still materializing every `permitted_verbs()`-predicted grant regardless of what a route serves — so a builtin role could hold e.g. `system.version:DELETE` in `role_permissions` even though no route answers `DELETE /version`, a discoverability inconsistency `GET /auth/roles` would otherwise surface. The fix is a one-line change in scope: the reconciler's desired-grant set is now `permitted_verbs(slug, resource.name) & resource.verbs`, so a builtin role's materialized grants can never exceed what the served-verb catalog admits — see Layer 2's `auth/reconciler.py` entry above for the mechanics. `auth.policy.permitted_verbs`'s own signature and policy semantics are untouched (out of scope by design), and custom-role grant validation at request time remains #40's own `assert_grants_grantable`, unaffected by this issue. The first boot after this ships is a deliberate one-time visible diff, called out here as the issue itself required: any builtin role holding a pre-#47 over-grant loses it via the reconciler's existing prune loop.

M4's issue #30 — the first of M4's two daemon-side issues (the milestone is otherwise a client, `tui/`) — extends this policy with a third resource class: `me.*`, self-resources whose subject is always the authenticated caller, granted every verb by every builtin role unconditionally (`auth.policy.is_self_resource`, checked first in `permitted_verbs()`) — not an escalation, since a `me.*` route can never reach another user's data by construction. `GET /auth/me` (`api/routes/me.py`, resource `me.profile`) is the first route on it, returning the already-resolved `Principal` with no database read and never sudo-gated. `api/identity.py` (new) holds `current_principal()`/`no_identity_response()`, the shared "resolved `Principal` or a 401" helpers `sudo.py`, `role_assignments.py`, and `me.py` all now share.

M4's issue #28 (done) adds `me.tokens` on the same prefix — self-service API token issuance/listing/revocation (`POST`/`GET /auth/me/tokens`, `DELETE /auth/me/tokens/{id}`), plus the admin-on-behalf-of equivalents on `auth.users` (`GET /auth/users/{id}/tokens`, `DELETE /auth/users/{id}/tokens/{token_id}`, and a narrowed `POST` — first-credential-only, 409 on a second) — and, while reviewing how the bootstrap credential's rotation worked, redesigns the bootstrap identity itself: it splits into a permanent, never-overridable, never-rotated **bootstrap identity** (auto-generated every first boot, capped at exactly one `api_token` ever) and a separate, ordinary **configured admin** (`ANSINA_SECURITY__ADMIN_USERNAME`+`API_TOKEN`, required together, provisioned once at first boot) that a scripted install or CI actually wants a reproducible credential from — see `docs/architecture/blueprint.md`'s "Bootstrap identity vs. configured admin" for the full reasoning, and Layer 2's `auth/bootstrap.py`/`auth/management.py` entries above for the mechanics. `last_used_at` bookkeeping (also #28) is coalesced, not per-request, per `[security] token_last_used_resolution_seconds`.

Issue #31 (done) lands the client side's foundation: `tui/` itself (see Layer 2), proven end to end by one real command, `ansina-tui status`, against a live daemon. The real end-to-end run on a live Cloudflare R2 bucket surfaced two genuine bugs this issue's own unit suite couldn't have caught, both fixed rather than deferred — the same "fix what the hardware/real binary finds" precedent #54/#56 already set:

1. **Every Vector release after ~0.45 is incompatible with R2.** A real `vector validate`/spawn against this project's own bucket reproduced `InvalidRequest: You can only specify one non-default checksum at a time` on `0.59.0` — `aws-sdk-rust`'s client now defaults to adding its own `x-amz-checksum-*` request checksum (awslabs/aws-sdk-rust#1240) on top of Vector's own long-standing `Content-MD5` header, a combination plain AWS S3 tolerates but R2 rejects outright. Independently confirmed by other reporters (vectordotdev/vector#23029); a fix exists (vectordotdev/vector#25803) but is **not merged or released as of this writing**. `ansina.dev.vector`'s own module-level comment carries the full citation trail. **Ansina's Dev Mode is pinned to Vector 0.45.x** until that fix ships — not a preference, a load-bearing compatibility requirement discovered empirically, not assumed. A second, smaller consequence of that same older baseline: `0.45.0` has no `--dangerously-allow-env-var-interpolation` flag at all (`${VAR}` interpolation is its unconditional default), so neither `preflight()`'s own `vector validate` call nor the real spawn argv passes it — passing it to `0.45.0` is a hard CLI error.
2. **`uvicorn.run()` never returns on a real SIGINT/SIGTERM, so a plain `try`/`finally` around it cannot stop the sidecar.** `uvicorn.Server.capture_signals()` (`uvicorn/server.py`) installs its own handler for the duration of serving and, once its own graceful HTTP shutdown is fully done, restores whatever handler was active beforehand and redelivers the *same* signal through it — "to trigger the expected behaviour" (its own comment). With nothing installed ahead of `uvicorn.run()`, that's the OS default (terminate), so the process dies from inside `Server.run()` itself; confirmed by direct observation — a real `ansina --dev` process sent a real SIGTERM completed uvicorn's own full shutdown log sequence and then simply ceased to exist, every time, leaving Vector orphaned. The fix (`posture.py`'s `_install_shutdown_hook`) installs a handler for the same two signals *before* `uvicorn.run()` runs, so `capture_signals()` captures *that* handler as the one to restore-and-replay through; it stops the sidecar, restores the pre-hook disposition, and redelivers the signal once more via `os.kill` — the identical restore-then-replay idiom uvicorn's own code already relies on, so the process still exits with the exact signal-termination semantics a caller (`tests/e2e`'s own `process.returncode == -signal.SIGTERM` assertion, a real process supervisor) already expects. The `finally` around the `with` block is kept as the backstop for the non-signal exit path (an exception raised inside it); `SupervisedProcess.stop()` being idempotent means both paths running is harmless.
